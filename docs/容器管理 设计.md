# 容器管理 设计

> 状态（2026-10-15）：用户确认以 Arcane 为蓝本，要求整个容器管理做完。**D0–D4 全部实现**（本机单测 + 冒烟通过），
> 上真机需要改 compose 并 `docker compose up -d`，见 `docs/归档/2026-10-15 容器管理 D0–D3.md`（D4 记在同一份末尾）。

2026-10-15。目标：在 Kura 里管 NAS 上的 Docker，不再依赖绿联自带的 Docker 界面（那个没法自定义）。
**以 [Arcane](https://getarcane.app/docs/docker/projects) 的产品形态为蓝本**，按 Kura 的范围（单设备、单用户、只做 Windows 客户端）裁剪。

## 一、从 Arcane 借什么、不借什么

| 借 | Arcane 的做法 | Kura 里怎么落 |
|-|-|-|
| 项目为主、容器为辅 | 「项目」= 一个文件夹（compose + `.env` + 其他文件），作为一个整体部署；「容器」页管所有容器，包括不在项目里的 | 同样两层。项目列表显示状态（运行中 / 部分运行 / 已停止）、服务数、目录 |
| 不扣押文件 | 项目文件就放在磁盘上，扫描目录发现在外面建的项目 | 不另存一份配置；读容器上 Docker Compose 自己打的标签找到项目目录 |
| 控制动作 | Up / Down / Restart / Redeploy（拉镜像再起）/ Destroy | 照搬这五个，名字用中文：启动 / 停止并移除 / 重启 / 更新并重建 / 删除项目 |
| 危险操作显式勾选 | 删项目时选保留还是删除卷与文件；「重建变更的卷（丢数据）」默认不勾、每次部署后复位 | 照搬。默认值永远是不丢数据的那个 |
| 输出实时可见 | 部署、重建、拉镜像可选「查看输出」，实时流 Docker 输出 | 这三个动作一律在面板里实时流输出，失败时停在原因上，不转圈 |
| compose 与 `.env` 并排编辑 | 两个编辑器并排，`Ctrl+S` 保存；compose 和 `.env` 是受保护文件，不能从文件树里改名删除 | 照搬并排编辑；保存前先 `docker compose config` 校验 |
| 日志 | 实时流、识别 JSON 日志、把多行堆栈归成一条、旁边有 CPU / 内存小图、可下载完整日志 | 实时流 + 下载 + 旁边的资源小图；结构化渲染放后面 |
| 更新提示 | 按镜像 digest 判断有没有新版，「有更新」角标；手动或定时更新 | **只做提示与手动更新**，自动更新继续交给 NAS 上已有的 watchtower |
| 删除保护 | 被容器用着的镜像、卷不能删；运行中的容器要勾「强制」才能删 | 照搬 |
| 活动记录 | 每个动作进活动中心 | 每个写操作进审计日志，界面上能看最近记录 |

**不借**（超出 Kura 范围或现阶段用不上）：多主机 / Swarm、权限与角色、Git 同步、构建镜像、漏洞扫描、
卷备份（Rustic）、模板库、按版本号跟随的 tag 更新策略、容器转 compose（实验功能）、卷内文件编辑。

**Kura 独有**：容器卡片和「服务映射」卡片互相跳转 —— kura-server 的服务清单里写着 `backend: http://openlist:5244`，
按容器名就能对上，点一下就到本机地址。这是别的工具做不到的，它们不知道映射。

## 二、架构

```
客户端「容器」页 ── IPC ── 主进程 DockerService
                              │ Mirror.internalEndpoint('docker')   ← 和 webdav / nas-console 同一条路
                              ▼
                     kura-server 内置服务 docker（新）
                       ├─ 只读：转 Docker Engine API（白名单接口）
                       ├─ 写：  容器启停删、镜像拉删（Engine API）
                       ├─ 项目：执行 docker compose（子进程，输出流回）
                       └─ 审计：每个写操作一行 JSON
                              │ /var/run/docker.sock
                              ▼
                           NAS 上的 dockerd
```

几条决定：

1. **走「内置服务」，不走网关的一次性请求。** `gatewayRequest` 一次最多读 1 MiB、30 秒超时，
   装不下实时日志和 compose 输出。注册成内置服务 `docker` 后，客户端用 `internalEndpoint('docker')`
   拿到本机回环地址，流式、WebSocket、链路切换、会话续期全部复用映射层 —— 符合 AGENTS.md「一切能力建在映射层之上」。
   中继支持 WebSocket 已经实测过，外网下也能看实时日志。
2. **kura-server 只暴露自己定义的接口，不透传 Docker API。** `docker.sock` 等于宿主 root，
   透传就等于把 root 交给任何能连到 8898 的人。白名单从现在的一条（`GET /containers/json`）扩成下面 §四 的那张表，
   每条在代码里显式列出；compose 里 `docker.sock` 的 `:ro` 挡不住 API 写操作，真正的边界一直是这张白名单。
3. **compose 在 kura-server 容器里执行**，不放进特权的 kura-shell。docker.sock 本身就够用，没必要再扩大特权容器的职责。
   镜像里加 `docker-cli` 与 `docker-cli-compose`（Alpine 包，固定版本）。
4. **传输层不认识 Docker。** 映射核心一行不改；Docker 的知识只在 kura-server 的 `docker` 模块和客户端的 `DockerService` 里。

## 三、项目从哪来

Docker Compose 会给每个容器打这几个标签，Kura 靠它们找项目，不自己记：

| 标签 | 用途 |
|-|-|
| `com.docker.compose.project` | 项目名 |
| `com.docker.compose.project.working_dir` | 项目目录（宿主路径） |
| `com.docker.compose.project.config_files` | compose 文件路径 |
| `com.docker.compose.service` | 服务名 |

再加一个**项目目录**（设置里配，默认 `/volume1/docker`）：扫描其中带 compose 文件的子目录，
这样已经停掉、没有容器的项目也能列出来、能重新启动。两边按项目名合并。

**路径要和宿主一致（重要，Dockge / Arcane 都踩过）**：compose 里的相对路径（`./state:/state`）
是按执行 compose 的那个进程看到的目录解析的。kura-server 现在把宿主根挂在 `/host` 下，
如果在 `/host/volume1/docker/x` 里执行 compose，`./state` 会被解析成 `/host/volume1/docker/x/state` 交给 dockerd ——
宿主上根本没有这个路径，dockerd 会**新建一个空目录挂进去**，应用看起来像数据全丢了。
所以项目目录要**按原路径**再挂一次：`/volume1/docker:/volume1/docker`，compose 一律在原路径下执行。
不在这个目录下的项目只读展示，不允许从 Kura 部署（界面上说清为什么）。

## 四、kura-server 接口（`docker` 内置服务）

全部 JSON；流式的用 WebSocket（日志、compose 输出、拉镜像进度）。

| 方法 | 路径 | 说明 | 阶段 |
|-|-|-|-|
| GET | `/api/containers` | 列表：名字、镜像、状态、端口、所属项目、是否 Kura 自己 | D1 |
| GET | `/api/containers/:id` | 详情：精简后的 inspect（环境变量值默认遮住） | D1 |
| GET | `/api/containers/:id/stats` | 一次性 CPU / 内存 | D1 |
| WS | `/api/containers/:id/logs?tail=500` | 实时日志（解开 Docker 的多路复用帧） | D1 |
| GET | `/api/containers/:id/logs/download` | 完整日志纯文本 | D1 |
| GET | `/api/projects`、`/api/projects/:name` | 项目列表与详情（服务、状态、目录） | D1 |
| GET | `/api/images` | 镜像列表：标签、大小、被谁用 | D1 |
| POST | `/api/containers/:id/{start,stop,restart}` | 启停 | D2 |
| DELETE | `/api/containers/:id?force=1` | 删除；运行中必须带 force | D2 |
| WS | `/api/projects/:name/{up,down,restart,redeploy}` | 执行 compose，输出流回；结束帧带退出码 | D2 |
| WS | `/api/images/pull` | 拉镜像，流进度 | D2 |
| DELETE | `/api/images/:id`、POST `/api/images/prune` | 删镜像（被用着的拒绝）、清理悬空 / 未使用 | D2 |
| GET | `/api/activity` | 最近审计 | D2 |
| GET/PUT | `/api/projects/:name/files` | 读写 compose 与 `.env`；PUT 先校验再落盘，旧版本留 `.kura-bak/` | D3 |
| POST | `/api/projects` | 新建项目（建目录、写文件，可选立即启动） | D3 |
| WS | `/api/projects/:name/remove?volumes=0&files=0` | 删除项目（先 down，成功了再按勾选删文件），卷与文件默认都保留 | D3 |

**动不了 Kura 自己**：带 `com.docker.compose.project=kura-server` 的容器（kura-server、kura-shell）
只读展示，停止 / 删除 / 重建一律拒绝 —— 在 Kura 里停掉 kura-server 等于把自己连接的那根线剪了，操作做到一半就断。
它们的更新继续交给 watchtower。

**审计**：沿用 `AuditLog`（`.jsonl`），新增 `docker-*` 动作类型：谁（来源 IP）、什么时候、对哪个对象、什么参数、结果。

## 五、客户端「容器」页

侧栏新增一页「容器」，三个标签：

- **项目**：卡片或表格，状态点 + 服务数 + 目录 + 「有更新」角标。点进去是项目详情：
  服务列表（每个服务一行：状态、端口、映射卡片链接）、控制按钮、输出面板；D3 起有「编辑」标签（compose 与 `.env` 并排）。
- **容器**：表格，按状态 / 项目筛选，搜索名字。详情抽屉：概览、端口、挂载、环境变量（默认遮住值）、日志。
- **镜像**：表格，被谁用、大小、是否悬空；「清理」按钮。

交互约定：

- 写操作按钮在执行中变成「进行中…」并禁用，输出面板自动展开；完成后立刻拉一次最新状态（不等轮询）。
- 危险操作走 `ConfirmDialog`，说清后果；勾选项默认是安全的那个。
- 轮询只在页面可见时跑（和映射页同一套规矩）；日志、输出走 WebSocket，不轮询。
- 界面只用 Sakura UI；终端 / 日志区沿用现有 xterm 与等宽字体。

## 六、分步

| 步 | 内容 | 判据 |
|-|-|-|
| D0 | NAS 只读调研（见 §七），**每条命令先给你看** | 能回答 §七 的四个问题 |
| D1 | 只读：容器、项目、镜像列表；容器详情、实时日志、下载日志；和映射卡片互链 | 假 dockerd 上单测 + 冒烟；真机上列表与 `docker ps` 一致 |
| D2 | 操作：容器启停删、项目启停重建（compose 输出实时可见）、镜像拉删清理、审计与最近记录 | 每个写操作都进审计；动 kura-server 自己的请求被拒 |
| D3 | 编辑：compose 与 `.env` 并排编辑、校验、保存前看差异、留旧版本；新建 / 删除项目 | 改坏的 compose 存不进去；删除默认保留卷与文件 |
| D4 | 更新提示（按 digest 比对仓库）、进容器 shell、卷与网络只读页 | 已做：更新只提示不自动装；shell 只能选白名单里的；卷的占用点了才算 |

D1、D2 体量和「补齐遗留」那轮差不多；D3 稍大，主要在编辑器与校验。

## 七、NAS 实测（D0，2026-10-15，只读命令）

1. **绿联界面建的项目也是标准 compose 项目。** 所有容器都带 `com.docker.compose.project*` 标签，
   `docker compose ls` 能看到全部 18 个项目。绿联另有一个 SQLite（`/volume1/@appstore/com.ugreen.docker/db/docker_info_log.db`
   的 `compose` 表），只记 **名字、compose 文件路径、上次部署输出**，**不存 compose 内容**（`content` 列是部署日志）。
   → Kura 改 compose 文件不会被绿联覆盖回去；绿联那张表只是登记，Kura 不碰它。
   绿联只登记了从它界面建的 7 个，其余是命令行建的，绿联界面里本来就看不到。
   绿联登记的路径有一处已经过时（`jmcomic-web` 登记的是 `.yaml`，实际文件是 `.yml`）—— 再次说明以标签为准，不读它的库。
2. **版本**：Docker Engine 29.6.2（API 1.55），Compose v5.1.3（插件）。
3. **项目目录**：绝大多数在 `/volume1/docker/<名字>/`；绿联应用商店装的在 `/volume1/@appstore/com.ugreen.docker.<名字>/`
   （由绿联商店管理，Kura 只读）；还有 3 个 `/tmp/envtest*` 的残留测试项目（已退出）。
   一个项目可以有多个 compose 文件（`astrahub` 有两个），文件名有 `docker-compose.yaml` / `.yml` / `compose.yaml` / `*.nas.yml` 多种。
4. **权限**：`docker.sock` 是 `root:docker 660`，kura-server 容器里是 root，读写都够。
   compose 里那个 `:ro` 只是挂载选项，挡不住经 socket 发的 API 写请求（设计 §二 第 2 条的前提成立）。

5. **「在 /host 下执行 compose 会挂空目录」实测成立**：同一份 openlist compose，按原路径解析出
   `source: /volume1/docker/openlist/openlist-data`，在 `/host/volume1/docker/openlist` 下解析出
   `source: /host/volume1/docker/openlist/openlist-data` —— 宿主上没有这个路径，dockerd 会新建空目录挂进去。
   （验证用了一个临时的 `docker:29-cli` 容器，`--rm`，只跑 `config` 不起服务。）

据此调整：

- 「项目目录」= `/volume1/docker`；容器里**按原路径**再挂一次（`/volume1/docker:/volume1/docker`）。
- `@appstore` 下的项目：可以启停（等同绿联界面里点启停），**不允许编辑 compose**（绿联商店升级会覆盖）。
- 不在项目目录下、也不在 `@appstore` 下的项目（如 `/tmp/envtest*`）：只读展示，可以「停止并移除」。

## 八、风险

- **权限面变大**：能连到 8898 的人就能管所有容器。终端已经是宿主 root shell，实际新增的风险不大，
  但白名单、审计、删除保护都不能省。局域网侧没有认证的问题（见 kura-server 设计 §三）依旧存在。
- **和 watchtower 抢同一个容器**：用户在 Kura 里手动「更新并重建」的同时，watchtower 也可能在重建。
  操作前检查容器状态，失败时如实报错，不重试。
- **compose 版本差异**：容器里的 compose 和宿主上的不是同一个版本时，个别新语法可能表现不同。D0 先确认版本。

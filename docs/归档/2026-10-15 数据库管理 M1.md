# 数据库管理 M1

2026-10-15。在 Kura 里管 NAS 上 Docker 里的数据库：一键装、把端口开到本机回环给本地程序直连、
在客户端里跑命令。**主要使用方是 AI（MCP 是主线）** —— 用户原话"客户端功能可以不用特别专业，
但是能支持命令操作，后面大多是 AI 在使用"。

设计见 `docs/数据库管理 设计.md`（决策与取舍都写在那份里，这里只记过程与踩过的坑）。

---

## 做了什么

**服务端（`server/src/db/`，新增）**

- `templates.ts`：PG / MySQL / MariaDB / Redis 的 compose 模板。绑定挂载 `./data`、**不写 `ports:`**、
  固定镜像 tag、Redis 必须 `--requirepass`；口令字符集刻意排掉 shell 特殊字符。
- `registry.ts`：登记表 `state/databases.json`（**不存口令**），与容器标签合并；从镜像名认出引擎，
  看不见的容器也算「接管的已有数据库」。
- `tunnel.ts`：`TunnelService` —— **白名单唯一入口**。三层防线：登记表为空一律 403、未登记 404、
  容器必须存在且在跑。只接受容器名做目标。
- `handler.ts`：`/api/db/*`，挂在**已有的 docker 内置服务**下（不新增内置服务名，见「踩过的坑」）。
  含 `WS /:name/tunnel` 与 `WS /:name/exec`。

**客户端**

- `src/core/tunnel-pump.ts` + `src/core/tcp-listener.ts` + `src/core/db-client.ts`（新增）。
- `src/main/db-tunnel.ts`：`DbTunnelService`，本机端口偏好落 `tunnels.json`。
- `src/main/features.ts`：`DatabaseService`；`src/main/mcp-tools.ts`：7 个 `kura_db_*` 工具。
- `src/renderer/DatabasesView.tsx`：列表 / 连接信息 / 命令台 / 安装 四块。

**engine.ts 的改动**：`createExec` / `startExec` 加 `{ tty }`（默认 `true`，现有容器 shell 不受影响）；
新写 `createStreamDemuxer()` 保留流身份（**没动** `createLogDemuxer`，容器日志那条路别碰）。

## 踩过的坑

### 1. 内置服务名不能随便加（差点在本机凭空多一个 5432 监听）

一上来想的是给 kura-server 加个 `db` 内置服务，客户端 `internalEndpoint('db')` 直连。看起来最干净。

**实测是**：`Mirror.attach()` 会对**每一个**内置服务算 `localPort = spec.port`，然后在本机回环上建一个
`ServiceListener` —— 加 `db` 的结果是 Kura 启动时在本机凭空多一个 `127.0.0.1:5432` 的 HTTP 反代监听
（用户本机真跑着 PG 的话还会撞端口，界面上显示「开着但监听失败」）。

**改成**：把 `/api/db/*` 挂在**已有的 `docker`** 内置服务下。`server.ts` 本来就按 path 分派，
`internalEndpoint('docker')` 那条通道带 `x-nas-service: docker` 头、路径原样到达 handler。
映射层、服务清单、本机端口全部零改动。

### 2. 隧道的 WS 早返回会静默丢字节（真机上最难查的那种）

`DbClient.tunnel()` 一开始是起 `new WebSocket(...)` 就返回。单测（`tunnel-pump.test.ts`）与接口层面
全绿；接进冒烟后表现是**「隧道连上了，但一个字节都过不去」**。

**原因是**：`ws.send()` 在 CONNECTING 状态**根本不发送**，只调用回调报错；而泵按 `readyState === OPEN`
过滤 —— 返回时 WS 还没握手完，本地客户端头几个字节于是无声消失。psql 的头几条消息很短，
正好落在这个窗口（本地回环握手只要几毫秒，但架不住 psql 是「连上就发」）。

**改成**：`tunnel()` 等 `open` 再返回（`exec()` 本来就是这么等的）。回归测试
`src/core/db-client.test.ts` 里把假服务端的握手**故意拖慢 120ms** —— 不拖的话客户端可能第一帧就已经 OPEN，
测不出这个坑。

教训：冒烟里那个「真的 TCP echo 当数据库」的设计是值得的。纯单测（假 WS 对象、readyState 一开始就是 1）
永远测不出这一类**时序**问题。

### 3. 冒烟的假 exec 帧形状写错了（对着客户端猜，而不是对着服务端写）

假 NAS 的 `/api/db/:name/exec` 一开始按自己想的写成收 `{type:'run', argv:[...]}`。
**实际客户端发的是 `{cli, args}`**（`DbClient.exec()` 里 `ws.send(JSON.stringify({ cli, args }))`）。
表现是命令台永远「没有输出」。

**改法**：照着 `src/core/db-client.ts` 的 `exec()` 抄帧形状，而不是照着自己的直觉写。
以后写假服务端一律先读真客户端那一侧。

### 4. 冒烟点「安装」点到了标签页上

标签页叫「安装」，提交按钮也叫「安装」，`clickButton('安装')` 按文字找，点到的是标签
（点一个已经选中的标签等于没点）。改成在 `.kura-db-connect` 范围内按前缀找按钮。

### 5. 重启后隧道不恢复（本机程序会突然连不上）

`DbTunnelService.sync()` 认识 `tunnels.json` 里每个库的 `enabled` 偏好，但 `sync()` 只在
数据库相关的 IPC handler 里被调用 —— 于是「上次开着隧道、重启 Kura」时，**本机端口要等用户打开
「数据库」页才会重新监听**。对本地程序（psql、DBeaver、跑着的应用）来说就是「重启后连不上了」。

改成在 `app.whenReady()` 里（`localDav.start()` 之后）主动 `databases.list()` → `dbTunnels.sync()`。
不 await、失败吞掉：还没配好 NAS 连接时这里本来就会失败，而那时也没有隧道要恢复。

### 6. 不能按引擎硬编码端口

NAS 上已有的 `sakura-pg` 是 `postgres:18` 跑在 **5444**，不是 5432。所以连接信息里的端口一律
**从容器实际配置读**（`containerDbPort()` 读 `Ports`），接管模式下也不自动 `up -d`
（绿联商店管的容器更不许改）。冒烟里专门有一条断言盯着「5444 显示出来了」。

## 验证

```
npm run check      # typecheck + kura-server 构建 + vitest + 无窗口冒烟
```

- `npm test`：**372 passed | 6 skipped**（新增 `src/core/tunnel-pump.test.ts`、`src/core/tcp-listener.test.ts`、
  `src/core/db-client.test.ts`、`server/test/db.test.ts`）。
- 冒烟：**63/63 PASS**（新增 6 条：列出 Kura 装的与接管的、5444 按实际端口显示、能给接管的开隧道、
  隧道开在回环上、**经隧道打到「数据库」**、命令台拿到输出与退出码、快捷安装）。
  重启冒烟 7/7。
- 冒烟里那条假「数据库」是一条**真的 TCP echo 服务**：本机 TCP → 本机监听 → WS → 假 NAS → 真 TCP，
  全是真字节搬运，所以坑 2 才被逮到。

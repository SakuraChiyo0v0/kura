# 2026-10-16 表格里滚不动；「清理悬空镜像」堵住前台

用户两张截图、两句话：

- 容器页的容器表**上下滑不动**：「在这个里面没法上下滑动」；
- 点「清理悬空镜像」后那个确认框**一直停在前台转**：「这个建议点击后 变成后台，
  不要一直占用前台 阻塞用户别的操作」。

一个看着像 CSS 小毛病，一个看着像交互设计。查下来两件都不是「小」——
前者是第三方库的一条规则和我们的布局结构凑出来的死角，后者是我们自己把一个
长任务当成了同步调用。

## 一、表格滚不动：`overscroll-behavior: contain` 配了一张滚不到底的表

Sakura UI 给表格滚动区的那条规则（`@sakura-ui/react/dist/styles.css`）：

```css
.sk-table-scroll { overscroll-behavior: contain; border: 1px solid var(--sk-line);
                   border-radius: 13px; max-width: 100%; overflow: auto }
```

**它没有高度上限。** 于是这个滚动容器高度 = 内容高度，`scrollHeight === clientHeight`，
永远纵向滚不动 —— 它里面那张表就那么大，长出来的部分是**外层 `.kura-main`** 在滚。

而 `overscroll-behavior: contain` 的含义正是「滚到头了也别把滚轮传给外层」。
库写它是为了「表格自己滚到底之后，别带着页面一起晃」这个正常意图；
但这里的表格**根本滚不到底**，于是那句「不许传给外层」就一直生效 ——
**滚轮指到表格上，事件被整片吃掉，页面上下一动不动**。想把页面挪一挪，
只能把指针从表格上挪开，滑到表格外面那条窄边上去滚。

`contain` 是按轴生效的，所以只放开纵向就够，横向的仍保留
（表格比窗口宽时，横滚不该带着页面一起晃）：

```css
.kura-main .sk-table-scroll { overscroll-behavior-y: auto }
```

### 怎么确认的（这一段比结论重要）

一开始在真 DOM 上量到 `scrollHeight === clientHeight`、`overscroll-behavior` 是
`contain`，就以为定案了。**但「属性长这样」不等于「行为就是这样」** ——
中间被自己的探针骗过一次：

- 头一版探针用 `webContents.sendInputEvent` 发滚轮，量出来「改前改后都是 0px」；
- 换成 CDP 的 `Input.dispatchMouseEvent` 才是真实数字；
- 而且是**多打几个刻度**才稳（离屏窗口不合成，单发一次常常丢）。

最后拿真应用（真构建产物 + 假桥，无窗口）量的：

| 投递方式 | 改前 | 改后 |
|-|-|-|
| `sendInputEvent` | 0px | 0px |
| CDP `dispatchMouseEvent` | 0px | **480px** |

**`sendInputEvent` 压根不参与滚动链**，用它写断言会得到一条永远绿的假测试。
冒烟里新加的那条判据因此改走 CDP（`src/main/smoke.ts` ⑦d3e2），
并且撤掉修复确认过它会变红（`overscrollBehaviorY=contain … scrollTop=297（起始 600）`）。

冒烟夹具原来只有 3 个容器，那张表**比视口矮、页面本来就不滚** ——
直接加断言也会「过」，但是过在「没有可滚的东西」上。所以给假 NAS 补了 40 行
填充容器（`project: ''`，界面上显示成「（单独）」，不动别的断言）。

## 二、「清理悬空镜像」为什么堵住前台

`ConfirmDialog` 只在 `onConfirm` **返回之后**才关：

```js
await O.run(() => c()) && (E.current = !0, T(!0), M(!1))   // M 才是关
```

而原来那段 `onConfirm` 是这样：

```tsx
const reclaimed = await window.kura!.docker.pruneImages(false)   // 普通 Promise IPC，服务端超时给到 120s
```

`run` 在它挂着的时候把对话框置成 `pending`（按钮变「正在处理…」）。
于是**清理跑多久，那个对话框就在前台占多久**，期间别的操作都做不了 ——
文案上写着「正在处理」，给人的感觉就是程序卡住了。

### 改法：按项目既有的长任务形状走流式

「拉镜像」「重启项目」「删除项目」早就是流式了（`OutputPanel` 右下角浮窗 +
`openStream(kind, target)` + `useStream`）。清理之前只是没跟上，这次补齐：

- kura-server 新增 `WS /api/images/prune?all=1`（`server/src/docker/handler.ts`
  的 `streamPrune`），沿用「先发输出、最后发 `{"type":"exit","code":N}`」那套约定；
- 客户端加 `DockerStreamKind = 'prune'`、`DockerClient.pruneImagesStream()`、
  `features.ts` 的 `open()` 分派、`main/index.ts` 的 kind 白名单；
- `ContainersView` 里 `onConfirm={onPrune}` —— `pruneImages` 只负责「把流开起来、
  把浮窗挂上」就返回，`ConfirmDialog` 立刻关。清理在后台跑。

界面上因此变成：**点确认 → 框立刻关 → 右下角浮窗显示「正在清理悬空镜像…」→
完成/失败弹一条提示 → 列表自己刷新**。

顺带：清理是后台跑的，跑完列表不刷新的话被清掉的镜像还挂在表里，
所以 `ImagesTab` 收一个 `refreshKey`，流结束时 +1 触发重读。

### 保留了一次性接口

`pruneImages()`（一次性 JSON 的那个）**没有删** —— MCP 的 `kura_image_prune`
工具还在用它（那条路是给 AI 客户端一次性拿回 `reclaimedBytes`，不需要流）。
流式是给界面用的另一条路。

## 三、这一版的边界

- **容器管理要新版 `kura-server` 镜像**：流式清理是服务端新增的端点，
  NAS 上还跑着旧镜像时，客户端点清理会收到 404 → 提示服务端太旧。
  其余功能不受影响。推 main 时 `kura-server-image.yml` 会自动构建新镜像，
  真机靠 watchtower 拉（见 `project-kura` 记忆里那两条待办）。
- 表格滚动那条是纯客户端 CSS，装上就生效，不需要动 NAS。

验证口径：两处都按「撤掉修复确认变红」做过 —— 表格 0px→480px，
清理对话框「整段清理期间都不消失」→「600ms 就关、当时清理还在跑」。

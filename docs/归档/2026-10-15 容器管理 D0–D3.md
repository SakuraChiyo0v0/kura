# 容器管理 D0–D3

2026-10-15。在 Kura 里管 NAS 上的 Docker，替代绿联自带的 Docker 界面（那个没法自定义）。产品形态以 Arcane 为蓝本，
设计见 `docs/容器管理 设计.md`。版本号升到 **0.4.0**。

## 做了什么

| 步 | 内容 |
|-|-|
| D0 | NAS 上只读调研（版本、项目在哪、绿联怎么登记、sock 权限、`/host` 路径问题），结论写进设计 §七 |
| D1 | kura-server 新内置服务 `docker`：容器 / 项目 / 镜像列表、详情（密码类环境变量遮住）、资源、实时日志（WebSocket）、下载日志 |
| D2 | 容器启停删、项目启动 / 重启 / 拉镜像重建 / 停止并移除（compose 输出实时流回）、镜像拉取 / 删除 / 清理悬空、审计与「最近操作」 |
| D3 | compose 与 `.env` 并排编辑：保存前看改动 → 服务端 `docker compose config -q` 校验 → 旧版本进 `.kura-bak/`（留 10 份）→ 原子替换；新建项目；删除项目（卷、文件默认都保留，勾了才删） |
| 客户端 | 侧栏新页「容器」：项目 / 容器 / 镜像 / 最近操作四个标签；项目链到服务映射的本机地址（Kura 独有） |

架构要点（细节在设计 §二）：

- 客户端经 `Mirror.internalEndpoint('docker')` 连，和文件、终端同一条路；映射核心一行没改。
- kura-server **不透传 Docker API**：`server/src/docker/engine.ts` 里每个能调的接口一个具名方法，名字逐个校验。
- Kura 自己的容器（`kura-server` 项目）一律只读，按 compose 标签判断，不信界面传的标志。
- 写操作要带 `x-kura-docker: 1` 头（浏览器里的跨站表单发不出来）。
- compose 用参数数组 `spawn`，不经 shell。

- 冒烟新增：项目列表、Kura 自己只读、重启项目输出实时显示、详情里密码遮住、实时日志、与映射互链、编辑 compose（坏的被拒且原因写清 / 能看改动 / 好的存上）。

**没在真机上跑过**：NAS 上还是旧镜像 + 旧 compose。要用需要（每条命令先确认）：

1. push 后等 CI 出新镜像（镜像里多了 `docker-cli` / `docker-cli-compose`）；
2. 把仓库里 `server/deploy/docker-compose.yaml` 的改动同步到 NAS 的 `/volume1/docker/kura-server/`

3. 在 NAS 上 `docker compose up -d` 让挂载生效。

## 踩过的坑

### 1. 「在 /host 下执行 compose」会挂空目录 —— 实测成立

以为 kura-server 已经把宿主根挂在 `/host`，在 `/host/volume1/docker/x` 下跑 compose 就行。
实测同一份 openlist compose：原路径下解析成 `source: /volume1/docker/openlist/openlist-data`，
`/host` 下解析成 `source: /host/volume1/docker/openlist/openlist-data` —— 这个路径宿主上不存在，dockerd 会新建空目录挂进去，
应用看起来像数据全丢了。所以项目目录必须**按原路径**再挂一次，compose 一律在原路径下执行。
绿联商店的项目（`/volume1/@appstore/...`）没挂原路径，所以只读（落到 external，只能停止）。

（验证这条时在 NAS 上临时拉了一个 `docker:29-cli` 镜像跑了一次 `config`，`--rm`，没起服务。镜像留在 NAS 上了，约几十 MB，不用可以删。）

### 2. 绿联的 Docker 数据库不存 compose 内容

担心 Kura 改了 compose，绿联界面会用自己存的那份覆盖回去。实测 `docker_info_log.db` 的 `compose` 表只有名字、路径和
上次部署的**输出日志**（`content` 列名字起得像内容，其实是日志），所以不会覆盖。而且它登记的路径已经过时
（`jmcomic-web` 登记 `.yaml`、实际是 `.yml`），说明以 compose 标签为准是对的。

### 3. `:ro` 挂的 docker.sock 照样能写

compose 里 `docker.sock:/var/run/docker.sock:ro` 看着像只读，实际只是挂载选项：经 socket 发的 API 写请求不受影响。
真正的边界一直是代码里的白名单，compose 注释已改正，免得以后有人以为「反正是 :ro」就随手加接口。

### 4. `npm run check` 里打包后的接线测试一直在静默跳过

`docker-wiring.test.ts` 依赖 `dist/server/main.mjs`，没有就 `skipIf` 跳过。以为 check 跑过了它，
实际 `build.mjs` 开头会清空整个 `dist/`，那个文件永远不在。改成 check 里先 `node server/build.mjs` 再跑单测。

### 5. 冒烟里点不到「保存」

按钮文字随「保存后应用」开关变（「保存并应用」/「保存」），冒烟按文字找按钮、又按 `aria-checked` 判断开关——
Sakura 的 `SwitchField` 是原生 checkbox，状态在 `.checked` 上，没有 `aria-checked`。改成按 `data-testid` 找按钮、看 `.checked`。

## 有意的取舍

- **不做自动更新**：NAS 上已经有 watchtower，Kura 只提示「有更新」，用户手动「拉取最新镜像并重建」。
- **`down -v` 不单独露出**：只能经「删除项目」并勾选「同时删除卷」触发；勾了还要输入项目名确认。
- **删项目文件只删认得的**：compose、`.env`、备份；目录里有别的（数据目录）就整个留着，用 `rmdir` 只删空目录。
- **compose 动作不能取消**：关掉输出面板不会杀进程，跑到一半被杀项目会停在半新半旧的状态。
- **编辑器是 textarea**：没引入代码编辑器库（Tab 插两个空格、Ctrl+S 打开保存预览）。

## 补记：同日做完 D4

用户要求「直到完成整个 docker 管理功能」，接着把设计里的 D4 做了：

| 项 | 做法 |
|-|-|
| 有更新 | 「检查更新」按钮：本地镜像的 RepoDigest 对比 dockerd 经 `/distribution/<镜像>/json` 问到的仓库 digest。复用 dockerd 自己的仓库凭据与镜像代理，Kura 不碰仓库凭据。只提示（项目上一个「有更新」标记），不自动装；Kura 自己的镜像不查 |
| 进容器 shell | 容器详情里的「Shell」：`docker exec -it`（exec 建好后用 `Upgrade: tcp` 接管连接，TTY 模式没有多路复用帧）。shell 只能从白名单（bash / ash / sh / zsh）里选；不指定时用一行**写死的** sh 脚本挑一个有的。Kura 自己的容器、没在运行的进不去。开关都进审计 |
| 卷 | 名称、所属项目、谁在用（容器列表自带 `Mounts`，不用逐个 inspect）；占用点了才算（`/system/df` 慢） |
| 网络 | 驱动、子网、网关、成员容器与 IP；Docker 自带的三个排后面 |

验证：`server/test/docker-d4.test.ts`（假 dockerd 支持 exec 升级、distribution、卷、网络）；冒烟加了 shell 回显、检查更新标记、卷与网络。
`npm run check`：单测 **268 passed | 4 skipped** · 冒烟 **39/39** + 重启 **5/5**；连跑 8 次全过。

真机只读核对过（2026-10-15）：

- `/distribution/openlistteam/openlist:latest/json` 返回的 digest 与本地 RepoDigest 一致（会显示「已是最新」）——**但一次要 26.7 秒**，
  NAS 配了国内镜像代理、问 Docker Hub 慢。所以单个查询超时放到 60 秒、服务端 6 个并发、客户端整批等 10 分钟。
- 卷（6 个）、网络、容器列表里的 `Mounts` 字段，形状都和代码假设的一致。
- exec 没在真机上跑过（会在容器里开进程，留到上真机时再验）。

### 坑：假 dockerd 关不掉

给假 dockerd 加了 exec 升级之后，测试的 afterEach 超时 10 秒。接管过的连接不归 `server.closeAllConnections()` 管，
`server.close()` 一直等它。和 proxy 测试里早先踩过的一样：升级过的 socket 自己记下来、stop 时 destroy。

### 坑：冒烟「清单到达后立即更新」偶发失败

8 次里 1 次，`pushed=false`。不是推送坏了：判据从「主进程说 ready」开始只等 1 秒，而推送前有 150ms 合并窗口、
查 snapshot 本身要一次 IPC 往返、轮询判据每 100ms 才看一次，机器忙时卡在边上。判据要证明的是「远小于 3 秒的轮询」，改成 1.5 秒。

## 补记：上真机（同日）

步骤：push 到 main → CI 出镜像；NAS 上的 compose 备份成 `docker-compose.yaml.bak-20261015`、换成仓库版、`config -q` 通过；`docker compose pull && up -d`。

结果：概览接口 200（0.6 秒），22 个容器与 `docker ps -a` 一致，项目分类正确（kura-server 是 self，其余 managed / external）；
容器 shell 对 `sakura-pg` 跑通（bash、尺寸 120×30 生效、回显正确）；网关清单里出现 `docker`。

### 坑：经 kura-shell 重建 kura-server，把自己掐断了

我以为 `setsid nohup` 起的 `compose up -d` 会跑完，实测它停在 `Container kura-shell Recreate` 之后：exec 本身跑在 kura-shell 里，
compose 先停掉旧 kura-shell，执行它的进程跟着没了。现场是旧容器 `Exited`、新容器（带 `<id>_` 前缀的临时名）只到 `Created`，
8898 全挂，中继对所有服务回 `500 failed to forward request`，本机这条 exec 路也断了。

救回来靠的是 NAS 上还留着的**旧独立 nas-console 容器**：用绿联登录链直接拿它 8890 app 域的 cookie，
不经 kura-server 调 `/api/exec`，再跑一次 `up -d` 就起来了。之后客户端要手动 `sync` 一次才重新拉到清单。

遗留：compose 被打断后，新容器保留了临时名（`a65f282eedfe_kura-server`、`f7ebcc657e23_kura-shell`）。compose 按 label 认容器，运行不受影响；
想改回来用 `docker rename` 即可（不重启）。**旧 nas-console 容器先别删**——它是 kura-server 挂了时唯一的外网救援通道。

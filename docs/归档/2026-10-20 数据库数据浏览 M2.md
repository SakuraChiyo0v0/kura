# 2026-10-20 数据库数据浏览（M2 自研面板）

`docs/数据库管理 设计.md` 的 M2 落地：在「数据库 → 数据」页里直接看库里的数据。

顺序按**易到难**：Redis → MySQL/MariaDB → PostgreSQL。

---

## 一、为什么自己写协议，不引驱动

`kura-server` 是「esbuild 打一个文件、镜像里只放 Node」的形态（`server/build.mjs`），
加 `pg` / `mysql2` / `ioredis` 要同时动**构建**和**镜像**两层。而这一版需要的东西很窄：

| 引擎 | 要实现的 | 不做的 |
|-|-|-|
| Redis | RESP2 解析、SCAN/GET/TYPE/TTL/HGETALL 之类 | 集群、哨兵、订阅、RESP3、管道流式 |
| MySQL | 握手 v10、native/caching_sha2 认证、COM_QUERY、结果集 | 预处理语句、游标、压缩、SSL、多语句、LOCAL INFILE |
| PostgreSQL | StartupMessage、md5/SCRAM-SHA-256 认证、扩展查询 | 简单查询、COPY、LISTEN/NOTIFY、SSL |

三份加起来约 1700 行，**零依赖**。对比下「引驱动」要处理的：镜像里放 node_modules、
版本升级跟着镜像走、驱动自身的连接池/重连策略与我们「一问一答、用完就关」的模型打架。

## 二、踩过的坑

### 坑 1：MySQL `if (!pending) continue` 会**静默丢包**

第一版 `onData` 是这么写的（当时想的是「没人等这条应答就跳过」）：

```ts
const pending = this.queue.shift()
if (!pending) continue   // ← 错
```

**我以为是**：一个 `data` 事件最多带一个包，没人在等说明是对端多发的、扔掉就好。
**实测是**：TCP 一次 `data` 常常带**好几个完整的包** —— 一个 5 行的结果集在测试里就是
70 字节、5 个包挤在一起。`queue` 里只有 1 个等待者，剩下 4 个包被直接扔掉，
后续 `read()` 就永远等不到。

**表现**：认证能过、查询发得出去、服务端也回了，客户端就那么挂着。非常难查 ——
所有日志都正常，就是没结果。

**已改成**：收到的包先缓冲进 `inbox`，有等待者就直接给、没有就存着。
PostgreSQL 那份一开始就按缓冲写（见 `postgres.ts` 里 `inbox` 的注释）。

**测试怎么抓到的**：用假服务器发 5 个包、客户端只收到第 1 个 →
`Test timed out`。把修复撤掉，6 条测试立刻变红。

### 坑 2：`Buffer.isUtf8` **不存在**

二进制判定最初写成：

```ts
if (typeof Buffer.isUtf8 === 'function' && !Buffer.isUtf8(value)) { ... }
```

**我以为是**：加个 `typeof` 守卫就兼容了。
**实测是**：`Buffer.isUtf8` 在 Node 24 上**仍然是 undefined**，守卫让整个判断
**静默变成「永远是文本」** —— Redis 里的二进制值会显示成一堆乱码而不报错。

正确的入口是 `node:buffer` 的 `isUtf8`。**已改**。单测里有一条专门守这个
（`decodeMaybe > 非法字节序列明确标成二进制`）。

### 坑 3：注入点必须在**驱动那一层**，不能只在隧道那层

`DbConnector.resolve()` 走 `tunnel.targetOf()` 拿目标（容器名 + 端口）。
测试里没有 docker，容器名解析不了（`ENOTFOUND cache`）。

**我以为是**：给 `TunnelService` 传一个假 `connect` 就够了。
**实测是**：那个 `connect` **只用于隧道**，真正连数据库的是驱动自己
（`RedisClient.connect({ host: db.host })`），它照样去解析容器名。

**已改**：`DbConnector` 把 `connect` 一路透传给驱动（`ResolvedDatabase.connect`），
handler 的 `createDbHandler({ connect })` 是注入点。测试里那条注释写明了这一点。

**这个坑的教训比 bug 本身重要**：只换隧道层的写法会让测试**看起来是绿的**，
实际驱动仍在走真路径。所以「测试通过」这个信号本身要能解释清楚为什么。

### 坑 4：MySQL 的 EOF 与「一行数据」用同一个 0xfe

协议里 `EOF` 包的第一个字节是 `0xfe`，而一行的第一个字节**也可能是** `0xfe`
（长度编码里的 254）。区分靠包长：真 EOF 是 5 字节。

第一版在 `isRowPacket` 里写 `payload.length > 5`，但另一处判 EOF 又写了 `payload.length < 9`
—— 两个地方对同一条规则用了不同阈值。现在统一为「5 字节」，
两处写在一起（`query()` 里的注释）。

### 坑 5：SCRAM 的 `authMessage` 是三段拼，**第一段不含 `n,,`**

```
authMessage = client-first-bare + "," + server-first + "," + client-final-without-proof
```

`client-first-bare` 是 `n=user,r=nonce`，**不含**前面的 `n,,`。拼错了服务端会回
`invalid-proof`，看起来像「口令错」，其实是格式错。

验证方式：**直接用 RFC 7677 的官方测试向量**（`db-postgres.test.ts`），
不是自己算一份期望值 —— 自己算的话实现犯同一个错，测试就是绿的而连不上真库。

### 坑 6：PostgreSQL 的 `bytea` 在文本格式下是 `\x...`，**不是原始字节**

PG 的文本格式（format=0）里，`bytea` 传过来的就是 ASCII 的 `\xdeadbeef`。
MySQL 则相反：BLOB 传的是**原始字节**。两边在 `toCell` 里各按自己的形状处理，
不要试图在界面统一 —— 界面只认 `DbCell`。

### 坑 7：PG 的 bool 文本是 `t` / `f`，不是 `true` / `false`

不翻的话界面上显示 `t`。`toCell` 里有这一条（只在非数字、非二进制时判）。

## 三、口令从哪来（接管的容器）

`docs/数据库管理 设计.md` §八 说「不在客户端存数据库口令」。但**接管的容器没有项目 `.env`**
（它们不是 Kura 装的），口令只在容器自己的 `Config.Env` 里。

**顺序**：调用方给的（用户手输）→ 容器 `Config.Env` → 项目 `.env`。

这样接管的库**大多能自动连上**，不用用户每次输。两边都拿不到（比如口令是后来手动
`ALTER USER` 改的）才弹输入框，那份口令**只在组件内存里**，关掉 Kura 就没了。

> 顺带发现：命令台（`exec`）那条路早有人把它改成从容器环境变量读口令了
> （`passwordOf(entry, raw)` + `templates.ts` 的 `clientEnv`），
> 本轮开工时以为要修的那个「MySQL 命令台连不上」其实已经好了。

## 四、上限与截断（都是刻意的）

| 位置 | 上限 | 为什么 |
|-|-|-|
| 一页行数 | 500 | 界面是滚动的，用户只看前几屏；拉 10 万行进来浏览器会卡死 |
| 一条 SQL 返回行数 | 2000 | 超过就截断**并明说** —— 静默截断会让用户以为「这个表就这么多」 |
| 单个文本单元格 | 4000 字符 | 一个大 JSON 字段能把整个结果撑爆 |
| Redis 单值字节 | 64 KiB | 100 MB 的 blob 拉进内存再塞 JSON 会把服务端和界面一起拖死 |
| Redis 一个 key 的元素 | 200 | LIST/ZSET 可能上百万 |
| 一页扫的 key | 500 | SCAN 的 COUNT 只是提示，按返回条数再截一次 |

**分页用 `LIMIT n+1` 判断「后面还有没有」**，不跑 `COUNT(*)` ——
后者在大表上是全表扫描，而浏览数据时用户要的是「下一页」不是精确总数。

## 五、没做的（明确排除）

- **数据编辑**：界面里只能看、能跑 SQL，不能双击改单元格。写操作走 SQL 编辑框。
- **SSL / TLS**：库只在容器网络里，隧道已经加密在 WS 那一层。
- **MySQL 的 `caching_sha2_password` 完整认证**：需要 RSA 加密口令，明确报错让用户
  改用 `mysql_native_password` 或走命令行。
- **PostgreSQL 的 `SCRAM-SHA-256-PLUS`**（通道绑定）与 GSSAPI/SSPI：明确拒绝并说清楚。
- **连接池**：每次请求开一条连接、用完就关。池要处理闲置回收、坏连接剔除、进程退出清理，
  而这里每条请求本来就只有几十毫秒。

## 六、真机验证清单（还没做）

**对着假服务器写协议必然有盲区**（这里踩过「假样本让 bug 一直绿」）。上真机前要验：

1. 装一个 PostgreSQL（17），在「数据」页看到 `public` schema 与表、能翻页、能跑 SQL。
   **重点验 SCRAM** —— 这是唯一一条没在真库上跑过的认证路径。
2. NAS 上已有的 `sakura-pg`（postgres:18 跑在 **5444**，不是 5432）能列出来、能看数据。
   **端口必须从容器实际配置读**，硬编码会连错。
3. 装一个 MySQL 8.4，验 `caching_sha2_password` 的 fast auth 走不走得通。
4. 已有的 Redis 能扫出 key、看到各类型的值。
5. **外网中继下**（不在局域网）同样能看 —— 这条链路和隧道共用，隧道验过就大概率没问题，
   但协议本身是新的。
6. 二进制值（bytea / BLOB）显示成十六进制而不是乱码。
7. 一张有 10 万行的表翻页不卡。

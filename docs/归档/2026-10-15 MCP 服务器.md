# 2026-10-15 MCP 服务器：让 AI 客户端能操纵这台 NAS

给 Kura 加一个 MCP 端点，AI 客户端（Claude Code / Claude Desktop）连上来就能读写 NAS 文件、
管容器、调服务映射、挂 rclone。**不含** NAS 宿主命令执行（没做 `POST /api/exec`）。

---

## 做了什么

- `src/core/mcp.ts`（纯 Node，不碰 electron）：手写 JSON-RPC 2.0 + MCP 的
  `initialize` / `tools/list` / `tools/call` / `ping`，版本协商，令牌生成与恒定时间比对，
  Host / Origin 判定。工具以闭包注入，所以能拿假工具直接单测。
- `src/main/mcp-tools.ts`：工具表（29 个），handler 直接调主进程已有的
  `FileService` / `ContainerService` / `NasScopeService` / `LocalDavService` / `ModuleManager` / `Mirror`。
- `src/main/mcp.ts`：`McpService`，持有 `ServiceListener`（复用回环强制），管启停、端口、令牌落盘。
- 设置页加「MCP」一节（`src/renderer/McpView.tsx`）：开关、端口、运行状态、令牌、可复制的接入命令。

零新依赖。`package.json` 一个包都没加。

## 踩过的坑

### 1. 以为必须实现 SSE，实测不用

**我以为是**：MCP 的 Streamable HTTP 传输要支持 `GET` 开 SSE 流，手写就得处理长连接与
`Last-Event-ID` 重连，否则客户端连不上。

**实测是**：不用。规范里 `GET` 允许回 **405**，表示「这个端点不提供 SSE 流」；`POST` 也允许回
`application/json` 而不是 `text/event-stream`。去翻了官方 SDK 的
`client/streamableHttp.js`，客户端明确把 405 当**预期**情况处理（注释原文：
「405 indicates that the server does not offer an SSE stream at GET endpoint / This is an
expected case that should not trigger an error」），纯 JSON 响应也照收。

**因为**：Kura 的工具都是短操作（列目录、启停容器），没有服务端主动推送的需求。所以一个
请求/响应式的 JSON 服务器就够了，省掉整套 SSE 状态机。这条是整个「手写不引 SDK」能成立的前提 ——
如果非写 SSE 不可，就会转而引官方 SDK。

**已于 2026-10-15 用官方 SDK 客户端实测确认**：`initialize` / `tools/list` / `tools/call` /
错误路径 8 项全通。以后升级协议版本要重跑这个互操作测试，别只看自己的单测。

### 2. `GET` 回 405 是个功能性判据，不是「没实现」

`GET` 与 `DELETE` 都回 405。渲染成文字是「不支持 GET」，看着像偷懒，但**不能改**成 404 或 400 ——
客户端靠 405 这个具体状态码来判定「服务端合法地不提供 SSE」，别的码会被当成错误。

### 3. 冒烟里 MCP 起在端口 0，界面读的是设置那份

冒烟要验 MCP，但真机日常在跑的 Kura 占着 18007，所以起在端口 0（系统挑空闲口）。
`ServiceListener` 支持端口 0（绑定后把真实端口记回去），所以 `view()` 里的 `url` 是真的。

坑在**设置**：一开始只调了 `mcp.apply(true, 0)` 没写 `settingsStore`，结果界面读设置里那份
（默认关、18007）会显示「未启用」，跟实际在跑的对不上。现在冒烟里设置也一并写上。

### 4. `ContainerService.open()` 会广播界面事件，MCP 不能用它

`open()` 是给界面用的：它把输出 `emit` 成 `dockerStreamEvent` 推到所有窗口。AI 拉个镜像，
界面上就会冒出一个「进行中的流」，用户莫名其妙。

**解法**：MCP 的流式操作（compose / pull）改用 `containers.client.project()` / `pull()` 直接收集，
不走 `open()`；日志本来就有不流式的 `logsText()`。这样 AI 的操作不会污染界面状态。

### 5. 令牌存在 0600 文件里、与设置分文件

`mcp.json` 只存令牌（`writeJsonAtomic` 落 0600），开关与端口在 `settings.json`。
分开是因为**令牌是一把钥匙**：它按规范需要在界面上明文显示、可复制、可轮换，
跟普通设置（主题、缩进）的读写语义不同；混在一起后，导出设置或看设置文件时容易顺手把钥匙带出去。

### 6. `Origin` 校验只在头存在时判，正好只挡浏览器

防 DNS 重绑定的标准做法是校验 `Origin`。但如果**没带** `Origin` 也拒，就会误伤命令行客户端 ——
Claude Code 这类不发 `Origin`。所以规则是：`Origin` 存在且非回环才 403，不存在放行。
浏览器一定带 `Origin`，命令行客户端一定不带，这条规则正好把两者分开。

## 没有做的（有意）

- **不含 `POST /api/exec`**（NAS 宿主 root shell）。它是 nas-console 本来为 AI 设计的接口，
  但等于把宿主 root 交出去，本轮明确排除。
- 不做 SSE、不发 session id、不做 `resources` / `prompts` / `logging` 能力。
- 不做 stdio 代理入口（只开回环 HTTP 端点，一个产物）。
- **不另立一套权限**：MCP 调的就是界面上那批能力，边界仍是 kura-server 的具名接口白名单与
  NAS 那份范围。容器工具背后的 `docker.sock` 本身是宿主 root 等价物（见 `docs/交接.md`），
  所以「不含 exec」不等于「低危」—— 破坏性工具靠 `destructiveHint` 标注 + 模型侧提示用户。

## 验证

- 单测 `src/core/mcp.test.ts` **34 项**：版本协商、两类错误（协议 `-32602` vs 执行 `isError`）、
  通知 `202`、`GET 405`、令牌恒定时间比对、非回环 `Origin` / `Host` → 403、令牌轮换。
- 冒烟 **10 项**（`SMOKE 54/54`）：真起监听，走完整 HTTP 路径；含「范围外的路径读不到」
  （证明 AI 受同一份范围裁剪，没有旁路）与「MCP 设置一节显示真实地址与接入命令」。
- 互操作：临时装了官方 `@modelcontextprotocol/sdk` 1.32.1，用它的 `Client` +
  `StreamableHTTPClientTransport` 连手写的服务器，8 项全通（握手、列工具、调用、`isError`、
  未知工具、能力协商、错误令牌被拒）。**这个测试脚本是一次性的，没进仓库** ——
  要是以后协议升级，照这个思路重搭一遍。
- `npm run check` 全绿（typecheck + 330 单测 + 54 冒烟 + 7 重启）。

真机（连真 NAS 的那次）**没做**：本轮验证都在本机假 NAS 上。第一次真接 AI 客户端时要留意
工具描述里的路径是 NAS 绝对路径这一点，别让模型拿本机路径去试。

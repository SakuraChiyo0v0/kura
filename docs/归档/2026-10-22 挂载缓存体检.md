# 2026-10-22 挂载缓存体检：rclone 只按文件大小判断「变了没有」

起因：用户在 NAS 上给音乐改了标签，Windows 里挂载的那个盘一直显示旧标题，刷新、重启都没用。
后来第二次出现（加了年份和歌词），同样的现象。于是把它做成 Kura 里的一等能力。

---

## 一、根因

**rclone 的 VFS 判断「远程文件变没变」只看大小。**

WebDAV 后端拿不到内容哈希 —— 实测 `rclone lsjson --hash` 对 `vendor=other` 和
`vendor=rclone` 都不返回任何哈希。`vfsMeta` 里存的是：

```json
{ "Size": 6444693, "Fingerprint": "6444693", "Dirty": false }
```

`Fingerprint` 就是字节数，别的什么都没有。

### 实测（用 `:local:` 和假 WebDAV 各做了一遍）

| 操作 | 挂载盘读到 |
|-|-|
| 原地覆盖成**同样大小**的新内容，mtime 变新 | ❌ 还是旧的 |
| 改成**差 1 个字节** | ✅ 重新下载，读到新的 |
| 删掉 `vfs/` + `vfsMeta/` 里的条目 | ✅ 立刻重下 |

顺带确认：WebDAV 的 `getetag` 其实带了完整信息
（`"18e0c152d1a835ed3742cd"`，前缀是 mtime 纳秒、后缀是十进制大小），
但 rclone 的 WebDAV 后端没用它。

### 为什么日常必中

改标签最常发生的场景就是**等字节长度**的改名：`年轮` → `花海`，都是 6 字节 UTF-8。
写标签时的 padding 又固定，文件总大小必然完全一致。

## 二、我以为是 A，实测是 B

| 我以为 | 实测 |
|-|-|
| Windows 资源管理器缓存了属性 | 不是，缓存目录里的文件本身就是旧的 |
| rclone 会在 poll 时发现 mtime 变了 | mtime 变了也没用，判据里没有 mtime |
| etag 能帮上忙 | 不能，两个 vendor 都拿不到哈希 |
| 文件被改名，旧缓存条目是孤儿 | 这只是表象，真正的问题是同名文件的内容没换 |
| 「写新文件再删旧文件」能治本 | **不成立** —— 大小由内容决定，先删后写改不了大小 |
| 改成「padding 随内容变」能治本 | 只对 astra 自己写的文件生效；ffmpeg 写的绕过它 |

最后一条是关键的教训：**在 astra 里改 padding 只能治 astra 写的文件**。
NAS 上那批文件带 `TSSE: Lavf62.3.100`（ffmpeg 的手笔），根本没有经过 astra 的 `writeTags`。
所以真正的通用解只能在**读的一侧**——也就是 Kura 里做体检。

## 三、设计：怎么判、怎么补

「不一样」有两类，代价相差两个数量级：

- **只改了标签**：音频流一个字节没动 → 只抄文件头（ID3 区），几十 KB
- **音频真的变了** → 只能整份重下

判据顺序**不能换**：

1. 大小不同 → 音频必然变了，整份重下（连头都不用比）
2. 大小相同 → 比文件头和末尾各一段的哈希
3. 头不同 + **尾相同** → 只补头
4. 其余 → 整份重下

第 3 步的「尾相同」是整个功能的安全底线：只比头的话，
「头和音频都变了」会被误判成「只改了标签」，补完就是一个坏文件。

线上实测（486 个文件的目录）：

```
缓存 214 个条目
├ 内容一致    196
├ 只改了标签   10  → 补 1.2 MB
└ 音频也变了    2  → 重下 16 MB
孤儿（NAS 上已无）6  → 删 5.6 MB

总需下载 17 MB（全量重下要 994 MB）
```

## 四、测试里的两个坑

### 1. 第一版测试拿长短不同的标题去比，撤掉修复照样绿

```ts
const shortTitle = retagMp3(original, { ...tags, title: '年轮' })   // 6 字节
const longTitle  = retagMp3(original, tags)                        // 11 字节
assert.notEqual(shortTitle.length, longTitle.length)
```

长度本来就差 5 字节，padding 写死也撞不上 —— 这个用例从来没在测 bug。
换成两个**等字节长度**的标题（`年轮` / `花海`）后，撤掉修复两条都变红。

**教训**：写「必须变化」的断言时，先问自己「不修的话它会不会失败」。
光跑一遍变绿说明不了什么。

### 2. 测试音频造小了，尾段判定永远为真

第一版 `makeAudio` 只造 200KB 音频，而 `HEAD_BYTES` 是 400KB ——
「头」就覆盖了整个文件，「末尾一不一致」永远成立，
于是「音频变了」也判不出来，测试失败。

真实 mp3 都是几 MB，测试数据得按真实形状造。改成 600KB。

## 五、服务层的坑：首次启动时定时体检被静默关掉

```ts
intervalHours: clampInterval(stored.intervalHours)   // ← undefined → 0 → 等于「关闭」
```

`0` 在设置里表示「关掉定时体检」。没配过的时候 `stored.intervalHours` 是 `undefined`，
`clampInterval` 把它收成 0 —— 于是**新用户从来没有定时体检**，而且界面上看不出来
（开关是关的，但用户没关过）。

改成只有真的存过值才钳。这条是写服务层测试时才抓出来的，属于「测试写对了就有回报」。

## 六、实现要点

- `src/main/cache-doctor.ts`：纯函数，不依赖 Electron，好单测。
  `scanCache()` 只读、`repairCache()` 才动文件。
- `src/main/cache-doctor-service.ts`：管设置、串行化、定时器、进度推送。
- `src/core/dav-client.ts` 新增 `readRange()`：按 HTTP Range 读一段。
  没有它就只能整份下载，「只补标签」失去意义。
- **相对路径的基准是 remote 根**（`vfs/：webdav{xxx}`），不是缓存根。
  第一版测试按缓存根造，扫描结果全是 0。
- `vfs/` 和 `vfsMeta/` 要一起改：文件内容补对了但元数据没更新，rclone 仍会认为没同步。
- 孤儿判定用「远端 stat 返回 404」，不是「列目录时没看到」——
  列目录可能因为范围裁剪、权限而漏项，按后者删会删掉还存在的文件。

## 七、已知限制

- **只认 mp3 的 ID3 头**。FLAC 的元数据块、m4a 的 atom 都没实现，
  这类文件一律退回整份重下（宁可多下，不能补出坏文件）。
- 体检要发大量 PROPFIND + Range GET。486 个文件的目录扫一遍要几分钟，
  所以挂载后自动扫延迟 5 分钟，且只在挂载期间跑。
- 扫描范围是「缓存里已有的条目」，不是整个 NAS。
  范围由缓存自然限住，不会因为用户挂了几个大目录而失控。

## 八、待观察

`--vfs-cache-max-age` 当前是 `87600h`（十年，等于永不），是挂载设置里手改过的值。
不是这次问题的成因，但意味着缓存只在容量超限时才淘汰。
如果体检发现「过期条目长期没人碰」，可以考虑把这个值调短。

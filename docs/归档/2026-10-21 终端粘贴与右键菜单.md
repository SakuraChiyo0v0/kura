# 2026-10-21 终端粘贴的 `^M`、复制粘贴入口、右键菜单

**已变更**：终端页与容器 shell 现在有完整的复制粘贴 —— 右键菜单（复制 / 粘贴 / 全选 / 清屏）、
`Ctrl+C` 有选区时复制、`Ctrl+V` 粘贴，并且**多行粘贴不再打出 `^M`**。
上游 Sakura UI 相应加了 `ContextMenu` 组件（0.2.3）。

---

## 一、`^M` 不是 NAS 的问题

现象是粘贴多行命令时，屏幕上出现一串 `^M`，回车后报：

```
bash: $'\r': command not found
```

我一开始以为要去 shell 侧改（`stty`、`dos2unix` 之类）。实际不是。

**真正的原因在客户端的粘贴路径上**：

1. bash 5.1+ 默认开 **bracketed paste**（`\x1b[200~ … \x1b[201~`）。
   此时 readline **不按键盘映射处理**，把框内的字节**原样**插进编辑缓冲。
2. xterm.js 自带的粘贴处理（打包产物里的 `prepareTextForTerminal`）把换行**一律换成 CR**：
   `text.replace(/\r?\n/g, '\r')`。
3. 框**外**用 CR 是对的 —— 那正是回车键，readline 把它当 `accept-line`。
   框**内**用 CR 就只是一个字面控制字符：既不能换行执行，也去不掉，显示成 `^M`；
   回车执行时它成了命令的一部分，于是 `$'\r': command not found`。

**所以换行要按模式选，不能一律**：

| `term.modes.bracketedPasteMode` | 发出的字节 |
|-|-|
| `true` | `\x1b[200~` + 文本（换行统一 **LF**）+ `\x1b[201~` —— 粘成可编辑的多行，确认后才执行 |
| `false` | 文本（换行统一 **CR**）—— 等于逐行敲回车 |

这也是 Windows Terminal / VS Code 的做法。readline 8.1 起能把 bracketed 里的 LF
显示成真正的多行、可编辑、确认后一次执行，这正是 bracketed paste 的原始目的。

**教训**：「终端里换行就是 `\r`」这个直觉只在「按键」这条路上成立。
粘贴是另一条路，走的是编辑缓冲，两条路的换行语义不一样。

## 二、之前根本没有复制粘贴入口

顺手查出来的：终端里 `Ctrl+C` 永远发 SIGINT，`Ctrl+V` 发 `^V`（quoted-insert），
也没有右键菜单。用户只能靠系统级复制粘贴，而且多行必坏。

现在（`src/renderer/xterm-clipboard.ts`）：

| 操作 | 行为 |
|-|-|
| `Ctrl+C` | **有选区就复制**，没选区才是中断信号（Windows Terminal 的约定） |
| `Ctrl+Shift+C` / `Ctrl+Insert` | 只复制，不管有没有选区 |
| `Ctrl+V` | 粘贴（浏览器派发原生 paste，由我们拦下来自己发） |
| `Ctrl+Shift+V` / `Shift+Insert` | 粘贴（这些组合不派发 paste 事件，直接读剪贴板） |
| 右键 | 复制 / 粘贴 / 全选 / 清屏 |

**想给正在跑的程序发 `^C`**：先按 Esc 清掉选区（选中过东西之后 `Ctrl+C` 优先当复制）。

几个实现上的取舍：

- **粘贴拦截走捕获阶段**（`addEventListener('paste', …, true)`）。xterm 在 textarea 与
  element 上各挂了监听，捕获阶段先跑到，拦得住。只拦这一个入口就同时覆盖了
  `Ctrl+V`、`Shift+Insert` 与右键菜单的「粘贴」—— 比逐个绑快捷键可靠。
- **读剪贴板走新 IPC** `kura:paste-text`。页面是 `file://` 加载的，
  `navigator.clipboard.readText()` 要权限、不可靠。
- **非 bracketed 时的多行粘贴先问一句**。那种模式下每一行都会被立即执行，
  误粘 50 行就是 50 条命令直接跑。用页内 `Banner` 问，不另起对话框。

## 三、反哺上游：`ContextMenu`

Sakura UI 原来只有左键的 `ActionMenu`，没有右键菜单。base-ui 已经有
`@base-ui/react/context-menu`，这是个真正通用的缺口，不是 Kura 专有的形态，所以搬上去了。

- `packages/ui/src/ContextMenu.tsx`，条目结构直接复用 `ActionMenuItem`（不另造一套类型）
- 弹层视觉与 `ActionMenu` 共用 `.sk-action-menu-*` 的样式，只补三条自己的钩子
- 版本 0.2.2 → **0.2.3**，`libraryComponentCount` 43 → 44

**上游的一个坑**：base-ui 的 `ContextMenu` **只认右键与长按，不响应 Shift+F10**，
键盘用户没有入口。我们补了一手 —— 在触发区上接住 `Shift+F10` / 菜单键，
把它变成「在触发区中心派发一次 `contextmenu`」，走 base-ui 自己的同一套路径
（锚点、定位都不用另写）。

补的时候又踩了两个小坑：

1. **base-ui 的开关状态在 React 之外**（store），组件里不订阅 `onOpenChange`
   的话，我们的 `useEffect` 压根不会重跑；从 ref 里读「这次是不是键盘打开的」永远读到旧值。
2. **弹层是下一帧才挂上的**。在 `open` 变 true 的那一帧 `querySelector` 还找不到条目，
   会静默失败、焦点留在弹层容器上。要在 `requestAnimationFrame` 里找。

这两点合起来的表现是「菜单能开、但焦点不在条目上」—— 看起来像键盘操作不支持，
其实是时序问题。

## 四、验证

- **单测** `src/renderer/xterm-clipboard.test.ts`：断言 bracketed 走 LF、非 bracketed 走 CR、
  CRLF 与单独 CR 都归一。**撤掉修复确认变红过**（把 bracketed 分支也改成 CR，
  「bracketed 模式里用 LF」那条立刻失败）。
- **冒烟**新增三条：
  - 假 NAS 连上就发 `\x1b[?2004h`（真 bash 就是这样），并记下收到的粘贴字节；
    断言 `\x1b[200~` 里是 `\n` 且**不含 `\r`** —— 这条直接盯着 `^M` 的成因。
  - 右键终端 → 菜单四项齐全、没选区时「复制」是禁用态。
  - 全选 → 复制 → **回读取系统剪贴板**，证明真写进去了（不是只在界面上点了个按钮）。
- 上游新组件：`tests/context-menu.test.tsx` 5 条（右键打开、禁用项、Esc、空菜单、键盘可开可点）。

**冒烟里两条与本次无关的失败**（`容器页：Kura 自己只读`、`自动更新：立即跑一轮`）：
已经用 `git stash` 在**干净基线**上复跑确认，同样失败 —— 是原有问题，不是这次引入的。

## 五、遗留

- 图片粘贴（`image/png` → 上传到 NAS 再粘路径）没做，是另一个功能
- `copyOnSelect`（选中即复制）、字体缩放、终端内搜索都没做
- 上游全量 `npm run check` 里 `overlays` / `workflow-showcase` / `local-discovery` /
  `live-workbench` 四个文件并行跑会 flaky（计时 + 真实 HTTP/SSE + 子进程抢资源），
  单独复跑全绿；这是已知现象，不是本次改动引起的。

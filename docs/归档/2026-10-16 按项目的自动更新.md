# 2026-10-16 把 watchtower 那件事收进 Kura：按项目的自动更新

## 起点

用户问「能不能让 watchtower 也加入到我们这个体系中」，紧接着澄清「我是说内置成 kura 的功能点」
—— 不是把 watchtower 接进来，是**把自动更新这件事做成 Kura 自己的能力**。

`docs/容器管理 设计.md` 原来写的是「只做提示与手动更新，自动更新继续交给 NAS 上已有的 watchtower」。
这次是把后半句改掉：Kura 也能自动更新，但**只管别人的项目**，自己仍然交给 watchtower。

## 关键的用户约束

中途用户说了一句定方向的话：

> 主要是我不希望有点多零零散散的依赖，其他人没法直接用的

这一句否掉了「再加一个容器」。单起一个 updater 容器意味着：跟着发布第二个镜像、
部署时多 `docker compose` 一次、多一份要配的东西 —— 别人从仓库拉下来想用自动更新，
得先知道还有这么个容器要起。

## 选了哪条路：调度器塞进 kura-server 的 serve() 进程

`server/src/main.ts` 的 `serve()` 本来就：7×24 常驻（compose 里 `restart: unless-stopped`）、
挂着 docker.sock、挂着 `/volume1/docker`、有审计、有 `checkUpdate()`。自动更新要的东西它一样不缺。

所以**新增部署量是零**：现有部署 `docker compose up -d` 换个新镜像就有了，不多一个容器、
不多一个目录、不多一份配置。正好对上那句约束。

独立容器那条路我也核过，代价更大而不是更小：多一个 compose 文件、多一份要一起发布的镜像，
而**隔离并没有变强** —— 它照样得挂 docker.sock，权限跟 kura-server 完全一样。
换来的只是「更干净一点」的错觉。调度器独立成一个模块（`server/src/docker/autoupdate.ts`），
哪天真想拆容器，把它搬走就是。

### 我中途说错的一句话

用户问「可以在 compose 单独起一个容器么 还是必须独立」时，我之前说过「必须独立于被更新的对象」。
这句话**过重了**：真正必要的约束只是「执行更新的进程不能待在**被更新的那个容器**里」。
跟它同不同 compose 项目都无所谓。

顺带在 NAS 上用只读命令核过一件事：compose 的粒度是**项目名**（`-p <name>`），不是目录
（`docker compose ls` 显示 kura-server running(2)、account-panel running(2)）。
所以「在同一个 compose 项目下」技术上可行，但那个项目里的服务会被一起重建
—— 更新器没法更新自己所在项目里的任何东西。用户自己也认了这一点
（「嗯嗯 我理解这个 没法更新自己」）。最后这条也没成为约束：把调度器放进进程里，压根没有「自己」这个容器。

## 边界怎么划

- **按项目 opt-in，默认全关**。不主动给任何项目开，别人的应用不会被 Kura 动到。
- **只对能部署的项目开放**（`managed` / `appstore`）：目录外的项目连 compose 文件都读不到，
  界面上不出现开关，服务端也会拒。这是 `DockerService.kindOf` 早就定下的口径，直接复用。
- **kura-server 自己硬排除**，两道：`set()` 拦一道（界面点不到），每轮更新时再拦一道
  （`state/autoupdate.json` 是可以手改的，不信它）。它继续归 watchtower 管
  —— 这条线就是用户要的「共存」。

### 一个 ordering bug（自己写出来的，测试抓到）

拦自己的那一道我一开始写在 kind 检查**后面**，于是手改状态文件塞进 kura-server 时，
报出来的原因是「这个项目不在项目目录里」—— 技术上不算错（`kindOf` 对 kura-server 返回 `self`，
不在 `updateableKinds` 里），但**对用户是误导**：真正的原因是这个项目根本不归 Kura 管。
把 self 判断提到前面就好了。测试里那条用例断言 reason 要匹配 `/watchtower/`，正好把它钉住。

## 语义：每轮先问再拉

跟界面上「检查更新」和 watchtower 的 label 模式一个口径：

1. 把项目里容器的镜像去重；
2. 逐个 `checkUpdate()` —— **只问仓库 digest，不拉镜像**；
3. 只有真有变化才 `pull` + `up -d`。

没变化就什么都不做，不留无谓的容器重建。`pull` 失败就不跑 `up`：拉不下来说明镜像有问题，
不该把在跑的那些停掉。这条也有单测（断言 pull 失败时 `composeCalls` 只有 `['pull']`）。

## 改了什么

- 新增 `server/src/docker/autoupdate.ts`：开关的读写（`state/autoupdate.json`，复用 `src/core/store.ts`
  的 `readJson` / `writeJsonAtomic`）、调度循环（照 `src/core/watchdog.ts` 那套：`setInterval` +
  重入保护 + `timer.unref()`）、每轮更新逻辑
- `server/src/docker/handler.ts` 加 `/api/auto` 三条路由，**挂在已有的 docker 内置服务下**，
  跟 `/api/db/*` 并列 —— 不新增内置服务名，就不会凭空多一个本机回环监听端口
  （`docs/归档` 里数据库那次踩过，`server/src/db/handler.ts` 顶部有记录）
- `server/src/main.ts` 接线：`AutoUpdate` 起调度，`close()` 里停掉
- 客户端一路：`docker-types.ts`（类型放这里，服务端也 import，一个形状只有一处定义）→
  `docker-client.ts` → `shared/ipc.ts` → `preload` → `main/index.ts` → `ContainersView.tsx`
- 界面：项目行上一个「自动更新」开关 + 工具栏「立即跑一轮」（只在有项目开着时才出现）
- 版本升到 0.8.0（新功能）

## 踩过的坑

### 1. SwitchField 的结构是猜不对的

项目行里的开关要跟按钮排在同一行、不能按 `SwitchField` 默认那套上下堆。我先按猜的选择器
写了一条 `.kura-docker-auto > :not(:first-child)`，**根本没生效** —— 去读
`node_modules/@sakura-ui/react/dist/index.js` 才发现真实结构是
`label.sk-switch-field > span.sk-switch-copy > span.sk-switch-label`，
文字被包在 `copy` 里，`> :not(:first-child)` 选不到它。改成对准 `.sk-switch-label`。

**教训**：UI 库的实际 DOM 要去看，别照着 props 名字猜。

### 2. 单测第一次 4 条失败，其中 3 条是假 dockerd 没登记镜像

`checkUpdate` 走 `inspectImage` 拿本地 `RepoDigests`，而 `FakeDocker.images` 是空的
→ 404 → `status: 'unknown'` → 永远没有「有新版」。测试里得同时给
`docker.images.push(...)`、`repoDigests`、`remoteDigests` 三样。抽了个
`registerImage()` 辅助函数统一登记。

**这条正好印证了项目里那条规矩**：假样本形状不对，测试会一直绿着骗人。

### 3. 一个坏项目会把整轮带下水（写完自己复查才发现的）

`runCompose`（compose.ts）在**项目目录不可达**时是**同步抛**的，不是返回一个非零退出码。
我在 `updateProject` 里只接了 `await run.done` 那条路径，没接同步抛 —— 于是一个目录有问题的项目
会从 `tick()` 冒出去，**同一轮里排在它后面的项目一个都不跑**。

修法是在 `runCompose` 调用点套 try/catch，转成一条 `ok: false` 的结果继续往下走。
测试里加了一条：两个项目都开了、compose 一律同步抛，断言 `results` 有两个、都是失败 ——
撤掉 try/catch 立刻变红（1 failed | 9 passed），恢复又绿。

### 4. 代码审查又挖出五条（自己写的东西自己看不全）

写完让一个独立的 agent 审了一遍，真挖出东西来。逐条核过，五条属实、一条不成立：

**① 绕过了项目锁（最要紧的一条）。** `handler.ts` 里本来就有个 `busy` 集合，注释写着
「同一个项目同时只能有一个 compose；两次 up 叠在一起结果不可预测」—— 但那是 handler 闭包里的私有变量，
**只护住了界面那条路径**。自动更新直接调 `runCompose`，完全绕开了它。
结果就是：自动更新正在 pull + up 的时候，用户在容器页点「重启」，两边同时动同一个项目的容器。
修法是把锁从闭包里搬出来（新的 `server/src/docker/locks.ts`），`main.ts` 造一把给两边用。

**② 一条项目出错会把整轮带下水**（比我先前修的那条更靠前）：`projectImages` 里的
`engine.listContainers()` 没被接住，dockerd 抖一下就从 `tick()` 冒出去；
而 `setInterval(() => void this.tick())` 会把未处理的 rejection 变成 unhandled rejection。
更糟的是 `lastRunAt` / `lastResult` 在循环**末尾**才赋值，中途抛出去就永远不更新，界面上的状态一直是旧的。
修法：`tick()` 里每个项目各自 try/catch，坏的那个记成一条失败结果，其余照跑。

**③ `unknown` 被静默当成「都是最新的」。** `checkUpdate` 在仓库连不上时返回 `status: 'unknown'`
（它自己不抛），而我原来只看 `=== 'update'` —— 于是「问不到」和「确实是新的」被混成一个结论，
用户看到的是「都是最新的」。这两个对用户不一样，现在有 unknown 就如实报出来。

**④ 重入时返回空数组，前端会误报。** 6 小时那轮还在跑的时候点「立即跑一轮」，
`tick()` 直接返回 `[]`，前端把空数组显示成「都是最新的」—— 其实啥也没跑。
修法：`status()` 里带上 `running`，前端据此区分。

**⑤ 名叫 `run` 的项目开不了开关。** 路由里 `POST /api/auto/run`（跑一轮）排在
`/api/auto/:项目名/on` 前面，而 `checkProjectName` 是允许 `run` 这个名字的 ——
点它的开关会被当成「跑一轮」。把 `on` / `off` 的判断提到前面。

**不成立的那条**：审查说「`stop()` 不中断正在跑的轮次，退出时 compose 子进程不会被杀」。
在容器部署下不成立 —— kura-server 容器一停，它的子进程跟着死。没改。

### 5. 验过它真的会红

按老规矩，改完把 `check.status === 'update'` 那个判断改成恒真，重跑
——「没变化就不拉」那条立刻失败（1 failed | 8 passed）。不是怎么改都绿的假测试。

后面补的五条修复也一样各撤一次验过：撤掉 unknown 分支和锁检查，对应的两条立刻红（2 failed | 11 passed）。

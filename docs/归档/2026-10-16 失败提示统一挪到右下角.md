# 2026-10-16 「停止并移除」报 ENOENT，以及把失败提示统一到右下角

起点是用户的一张截图：在容器页对 `envtest2` 点「停止并移除」，输出面板顶部写着

```
无法执行 docker compose: spawn docker ENOENT
```

外加一句需求：**这种提示都做成右下角弹出的**，别随便找个地方提示、让人找不到；
顺手看看项目里其他提示位置是不是也该改。

所以这次是两件事：一个是真 bug（ENOENT），一个是提示位置的统一。

## 一、ENOENT 不是 docker 没装

第一反应是「NAS 上的容器里没有 docker CLI」。**实测不是。**

`envtest2` 这类项目的目录是 `/tmp/envtest2` —— 在 NAS 宿主上真实存在，但
**没有挂进 kura-server 容器**（compose 里只挂了 `/volume1/docker`）。

`server/src/docker/compose.ts` 的 `runCompose` 把 `cwd` 设成了 `target.dir`：

```js
spawn(bin, args, { cwd: target.dir, ... })
```

`cwd` 指向一个**不存在的目录**时，Node 报的正是 `spawn <bin> ENOENT` ——
和你命令行里敲错可执行文件名是同一个 errno。错误信息里那个 `docker` 把人往
「docker 没装」上带，实际是**工作目录不存在**。

（本机验过形状：`spawn(process.execPath, ['-v'], {cwd:'/no/such/dir'})` →
`spawn C:\...\node.exe ENOENT`，连可执行文件的绝对路径都不出现在消息里。）

### 怎么办：down 根本不需要那个目录

翻 `docs/容器管理 设计.md:163`：

> 不在项目目录下、也不在 `@appstore` 下的项目（如 `/tmp/envtest*`）：只读展示，可以「停止并移除」。

设计上这类项目**本来就该能停掉**。而 `docker compose -p <名字> down` 靠的是容器上的
`com.docker.compose.project` 标签找容器与网络，**既不需要 compose 文件，也不需要待在那个目录里**。

所以改成分两路：

- `down`：目录不可达也照跑，`-f` 参数一律省略（没有文件可指），`cwd` 换成 `/`；
- 别的动作（up / restart / pull）：目录不可达就直接抛出说人话的错误
  ——「项目目录 /tmp/envtest2 没有挂进 kura-server，无法执行 compose up」，
  不再让 spawn 抛一句看不出所以然的 ENOENT。

**为什么别的动作不能凑合**：`up` 要读 compose 文件，而 compose 里的相对路径
（`./state:/state`）是按执行目录解析后交给 dockerd 的 —— 在错误目录里跑，dockerd
会建一个空目录挂进去，应用看着像数据全丢了（compose.ts 顶部那段注释记的就是这个坑）。
不能为了「不报错」硬跑。

改动：`server/src/docker/compose.ts`（`reachable = existsSync(target.dir)`），
测试加在 `server/test/docker.test.ts`。

**验过它真的会红**：把 `cwd` 改回 `target.dir`、`-f` 改回无条件加，新用例立刻失败。
不是那种「怎么改都绿」的假测试。

## 二、提示位置：用户找不到，就是没有提示

用户的原话是「随便找个地方提示都找不到」。过了一遍全项目，问题分四类：

### 1. 长任务失败只写在页面顶部的输出面板里（这次的重点）

compose / 拉镜像 / 删项目 的输出流走 `OutputPanel`，那块在**页面顶部、自己能滚**。
跑个十几秒后开头那几屏就被顶出去了，失败原因（compose 的报错都在最后一行）得回去翻。

现在 `OutputPanel` 里挂了 `useStreamFailure(title, streamId)`：流以**非零退出码**结束时，
除了面板，再往右下角弹一条 toast，正文取输出的**最后一行**。
成功不弹 —— 面板上已经写着「完成」，再弹一次是刷屏。

提示的标题用动作名而不是面板标题：面板标题是「项目名 · 动作」拼的（`envtest2 · 停止并移除`），
接上「失败」读着别扭；单独传一个 `failTitle`（`停止并移除 envtest2`）。

### 2. 订阅竞态：后订阅的人收不到已经吐出来的输出

改完发现一个更隐蔽的 bug。原来的 `listenStream` 补发完缓存就 `delete`：

```js
for (const e of streamPending.get(id) ?? []) listener(e)
streamPending.delete(id)     // ← 谁先订阅谁把缓存吃掉了
```

`OutputPanel`（子组件的 effect）和新的失败提示**先后**订阅同一个流。
先订阅的（面板）把缓存吃掉，后订阅的（提示）拿到的是空的
—— `text` 是空串，提示里就没有报错内容，白弹一条。

改成**补发不消耗**缓存：谁都看得到已经吐出来的那几帧；只有**最后一个订阅者退订、
且缓存里已经有 exit 帧**（流已终结、不会再有新事件）时才清掉。

### 3. 一批操作原来默默失败

`.then()` 后面没接 `.catch()` 的，用户点了没反应、也没有任何提示：

| 位置 | 原来 |
|-|-|
| 改 MCP 设置 / 换接入令牌 | 只在字段下留一行小字，或什么都没有 |
| 复制地址、复制接入命令 | 失败就静默（`copyText` 会拒绝） |
| 打开 / 重连终端 | 未处理拒绝，按钮像是失灵 |
| 进容器 shell | 未处理拒绝 |
| 连容器日志 | 抽屉一直停在「正在连接日志…」 |
| 同步服务端清单（空白页那处按钮） | 未处理拒绝 |
| 清除连接与凭据 | 未处理拒绝，用户以为已经清了 |
| 「拉取并重建」的第二步 | 第一步成功后第二步没起来，界面只显示「完成」 |

都按「**用户主动触发的失败一律给 toast**」补齐。

### 4. 只在内联位置显示的

- **保存 compose 失败**：原注释写着「不塞进 toast」—— 理由是 compose 的报错是多行的。
  这个理由成立，保留编辑器下方的完整报错，但**补一条 toast** 报一声 + 第一行。
  两处都要：多行细节留在原处看得清，一眼知道「没保存上」不用去页面里找。
  新建项目同理。
- **挂载到本机失败**：挂载是异步的，失败发生在点下去几秒之后，原来只在卡片底部一行小字。
  改成状态落到 `error` 时弹一条（按错误内容去重，不重复弹）。
- **模块页首次加载失败**：`status` / `settings` 拿不到时整页 `return null` —— **一片空白**。
  现在给原因 + 「重试」。

### 有意留在原处的

轮询类状态（映射快照、容器概览、数据库列表、DAV 状态）继续用页面上的 `Banner`
——它们是「持续状态」，不是「你刚才做的那件事失败了」，
每 3 秒弹一次 toast 才是灾难。这条线划在这里：**用户主动触发的 → toast；后台轮询的 → 页面**。

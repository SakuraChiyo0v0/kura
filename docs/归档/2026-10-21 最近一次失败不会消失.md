# 2026-10-21 「最近一次失败」清不掉

**已变更**：服务映射卡片上那句「最近一次失败：…」现在会在**下一次请求成功后消失**。
5xx 仍照常记一次失败（不会把上游真坏着的情况说成正常）。

起因是用户看到一张卡片上挂着：

```
最近一次失败：getaddrinfo ENOTFOUND app-<端口>-<设备>.<节点>.ugdocker.link
```

---

## 一、这条错误本身是什么

那个域名是**绿联网关的外网中继域名**，形状 `app-<端口>-<设备>.cn<节点>.ugdocker.link`
（拼法见 `core/ugreen.ts` 的 `appBase`）。走网关的服务在 wan 模式下都得拨它。

`ENOTFOUND` 是**本机 DNS 解析失败**，不是域名不存在 —— 事后我 `nslookup` 同一个域名能正常解析到 IP。
典型触发是切换网络的瞬间：Wi-Fi 掉线重连、VPN 起来/断开、睡眠唤醒。

所以**那句话本身是真实的一次抖动**，不是 NAS 又坏了。真正的问题是它**不会消失**。

## 二、为什么不会消失

`core/stats.ts` 的 `ServiceStats.lastError` **只写不清**：

```ts
noteError(error) { this.errors += 1; this.lastError = ... }   // 只有写入
```

全仓只有 `listener.ts` / `tcp-listener.ts` 会在监听成功时清**各自**的 `lastError`
（那是端口监听失败，不是请求失败），`ServiceStats` 没有重置路径 ——
只有服务重新挂载、`new ServiceStats()` 换掉整个对象时才会一起没。

于是：**只要历史上失败过一次，那句红字就一直挂到 Kura 重启或服务重挂**，
哪怕之后几千个请求全都成功。用户看到红字会以为服务还坏着。

## 三、改成什么

`ServiceStats` 加 `noteSuccess()`，**只清 `lastError`，不动 `errors` 计数**：

```ts
noteSuccess() { if (this.lastError) this.lastError = '' }
```

`errors` 保留是刻意的 —— 它是「一共失败过多少次」，清掉等于篡改统计。
要清的是「**最近一次**失败」这句话，让它名副其实。

## 四、哪里算「成功」——这条比看上去难

三处调用点，语义必须一致：

| 位置 | 判据 |
|-|-|
| `proxy.ts` HTTP | 收到响应头，且 **`status < 500`** |
| `proxy.ts` WebSocket 升级 | 拿到 101；上游拒了升级但回了正常响应（非认证跳转）也算链路通 |
| `dav-server.ts` | 与 proxy 同一口径：`status >= 500` 记失败，其余清 |

**最容易做错的一点**：一开始我把「收到响应头」直接当成功，于是 5xx 也会清掉红字。
那比不清还糟 —— **上游真坏着的时候卡片反而一片正常**。
所以最终收敛成「5xx 记失败、其余清」，和 `dav-server` 原有的 5xx 判据对齐。

认证失败（302 → 登录页）走的是另一条分支，既不记也不清：那是会话问题，不是链路问题。

## 五、验证

单测（`stats.test.ts` / `proxy.test.ts`）：
- 清掉 lastError，但 `errors` 计数不动
- **失败后再成功一次，lastError 变空** —— 撤掉 `noteSuccess` 确认变红过
- **5xx 不算成功** —— 把 5xx 也当成功时确认变红过

冒烟（假 NAS 加了一个 `/__smoke/fail` 开关，能让所有应用请求回 500）：
- 上游出错 → 卡片出现「最近一次失败」 ✓
- 关掉故障、成功一次 → 那句话消失 ✓

两条是**成对**的，撤修复时验过两次：
- 完全撤掉（既不清也不记）→ **第一条**红（红字压根不出现）
- 只撤 `noteSuccess` 保留 `noteError` → **第二条**红，卡片卡在「最近一次失败：上游 HTTP 500」不动
  —— 这正是用户遇到的状况

冒烟 98/98。

## 六、顺手补的脱敏（2026-10-21 同日）

原本想把「`lastError` 直接拼 `error.message`」也脱敏，查着查着发现**更值得先处理的是别处**：
`SakuraChiyo0v0/kura` 是**公开仓库**，而文档里写进了真实的设备标识。

| 位置 | 原来 | 改成 |
|-|-|-|
| 本篇开头那条报错 | `app-8898-dxp4800gt-114a.cn30.ugdocker.link` | `app-<端口>-<设备>.<节点>.ugdocker.link` |
| `2026-10-14 kura-server S1–S6` 部署段 | `UGREEN DXP4800GT`、`DXP4800GT-114A` | `UGREEN <型号>`、`<机型>-<序列>` |
| 同篇外网终端那条 | `wss://app-8890-….ugdocker.link` | `wss://app-<端口>-<设备>.<节点>.ugdocker.link` |
| `modules.test.ts` 的卷标测试数据 | `DXP4800GT` | `NAS-SHARE` |

**教训**：脱敏这条规则一直在，但它管的是「写进文件的内容」；真正容易漏的是
**「这个仓库是公开的吗」这个前提**。写归档时我照常写实测现象，没意识到 kura 是 PUBLIC 而
`nas-mirror` / `sakura-ui` 都是 PRIVATE —— 同一套习惯搬到公开仓库就出事。

**历史没有改写**：这些内容已经推上去过（`e0c6846` 等），删 commit 追不回（GitHub 有缓存、
可能被 fork 或索引）。只改当前文件，让后来的人看不到。彻底清需要 rewrite history + force push，
代价大于收益。

## 七、没做的

- **`lastError` 里的域名脱敏**：它仍然直接拼 `error.message`，完整域名会显示在界面、也进日志。
  那是**本机运行时**的信息，不上传、不进仓库，暴露面比上面那种小得多 —— 所以这次先做文档侧。
  真要收敛，得在写 `lastError` 的地方做一层替换。
- 累计的 `errors` 计数与趋势柱状图仍然永久累计，没有「清零」入口。

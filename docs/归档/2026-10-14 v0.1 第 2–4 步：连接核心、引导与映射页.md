### 冒烟

`npm run smoke` 起一个本地假 NAS（绿联登录链 + Authelia + `/__services` + 一个应用），主进程经两个只在冒烟时生效的接缝（`smoke-seams.ts`）把绿联域请求改拨到它。
15 项全部对外部事实判定：本机端口的 HTTP 实际响应、`credentials.json` 磁盘内容里找不到明文、关服务后端口确实连不上、侧栏底 = 视口高度。

## 与 Go 版的有意差异

1. **路由按服务现算**：Go 版启动时按服务列表预算地址，运行期才发现的服务查不到、落进兜底分支。TS 版每次拼接，没有这个盲区。
2. **端口被外部程序占用不算「跳过」**：Go 版记进 skipped，页面上却又看得到它；TS 版只把「挂不上」（端口非法、与别的服务冲突）记为跳过，被占用的照常挂上、显示「开着但监听失败」，可以就地改端口。
3. **保存连接前必须测试通过**：Go 版是 `--check` 手动自检。

## 踩过的坑

### 1. `req.destroyed` 不代表调用方走了

反代测试里 5 条超时。我以为是测试的服务器没关干净；实测是**每个失败的请求都被当成「调用方已断开」，所以根本没写响应**。
原因：Node 的 IncomingMessage 开着 autoDestroy，**请求体一读完 `destroyed` 就是 true**（单独写脚本验证：`after end: req.destroyed= true socket.destroyed= false`）。
`callerGone` 改成只看 `req.socket.destroyed`。Go 版看的是 `context.Canceled`，概念上对应的是连接，不是请求流。

### 2. 「测试通过」的前提是假 NAS 像真 NAS

链路类退避测试失败：期望 credential=false，实际 true。不是代码错，是假服务器错——我让它在「链路故障」模式下返回 `500 {"status":"KO"}`，而按 Go 版口径带 `status=KO` 的响应一律算凭据类。
真实的链路故障长什么样？nginx 的 502 HTML 页面。假 NAS 改成那样之后通过。**测试替身要按真实故障的样子造，不然测的是自己的想象。**

### 3. 并行跑测试时超时，根因是每个用例都在生成 RSA 密钥

单跑全过，整套并行跑有 3 条超时（包括完全不碰网络的凭据测试）。每个假 NAS 都现生成一对 2048 位 RSA 密钥（几百毫秒、吃满一个核），并行时把别的用例也饿死。
改成同一进程共用一对密钥：整套从超时变成 4.65 秒。

### 4. 升级过的连接不归 `closeAllConnections` 管

WebSocket 用例之后的清理钩子卡 10 秒超时，连带下一个用例失败。被 upgrade 接管的 socket 不在 http.Server 的连接跟踪里，`close()` 永远等不到。测试工具里自己记 socket 并销毁；`ServiceListener` 里同样自己跟踪，关服务超时后强断。

### 5. Windows 上 `ui-monospace` 不生效

截图里本机地址是很宽的衬线等宽体。Chromium 在 Windows 上不认 `ui-monospace`，落到了默认等宽字体。字体栈改成 `'Cascadia Mono', Consolas, …`（Win10/11 自带，已确认 `C:\Windows\Fonts` 里有）。
Sakura UI 地基里没有等宽字体变量，先在应用层定义 `--kura-font-mono`——**这是库的缺口**，应该补进 tokens。

## 遗留

- **没在真实 NAS 上验收**。冒烟证明的是代码路径通，不是绿联中继今天的行为没变。下一步第一件事。
- 公司网络的出网代理没接（Go 版用 `ProxyFromEnvironment`；Node 的 Agent 不读 `HTTPS_PROXY`）。
- 中继是否支持 WebSocket 仍未证实（客户端这一侧已由测试证明能透传）。
- 开机自启、安装包、正式图标未做。
- Sakura UI 缺口：等宽字体 token；`StatCard` 的值区域对文字型值偏大（应用层收小了一档）。

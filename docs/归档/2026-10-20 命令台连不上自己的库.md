# 命令台连不上自己的库（role "root" does not exist）

2026-10-20。现象、根因、修法，以及为什么不是「补一个 -U」那么简单。

## 一、现象

「数据库 → 命令台」里选一个 PostgreSQL，默认参数 `-c "SELECT version()"`，点执行：

```
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed:
FATAL:  role "root" does not exist
```

命令本身没问题（它能在任何 psql 里跑）。是**以谁的身份**去连错了。

## 二、根因：镜像的 `POSTGRES_*` 和客户端的 `PG*` 是两套变量

我以为是 A：容器里有 `POSTGRES_USER=sakura`，`docker exec` 进去跑 psql 自然就认这个用户。

实测是 B：**`POSTGRES_USER` 只有镜像的 entrypoint 认**（它拿这个变量去 `initdb` / `CREATE ROLE`），
psql 客户端认的是另一套名字 `PGUSER` / `PGDATABASE` / `PGPASSWORD`。

因为 C：`docker exec` 不带用户时以镜像的默认 USER 运行。官方 postgres 镜像的 entrypoint 会用
`gosu postgres` 降权，但那**只影响它自己 fork 的主进程**，exec 出来的新进程不受影响 —— 于是 psql 看到
`geteuid() == 0`，按 OS 用户名 `root` 去登录，库里有 sakura、有 postgres，就是没有 root。

同一类错位另外两个引擎也有：

| 引擎 | 镜像里初始化用的变量 | 客户端认的 | 命令台实际表现 |
|-|-|-|-|
| PostgreSQL | `POSTGRES_USER` / `POSTGRES_DB` / `POSTGRES_PASSWORD` | `PGUSER` / `PGDATABASE` / `PGPASSWORD` | `role "root" does not exist` |
| MySQL / MariaDB | `MYSQL_USER` / `MYSQL_PASSWORD` | `-u` 参数 + `MYSQL_PWD` | `Access denied for user 'root'@'localhost'` |
| Redis | `REDIS_PASSWORD`（模板里传给 `--requirepass`） | `REDISCLI_AUTH` | `NOAUTH Authentication required` |

顺带发现一个一直没被用到的函数：`server/src/db/registry.ts:93` 的 `deriveConnection()`
写好了「从容器 `Config.Env` 推 user / database」，但**没有任何调用点** —— 于是接管来的容器
（NAS 上原有的 `sakura-pg` 之类）在登记表里 user / database 永远是空串。

## 三、修法：连接身份只在服务端补一处

`server/src/db/templates.ts` 新增两个纯函数，是「容器内的官方 CLI 该怎么连自己」的唯一来源：

- `clientEnv(engine, {user, database, password})` → `['PGUSER=..','PGDATABASE=..','PGPASSWORD=..']`
- `clientArgs(engine, {user, database})` → MySQL 的 `['-u', user, database]`，其余为空

`server/src/db/handler.ts` 的 `execLoop` 每次执行前把它拼进去，`docker/engine.ts` 的
`createExec` 新增 `env` 选项（走 Docker API 的 `Env` 字段，不经 shell、不改容器本身）。

三个决定值得记：

1. **口令走环境变量，不走命令行。** `psql --password` 之类会把口令放进 exec 的 `Cmd`，
   `docker inspect` 里看得见；`MYSQL_PWD` / `REDISCLI_AUTH` 是这几个客户端官方的做法。
2. **空值一个都不传。** 传 `PGUSER=` 会覆盖容器自己的默认值，比不传更糟。
3. **补的放前面，用户的参数放后面。** 命令行语义是后者覆盖前者，所以用户在参数里写
   `-U someoneelse` 时他的选择自然生效，不需要额外判断。

`fillConnection()` 把 `deriveConnection()` 接上：`list` / `detail` / `info` / `lookup` 都过一遍，
接管的容器终于能正确显示用户名与库名。`passwordOf()` 也补了第二个来源 —— 接管的容器没有 `.env`，
口令只存在于它自己的环境变量里。

## 四、客户端这边删掉了一份重复

`src/main/mcp-tools.ts` 原来有个 `connectArgs()`，给 postgres 补 `-U postgres`、给 mysql 补 `-u root`
—— 全是猜的，接管来的容器根本不一定是这两个。现在改成服务端补，客户端原样传用户的参数。

这一点很重要：**命令台和 MCP 走同一条路**，不会再出现「界面里能跑、AI 调用不行」。

## 五、验证

- `server/test/db.test.ts` 新增三引擎各一条端到端用例（真起 WS、真走 exec），断言的就是
  `exec.cmd` 与 `exec.env` 的实际形状。
- 按「修完要撤掉修复确认变红」的规矩做过一次：把 `clientEnv` / `clientArgs` 的调用改回空，
  三条用例全部转红（`expect(exec.env).toContain('REDISCLI_AUTH=...')` 直接报 undefined）。
- `npx tsc --noEmit` 通过；全量单测 432 passed / 6 skipped。

**没做的**：没在真机上验。这轮只跑了单测，没有 build / smoke（同期有另一个 session 在同一份仓库里
改 Redis 浏览面板，跑 build 会抢 dist）。真机上要确认的还是那两条：`sakura-pg` 在命令台里
`-c "SELECT version()"` 能出结果；以及 Kura 自己装的 MySQL 能出结果。

## 六、要注意的副作用

补上的 `-u` / `-U` 在**所有**经命令台跑的 CLI 上都生效，包括 `pg_dump`、`mysqldump` 这些。
这正好是想要的（备份也该用同一个身份），但意味着用户想用别的角色做特定操作时必须自己显式写参数。

需要新版 `kura-server` 镜像（`docker exec` 带 `Env` 是新行为）：watchtower 会自动拉，
没升级时命令台仍是老样子 —— 但也不会报新错。

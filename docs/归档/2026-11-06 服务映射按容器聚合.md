# 2026-11-06 服务映射按容器聚合

起因：服务清单把 `snowluma` 的 3000、3001、5099、6081 显示成四个服务。实测它们属于同一个容器，分别承担 API、实时通道、控制台和 noVNC 桌面，四个端口都在用。一个容器发布多个端口时，界面应按应用聚合，但底层仍要保留每个入口自己的监听与分流。

## 现在的口径

- **应用 / 容器是展示和统计的上级**。服务映射卡片、概览应用数、托盘应用数都按容器聚合。
- **入口是监听单位**。每个端口仍独立占用一个本机回环端口、独立探测、独立开关、独立改本机端口。不能把多个后端端口合并成一个 HTTP 监听。
- **统计仍按入口落盘**。容器卡片显示各入口求和后的累计数和近一天数据；入口行可以展开看自己的数字。历史统计键不变，因此升级不会丢历史。
- **清单向后兼容**。`/__services` 继续输出每个入口的顶层 `name/container_port/host_port/published`，并新增 `container/container_id/ports[]`。旧客户端仍按入口当服务；新客户端用容器 ID 聚合。
- **旧服务端照常可用**。没有容器字段时，每个入口仍显示成单独的“应用”。服务端更新后，即使启动时先按旧缓存挂载，下一次同步也会补上容器元数据。
- **默认入口不猜**。卡片可以展示多个入口，但不自动选“主入口”。容器页映射链接按全部启用入口列出，避免误把 3000 的 API 当成主界面。

## snowluma 实测

| 端口 | 结果 | 用途判断 |
|-|-|-|
| `3000` | `401`，`application/json` | JSON API |
| `3001` | 普通 HTTP 为 `426`；带 WebSocket 升级头为 `401` | 实时协议入口 |
| `5099` | `200`，页面标题 `SnowLuma 控制台` | 管理页面 |
| `6081` | `200`，页面标题 `noVNC` | 图形桌面 |

四个入口都由同一个 `Kura.exe` 映射到 `127.0.0.1`，不是四个进程；NAS 上对应的入口同属容器 `snowluma`。容器还声明了未发布的 `5900/tcp`，通常供 noVNC 连接 VNC 本体，Kura 不会为未发布端口创建映射。

## 踩过的坑

### 按“端口就是服务”建模，会把同一应用拆散

旧扫描逻辑在容器有多个可用端口时生成 `容器名-宿主端口`，避免网关路径前缀重名。这个入口名必须保留，因为反代的 `X-Nas-Service` 和路径前缀靠它分流；但界面不能把入口名直接当成应用名。两种粒度要分开。

### 监听与展示不能共用一份服务列表

如果只把快照里的列表合并成一条，内部 `byKey` 和 `byPort` 会失去独立入口的统计、探测、开关和改端口能力。因此保留入口级 `services`，新增容器级 `containers` 给界面使用。

### 用户主动关掉的入口不是故障

多端口应用可能只关掉一个入口。应用的总状态只聚合仍启用的入口：全部关闭才是“已关闭”，启用入口有失败才算异常。否则“关掉 API 入口”会被误报成整个应用有问题。

# 流量统计落盘与「近一天」

2026-10-22

> **已于 2026-10-22 变更（v0.10.8）**：落盘介质从 JSON 改成 SQLite（`stats.db`），
> 见本文末尾「改成 SQLite」。上面表格与「踩过的坑」写的是 v0.10.7 当时的做法，照原样保留。

## 起因

升级重启后，概览上那四张卡（请求 / 失败 / 上行 / 下行）全部归零。用户问「没有做持久化之类的么」——
确实没有：`ServiceStats` 是在 `Mirror.attach()` 里现 `new` 出来的，全在内存；
`dataDir` 下只落了 `services.json`（开关 / 端口）和 `discovered.json`（服务清单）。

## 定了什么

按用户的要求：**以小时为粒度先存起来，界面上显式给「近一天」**，后面可能要做数据统计，所以宁可存粗一点、
存得久一点（两天），也别为了好看只存「本次启动」。

| 项 | 决定 |
|-|-|
| 落盘 | `%APPDATA%/Kura/mirror/stats.json`，一个服务一条 |
| 粒度 | **小时格**（48 格 = 两天） |
| 界面 | 概览的两张卡读「近一天」（末尾 24 格）；服务卡片上排近一天、下排累计 |
| 键 | `Mirror.keyOf()`（服务名，取不到才 `port-<NAS端口>`）—— 改本机端口不清零 |
| 写盘 | 15 秒节流 + `stop()` 兜一次，原子写 |
| 趋势柱 | **不落盘**（见下） |

## 踩过的坑

**我以为是「把趋势柱也存下来就完整了」，实际是存了也白存。**
趋势柱是最近 30 根、每根 1 分钟、按时间对齐的窗口。写盘到读回之间只要隔了几分钟，那些格子在
`advance()` 里就已经过期，读回来会被整段补零冲掉 —— 存进去的是一份注定作废的数据。
所以分成两套：**累计数**（装机以来，不清零）+ **小时格**（近两天，可接续）。趋势柱仍然只在内存里，
它本来要回答的就是「现在忙不忙」。

**我以为是「写盘成功再记 written」，结果测试里那一条一直绿着，其实没真的验证到。**
第一版测试想构造「写盘失败」，做法是把父目录做成一个普通文件、指望 `mkdirSync` 抛。
但 `StatsStore` 存的路径是测试目录下的 `stats.json`，跟那个被占住的路径根本不是同一条 ——
失败压根没发生。改成**把目标文件本身先建成目录**（`mkdirSync(file)`，改名那一步必挂），
才真踩到那个分支。教训：构造失败现场要盯着**目标路径本身**，别绕道。

**`stop()` 在没 `start()` 过时会提前 return，把兜底写盘一起跳过了。**
`Mirror.stop()` 开头是 `if (!this.running) return`。可「只跑了一轮 `syncNow()` 就停」这种路径下
统计已经变了，兜底却没执行，重启后数字还是 0。现在这个提前返回里也调 `statsStore.stop()`。
是测试先红才发现的 —— 手写的时候完全没意识到。

**setter 要按增量记账。**
`stats.bytesDown = 900` 这种写法在反代里是**逐 chunk 累加**（`stats.bytesDown += chunk.length`），
所以 `ServiceStats` 把 `bytesUp/bytesDown` 改成了 getter/setter：setter 只把**差额**记进当前小时格。
不这么做的话，每来一个 chunk 就把**累计总数**再记一遍进小时格，「近一天」会比实际大出好几个数量级。

## 顺手做的

- 磁盘上的数读回来先洗：负数 / NaN / 非数字 → 0；同一小时格写了两遍只留一条。手改坏了文件不该让
  NaN 一路污染到界面。
- `StatsStore.flush()` 先写盘、写成了才更新 `written`。反过来的话，某次写失败（磁盘满、文件被占用）
  之后那一段变化就再也不会写了 —— 有个测试专门盯这个。
- 冒烟加了两条断言并**验证过它们真的会红**：把标签临时改回「请求」「流量」、把第二排的修饰类去掉，
  跑出 `98/100 => FAIL`，两条都报了；还原后回到 `100/100`。
  （只验「有 `<dl>`」看不出两排数字是不是被写成了同一个值，所以查的是结构与标签。）

## 没做

- **没有「重置统计」按钮**。数字从此是装机以来的累计，要归零得清文件。用户还没提这个需求，先不加。
- 本机 WebDAV 自己那份统计（`DavServer`）仍只在内存里，概览的流量卡也不含它 —— 这条路上不涉及重启丢失的问题（它随进程重建），暂不落盘。

## 改成 SQLite（v0.10.8）

用户一句话：「用 sqlite 呗」。理由站得住 —— 这一版本来就是奔着「以后可能做数据统计」去的，
按小时分格的数据迟早要按时间范围查、按服务聚合，JSON 得整个读进内存再自己算。

**用的是 Electron 自带的 `node:sqlite`，不是 better-sqlite3。** 实测过才定的：

- Electron 44 里 `process.versions.node` 是 24.21，`node:sqlite` 是内置模块，直接可用；
- 没有 `ExperimentalWarning`（Node 24 里它已经转正），不会在日志里刷屏；
- esbuild 打包时它被当成内置模块保留成 `require("node:sqlite")`，没有被 bundle 进去 —— 这一点专门查过构建产物；
- 反过来，better-sqlite3 是原生模块，得跟着 Electron 的 ABI 重编，`npm ci` / 打包 / 换 Electron 版本每一处都可能坏。为了一个统计功能引入这种依赖不值得。

**两张表，不合并成一张。** `service_total`（累计，只 upsert）与 `hourly`（按小时明细）。
我一开始想的就是「一张表存小时格，累计用 SUM 算出来」—— 那样最干净，但只要哪天按保留期清明细，
`SUM` 就会跟着变小，「一共走了多少」的数字自己往回缩。所以累计单独一张，清明细不影响它。
这个设计有一个测试专门盯着（`清理明细不动累计数`）。

**只写动过的小时格。** 小时格一共 48 个，可当前那一格每个请求都在变。整份重写等于每分钟
往库里灌 48 行不变的数据。现在 `ServiceStats` 记着「自上次落盘以来动过哪几格」（`touched`），
`toSaved()` 只返回这几个，写的是**绝对值**而不是增量 —— 所以同一格重复写是幂等的，写失败后重试安全。

**`markSaved()` 只在写成功之后调。** 这个顺序在 JSON 版就是对的，换库时保住了：
先清脏标记再写，某次失败（库被占、磁盘满）之后那一段就永远不会再写，而且看不出来。

### 又踩了三个坑

**1. 构造失败时数据库句柄没关，Windows 上连临时目录都删不掉。**
`new DatabaseSync(file)` 成功、但后面建表失败（文件不是 SQLite）时，我把异常抛出去了，
句柄却没关。测试里 `afterEach` 的 `rmSync` 直接 EPERM。真机上就是：库坏了一次之后，
用户想删掉那个文件重来都删不掉。现在整段初始化包在 try 里，失败先 `close()` 再抛。

**2. 库打不开不该让映射跟着起不来。**
JSON 版有个隐患我没意识到：`new StatsStore(...)` 在 `Mirror` 构造函数里，路径不可写就整个连接核心起不来 ——
**统计把服务拖垮了**。现在 `openStatsStore()` 兜住异常、记一条 WARN、退回 `NullStatsStore`（什么都不存），
服务照常跑。有测试（`统计库坏了也让映射照常起来`），并且撤掉兜底验证过会红。

**3. 「写全部」的旧测试换了语义，得跟着改。**
原来有一条断言 `toSaved().hours` 有 48 格。改成增量之后它必然红 —— 这不是 bug，
是契约变了。改掉之后补了一条正面盯新契约的（`toSaved 只给动过的格子`），
否则「只写动过的」这件事没有任何测试守着，退化成全量也没人知道。

### 冒烟加的那条

`流量统计落进 SQLite 文件`：等最多 25 秒，读 `%APPDATA%` 下那个 `stats.db` 的前 15 字节是不是
`SQLite format 3`。这一条盯的是「打包产物里真的用上了库」—— 路径写错、`node:sqlite` 在 CJS 产物里
require 不到，界面都完全正常，只有这个文件是没出现的。

### 不迁移

0.10.7 的 `stats.json` 没搬过来。那一版发出去几分钟、0 下载，里面最多十几分钟计数，
为它写迁移代码不划算。代价是累计数从 0.10.8 重新攒，CHANGELOG 里写明了。

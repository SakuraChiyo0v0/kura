# 网络位置残留与卸载竞态

## 现象

「网络位置」形态挂过 NAS 之后，资源管理器里会留一条 `\\server\<卷名>` 死图标，点不开。
0.8.4 已经加了「删不掉就重试」，但用户机器上仍然复现。

## 我以为是 A，实测是 B

**我以为是**：残留是「Explorer 还占着这条键不放手」，所以删一次失败、过一会儿再删就行了。

**实测是**：这条键**根本不是挂载时写的，是卸载时才由 Explorer 写下的**。
拿 `reg query` 定时探：
- 挂载期间、卸载前：键**不存在**
- 卸载后：键才出现

所以「卸载后立刻删一次」删的是个空。而当时的代码在删失败、且**此刻**键不存在时，
会直接 `return ''` 当成清干净了 —— 恰好**完整绕过**了这个窗口，比不重试还糟：
它让「重试」形同虚设，还对外报成功。

## 量出来的时间关系

| 挂载方式 | rclone 退出/unmount 返回那刻 | 残留 |
|-|-|-|
| 命令行（Kura 现在用的） | 键**还不存在**，+0.06~0.11s 才出现 | **有** |
| rc API（NetMount 用的） | 键**已经在了**（+0.02s） | **有** |

两边都留残留，只是时机不同。命令行这种方式正好卡在最坏的窗口上。

**触发条件是「Explorer 访问过这个盘」**（受控实验）：
- A 组：挂载后只用 Shell API 列一次「我的电脑」（模拟用户在看资源管理器）→ 卸载后**有**残留
- B 组：挂载后完全不碰 Explorer → 卸载后**无**残留

所以「用不用得到」这件事本身决定它会不会出现，跟是不是 network 模式无关 —— 但只有
network 模式会走到这段清理逻辑。

## 参考 NetMount 的结论

[VirtualHotBar/NetMount](https://github.com/VirtualHotBar/NetMount)（Tauri + Rust），
同样有「模拟本地硬盘」开关（`NetworkMode`，默认 `false`，语义与默认值都跟 Kura 一致）。

**它没有解决这个问题，是根本没管**：全仓 grep 不到 `MountPoints2` / `##server#` 的任何清理，
只有 autostart 用的 `HKCU\...\Run`。它在 SMB/NFS 场景下必然也留残留。

它用 rclone **rc API** 挂载（常驻 `rclone rcd`，调 `/mount/mount`、`/vfs/forget`、
`/mount/unmount`），不走命令行。我实测了 rc 方式的时机（见上表）—— **并不豁免**。

**结论：不值得为这个改挂载方式。** 换 rc 要多一个常驻进程、多一个端口、生命周期得跟 Kura 绑定，
启动/停止/日志/错误处理全得重写；换来的只是把清理窗口从 0.11s 变成 0，而重试本来就能覆盖。
收益与代价不成比例。

## 修法

不能以「此刻键在不在」判断有没有清干净，得守着整个窗口反复删，**最后一眼为准**：

```ts
const deadline = Date.now() + windowMs   // 默认 2s，实测窗口的约 18 倍余量
do {
  try { registry.delete(key); last = '' }
  catch (error) { last = registry.exists(key) ? errorMessage(error) : '' }
  await registry.sleep(250)
} while (Date.now() < deadline)
return registry.exists(key) ? last || '…残留删不掉' : ''
```

「固定磁盘」形态完全不受影响 —— 它压根不产生这条键。

为了能在单测里复刻这个窗口，把注册表三个动作（`delete` / `exists` / `sleep`）抽成
`RegistryAccess` 接口注入。

## 踩过的坑（写测试时）

1. **假绿一**：把「Explorer 稍后写键」挂在被测代码的 `sleep` 上。旧逻辑提前 `return`，
   那个 `sleep` 从没执行 → 残留根本没被制造 → 测试绿。**写键必须由独立计时器驱动。**
2. **假绿二**：断言在 `clearNetworkHistory` 返回后立刻做。旧逻辑几乎瞬间返回，此刻写键
   定时器还没触发，`present` 自然是 `false` → 又绿。**得等窗口过去再断言。**

修完按规矩撤掉修复确认变红：旧逻辑 `expected true to be false` ✓，恢复后 21/21 绿。

## 顺带

- 之前在用户机器上看到的 Z: / Y: 死图标，是切换挂载形态留下的历史遗留（explorer.exe
  从挂载形态切换前就一直开着，缓存没刷新）。`GetDriveType(Z:) = 3`、Shell API 的
  「此电脑」里也在，**Z: 本身是好的**；重启 explorer 后两个残留图标都消失了。
- 别用 `reg delete` 当只读探测 —— 它是真删（这次踩过）。

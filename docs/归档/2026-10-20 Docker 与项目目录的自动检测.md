# 2026-10-20 Docker 与项目目录的自动检测

起因：用户问「进 Kura 容器列表还是靠手动改服务端，能有什么自动检测的方式吗」。

答案分两件本来不相干的事，但它们都源于同一个毛病：**该看实际情况的地方，代码在看配置或字符串**。

---

## 一、Docker socket：功能一直在，只是没人告诉程序去那儿看看

### 改动前

`server/src/main.ts`：

```ts
const socket = process.env.KURA_DOCKER_SOCKET
const hasDocker = Boolean(socket && existsSync(socket))
```

`KURA_DOCKER_SOCKET` 没配 → 内置服务 `docker` 不注册 → 客户端 `Mirror.hasService('docker')` 为假 →
Docker 页显示「NAS 上还没有开容器管理」。用户只能去 NAS 上改 compose 加两行再 `up -d`。

### 实测（2026-10-20，真机，经 `~/.config/kura/exec.sh`）

```
docker exec kura-server stat -c '%d:%i %n' /var/run/docker.sock /host/run/docker.sock /host/var/run/docker.sock
→ 25:1633 /var/run/docker.sock
  25:1633 /host/run/docker.sock
  25:1633 /host/var/run/docker.sock
```

**同一个 inode。** 再用 node 经 `/host/run/docker.sock` 打 `/v1.43/info`：

```
OK 29.6.2 Debian GNU/Linux 12 (bookworm) 58
```

原因是 `/:/host` 这个挂载——WebDAV 的根就是它（`webdavDefaults.root = '/host'`），**必需项，拆不掉**——
宿主的 `/run/docker.sock` 自然就在 `/host/run/docker.sock`。

### 改动后

新增 `server/src/docker/socket.ts`，按优先级找：

```
KURA_DOCKER_SOCKET → /var/run/docker.sock → /run/docker.sock
                   → /host/run/docker.sock → /host/var/run/docker.sock
```

两条判定都要过：`statSync().isSocket()`（文件类型对）+ 真发一次 `GET /_ping`（daemon 活着）。
配了环境变量就**只认它**，不回退——显式配置优先，别让探测把用户的选择盖掉。

`DockerSocket` 带三个字段：`path`（容器内连它用）、`hostPath`（宿主上的路径）、
`source`（`env` / `mounted` / `host-root`，界面上如实说清怎么发现的）。

### 坑 1：`hostPath` 不是可有可无的

自更新要起一个短命兄弟容器跑 `docker compose`，那边按**宿主**路径挂 socket。
原来的写法是 `${target.socketPath}:${target.socketPath}` —— 同一个路径进、同一个路径出，
真机上宿主路径恰好等于容器内路径，所以**碰巧**是对的。

自动发现一旦给出 `/host/run/docker.sock`，这个路径在**宿主上不存在**，`-v` 会挂出一个空目录：
兄弟容器起得来、`docker compose` 却连不上 daemon —— **自更新静默失效**。
最讨厌的那一类：`docker run` 返回 0，看起来成功了。

改成左边宿主路径、右边固定 `/var/run/docker.sock`。

### 坑 2：只判文件类型会把「dockerd 正在重启」当成可用

文件在、daemon 没起来，这种情况在 docker 升级、宿主重启时很常见。
只看 `isSocket()` 会让 Docker 页显示成「已启用」，然后每个请求都报连不上。
所以加了 `/_ping` 活体检查，3 秒超时，探不到就跳过（并写日志）。

## 二、项目目录：从「比字符串」改成「比 inode」

### 改动前

`DockerService.kindOf()` 只做字符串比较：

```ts
if (within(dir, this.options.projectRoot)) return 'managed'
```

`within` 是纯路径段比较（这个函数本身是对的，注释里也写明了「按路径段判断，不按字符串前缀」）。
问题在于它回答的是「路径**长得**对不对」，而不是「这个目录**在不在**」。

于是 `/volume1/docker` 没按原路径挂进容器时：`kindOf` 照样返回 `managed`，界面给「部署」按钮，
点下去才在 `runCompose` 里撞上 `existsSync(target.dir) === false`，抛「项目目录没有挂进 kura-server」。

### 为什么这条必须修，不只是「难看」

compose 里的相对路径（`./state:/state`）是按**执行目录**解析成绝对路径再交给 dockerd 的。
在 `/host/volume1/docker/x` 下执行，dockerd 拿到 `/host/volume1/docker/x/state` ——
宿主上没有这个路径，dockerd 会**新建一个空目录挂进去**，应用看起来就像数据全丢了。
（`docs/容器管理 设计.md` §三、`compose.ts` 顶部都记着，真机验过。）

更糟的是数据库快捷安装：它直接往那个路径写 compose 与 `.env`。
没挂对时写进的是**容器自己的**文件系统，容器一重建就没了，NAS 上什么都没发生。

### 改动后

新增 `server/src/docker/mounts.ts`，判据是**是不是同一个目录**：

```ts
const here  = statKey('/volume1/docker')          // dev:ino
const there = statKey('/host/volume1/docker')
return there !== undefined && there === here
```

真机实测三种形状（`docker exec kura-server` 里跑）：

| 路径 | 容器内 inode | `/host` 下 inode | 判定 |
|-|-|-|-|
| `/volume1/docker` | `64768:137101313` | `64768:137101313` | 挂进来了 |
| `/volume1/@appstore` | 不存在 | `64768:209453057` | 没挂 |
| `/home` | `100:50748311` | `64768:17039361` | **没挂** |

第三行最值得记：容器里的 `/home` **本来就存在**（是镜像自己的），只看 `existsSync` 会误判成可用。
inode 不同立刻暴露。

`resolveProjectRoots()` 给出两套坐标：

- `projectRoot` —— 宿主原路径，**也是 compose 要用的执行目录**
- `scanRoot` —— 实际去 `readdir` 的地方；原路径不可达时退到 `/host` 下那份

扫出来的路径用 `toOriginalPath()` 换回宿主原路径再报给界面。**`scanRoot` 只代表「读得到」，
绝不代表「能部署」**——`scanRoot !== projectRoot` 时一律 `reachable: false`。

### 顺带修掉的两处

**绿联商店的 `appstoreMounted` 选项删了。** 它原本是 `existsSync(appstoreRoot)`，一个独立的开关。
现在统一走 `isMounted(appstoreRoot)`：真机上判成 false（原路径确实不存在），与今天的行为一致，
但依据从「手工传进来的布尔」变成了实测。

**`ProjectFileStore` 的开关从 `existsSync` 改成 `isMounted`。** 前者在 `/home` 那种情况下会误开，
而误开的后果是往容器自己的文件系统里写项目文件。

## 三、Kura 更新自己的目录

改动前：`process.env.KURA_SELF_DIR ?? '/volume1/docker/kura-server'`。

两个问题：① 换目录部署就得记着配环境变量，**真机上就漏过**（`docs/归档/2026-10-16 Kura 更新自己.md`
§「真机 compose 是旧的，缺 KURA_SELF_DIR」）；② 默认值恰好等于实际值，所以漏了也看不出来。

改成从 kura-server 自己容器的 `com.docker.compose.project.working_dir` / `config_files` 标签读。
`AutoUpdate.self` 选项缩成只留 `socketPath`。

读不到（`docker run` 起的老独立容器没有 compose 标签）就如实报
「kura-server 不是用 compose 起的，不知道在哪更新；请在 NAS 上手动更新」，不再拿猜出来的路径硬跑。

`server/deploy/docker-compose.yaml` 里的 `KURA_SELF_DIR` 与 `KURA_DOCKER_SOCKET` 两行一并删掉
（后者现在可选，留着也行但没用了）。

## 四、踩过的坑（这次新踩的）

### 坑：改一个「能不能部署」的开关，把一条不相干的测试搞红了

`docker-client.test.ts` 里那条「流的结束帧」测试给假 dockerd 报的项目目录是写死的 `/volume1/docker/app`。
我的判定改成看真实文件系统后，这个路径在 Windows 开发机上**不存在** → 判成 external →
compose 流被 403 拒 → 退出码 1 而不是 0。

一开始怀疑是协议改坏的。真正原因是**测试里的样本用了真机上才存在的路径**。
这条属于 memory 里记的「测试按真实形状写」的反面：形状是对的（真机上就这样），但**跑测试的机器不是真机**。

改法：测试里用 `mkdtempSync` 造一个临时项目目录，让假 dockerd 报它。

### 坑：`decodeURIComponent` 之外，`trimSlash` 也得有

`hostSide('/volume1/docker/')` 原来返回 `/host/volume1/docker/`（带尾斜杠）——
这个字符串会流进提示文案和路径比较里。单测抓到了（`expected '/host/volume1/docker/' to be '/host/volume1/docker'`）。
加了个 `trimSlash`，`isMounted` / `resolveProjectRoots` / `toOriginalPath` 全部先规范化。

### 坑：`kura-server` 不是 compose 起的时候，它就不算「自己」了

`DockerService.projectsFrom` 原来只从 `com.docker.compose.project` 标签造项目，
`selfProject` 那行只是给**有标签**的项目改 kind。所以 `docker run` 起的老独立容器
在 Kura 界面上**看不到**，自动更新里也走不到 `runSelf`。

改成先按**容器名**给 `kura-server` 占位（`kind: 'self'`），标签那份再填 dir / configFiles。
`projectImages` 同理。这样「自己不能从自己里面操作」这条在非 compose 部署下也成立。

## 五、验证

- 单测：`npx vitest run` → 48 个文件、587 条，**581 通过 / 6 跳过**（跳过的是需要打包产物的）
- 类型：`npx tsc --noEmit` 干净
- 新测试做过**破坏性验证**：
  - 去掉 `toOriginalPath` 的转换 → 「报出去的是宿主原路径」那条变红
  - 去掉 `/_ping` 判定 → 「文件在但 daemon 不答应」与「跳过要写日志」两条变红
  - 都恢复后全绿
- **真机**：上面表格里三行 inode 是 `docker exec kura-server` 真跑出来的，不是推演

## 六、没做的

- **没跑 `npm run check` / `smoke`**：同工作区有 6 个 peer session，`build.mjs` 会抢 `dist/`
  （memory 里记着踩过 `ENOTEMPTY`）。冒烟要等无人占用时单独跑。
- **没上真机验证 UI**：`/volume1/docker` 现在挂对了，所以「不可达」那条横幅在真机上**不会出现** ——
  要看它得临时把 compose 里那行挂载去掉。这个操作会动正在跑的服务，没在这里做。
- `KURA_SMOKE` 那条假服务端没造「目录不可达」的场景，冒烟只覆盖了可达的那条路。

# 2026-10-16 Kura 更新自己

紧接同一天那份「[按项目的自动更新](2026-10-16%20按项目的自动更新.md)」。那份的结论里有一条：

> **kura-server 自己硬排除**，仍归 watchtower

用户看完说：**「这个我不满足」**，随后选定「自动、不要回滚、默认开」。
也就是说：**连 watchtower 都不再需要**，Kura 自己更新自己。

同一份文档里那个「两条线划在 selfProject 上」的结论，从这天起作废。

## 真正的约束：一个容器没法重建它自己

不是「懒得做」，是一条硬约束：

`docker compose -p kura-server up -d` 会**先停 kura-server 再重建**。而执行这条命令的进程
就住在这个容器里 —— 容器一停，进程跟着没了，重建吊在半路。

**这不是推测，是踩过的。** 记忆里记着上一次：经 kura-shell 的 exec 试过重建 kura-server，
compose 先停掉 kura-shell、执行它的进程立刻死，**8898 整个挂掉**，
最后靠 NAS 上还留着的旧独立 nas-console 容器才救回来
（`docs/归档/2026-10-15 容器管理 D0–D3.md`，`project_kura.md` 里也记了一条）。

所以「Kura 更新自己」这件事，**唯一的问题就是让执行者活过 kura-server 被停的那一刻**。

## 办法：不属于这个 compose 项目的短命兄弟容器

`docker run --rm -d --name kura-self-update-xxx ... sh -c 'sleep 3; docker compose -p ... pull && ... up -d'`

关键在**它由 `docker run` 起、没有 compose 的项目标签** —— 所以
`compose -p kura-server up -d` 重建 kura-server / kura-shell 时，它不在被停之列。
它把这件事做完，然后 `--rm` 自己消失。

**不是一个常驻部署物**，因此没有违反用户那条「不希望零散依赖」：
- 不需要新镜像（用 kura-server 自己那个 —— Dockerfile 里本来就装了 docker-cli + compose）
- 不需要新目录、不需要新配置
- 只在真要更新自己的那几十秒里存在

### 几个必须做对的细节

**`-d` 不能省。** 它就是「活过发起方」的全部。少了它，兄弟容器是 Kura 的子进程，
kura-server 一停它跟着死 —— 又回到原来那个坑。

**脚本开头 `sleep 3`。** 等发起方那条 `docker run` 的 API 调用返回。
不然可能出现：`docker run` 还没返回，兄弟容器里的 compose 已经把发起它的容器停了。

**参数走位置变量，脚本正文不拼任何路径。**

```sh
sleep 3; n="$1"; shift; docker compose -p "$n" "$@" pull && docker compose -p "$n" "$@" up -d
```

项目名与 `-f` 文件都从参数进来。跟 `compose.ts` 那条「路径进不了 shell」是同一个规矩 ——
拼进去就是注入面。项目名还过一遍 `checkProjectName`。这条有单测钉住。

**镜像名不硬编码。** 从运行中容器的 image 标签动态拿。硬编码的话，哪天改了镜像仓库名，
自更新会静默地一直失败。

**`docker run -d` 的退出码只代表「兄弟容器起来了」。** 不是「更新成功了」。
真正的成败在几秒之后 —— 那时 kura-server 已经被重建，本进程早没了，看不到结果。
所以结果里只说「已交给更新容器」，不撒谎说成功。

### compose 要加一个环境变量

`KURA_SELF_DIR: /volume1/docker/kura-server` —— kura-server 自己那个 compose 项目的目录。
用它定位 compose 文件与 `.env`。那个目录本来就在 `/volume1/docker` 挂载范围内（按原路径挂的），
不用新增挂载。

挂进兄弟容器时是 **`:ro`**（只读）：它只需要读 compose 文件。compose 里的相对路径
（`./state:/state`）是由 compose 客户端解析成宿主绝对路径后交给 dockerd 的，
dockerd 在**宿主**上建目录 —— 不需要在这里写。

## 没有回滚（用户明确不要）

新镜像如果有问题，8898 直接不可达，得去 NAS 上救。
**这和之前 watchtower 更新 kura-server 时的风险完全一样** —— 区别只是现在自己在踩。

要加回滚是另一件事：记下旧镜像 digest，新容器健康检查不过就换回去。
用户选了不做。

## 界面上的一处区别

Kura 自己那一行原来是整行只读（`readOnly` 分支），只显示「由 watchtower 更新，Kura 里只读」。
现在给了**自动更新开关**，但仍然**不能启停 / 删除**（那会剪断自己连着的那根线）。

所以「能不能手动启停」（`canStart`）和「能不能开自动更新」在这里是两件事 ——
前者 Kura 自己永远是 false，后者现在是 true。界面上那句改成了
「自己更新自己 · 不能在这里启停」。

## 踩过的坑（这次不是技术问题）

### 差点被同仓的另一个 session 卷走

写完自更新、跑通测试，正要去写版本和归档时，注意到工作树 `git status` **变干净了** ——
我未提交的改动不见了。查下来：这台机器上同时开着的另一个 session 在同一个仓库里
跑了 `git stash`、又提交了它自己的东西（`1015894`）。

我的改动在 `stash@{0}` 里，没丢（后来它又 pop 回来了）。但**这个风险是真的**：
如果我正在它 stash 的那一刻写文件，或者它没 pop 回来，这轮工作就要重做。

**处置**：立刻把这批提交掉并推上去，先锁住成果，再慢慢写文档。
`project_kura.md` 里早就记着「用户常同时开多个 session 改同一份 Kura」，
这次是第一次真的擦到边。

（另外：界面那句「自己更新自己」是被那个 session 一并提交进 `1015894` 的 ——
它提交时工作树里有我的改动，就一起带进去了。核实过确实在，没漏。）

### 测试基线全塌了一次

默认项目列表从「空」改成「Kura 自己开着」之后，**整个测试文件 12 条全红**。
原因有两层：

1. `make()` 原来只是拼个路径、不写盘，所以构造时读不到状态文件 → 走默认 → 现在默认含
   `kura-server` → 每一条都被它带偏。改成 `make()` 显式写一个空列表，另加一个 `load()`
   读当前文件（给「落盘再读回来」那条用）。
2. 有几条测试自己 `new AutoUpdate(...)` 而不是用 `make()`，同样中招。

**教训**：改默认值 = 改所有测试的隐含前提。默认值这种「全局假设」一变，
要顺着每一条测试问一遍「它的起点还是我以为的那个吗」。

## 真机验证（2026-10-16，同一晚）

发完 v0.8.2 之后上真机跑了一遍。**这是唯一能验它的方式 —— 让它把自己真的重建一遍。**

### 先确认救援通道还在

这是动手前必须做的。我碰 NAS 走的是 `~/.config/kura/exec.sh` → 本机 8890 的 nas-console，
而自更新要重建的正是 kura-server。**如果通道被自己切了，就没法核实、也没法救。**

查下来：`nas-console` 是**独立的 compose 项目**（`com.docker.compose.project=nas-console`），
发布到宿主 8890。自更新重建的是 `kura-server` 那个项目，**碰不到它** —— 这正是当初留它当救援的原因。

### 触发与结果

先确认前置条件成立（`/docker/api/updates`，注意要带前缀路由）：

```
[{"image":"...kura-server:latest","status":"update",
  "local":"sha256:bc3e6f79...","remote":"sha256:63f89f8d..."}]
```

`status: "update"` —— 确实有新版。于是 `POST /docker/api/auto/run`，返回：

```
[{"project":"kura-server","images":["...kura-server:latest"],"ok":true,"reason":"","at":...}]
```

**这个 `ok: true` 只代表「兄弟容器起来了」**（`docker run -d` 一起手就返回）。
真正的结果要等几秒 —— 那时发起它的进程已经被重建、早没了。

等 25 秒后核实：

| 查什么 | 结果 |
|-|-|
| 容器名 | 变回干净的 `kura-server` / `kura-shell`（不再是 `a65f282eedfe_` 前缀） |
| 兄弟容器 | `docker ps -a` 里**查无此容器** —— `--rm` 生效，做完自己消失了 |
| 镜像 | image ID `760fbe98...` → `8b51f224...` |
| 健康 | 两个容器都 `Up (healthy)`，`/api/health` 正常 |
| 幂等 | 再查一次 `status: "current"` —— 下一轮不会重复更新 |

决定性的一步是**把 digest 和 image ID 对上**：

```
docker image inspect ...kura-server@sha256:63f89f8d... --format '{{.Id}}'
→ sha256:8b51f224...   ← 与容器实际在跑的 image ID 完全一致
```

（`63f89f8d` 是仓库要的 manifest digest，`8b51f224` 是本地 image ID —— **这两个本来就不是一回事**，
别拿它们直接比。要比的是「容器在跑的 image ID」与「目标 digest 对应的 image ID」。）

**结论：Kura 确实把自己换成了仓库上的最新镜像。** 用户要的「不再依赖 watchtower」在真机上成立了。

### 意外收获

这次重建把之前留下的 `a65f282eedfe_` / `f7ebcc657e23_` 那种临时容器名清掉了
（那是早先 compose 被打断留下的）。**现在 NAS 上的 Kura 是被 compose 正常管的。**

### 验完发现的、还没处理的两件事

**① 真机 compose 是旧的，缺 `KURA_SELF_DIR`。**

`docker inspect` 的环境变量里没有它。也就是说这次自更新能成功，
**靠的是代码里默认值恰好是 `/volume1/docker/kura-server`** —— 是运气，不是设计。

要同步这个改动**只能手动 `docker compose up -d`**：watchtower 永远传不过去 ——
它按 Docker API 重建容器（停 → 拉 → 用容器自己的旧配置重建），**不重读 compose 文件**。

**② watchtower 的标签还在，两边都在更新 Kura。**

真机上 kura-server / kura-shell 仍带 `com.centurylinklabs.watchtower.enable=true`，
watchtower 是 `LABEL_ENABLE=true` + `POLL_INTERVAL=300`。于是：
**Kura 自己每 6 小时一轮、watchtower 每 5 分钟一轮，目标相同，白干一份工。**

用户明确说：**「先不实现依赖，但不着急停」**。摘标签还是停 watchtower，
得先查清它是否还管着别的项目（bili23-web / account-panel 等）—— 那是另一件事。

### 没验的

- **失败路径**：兄弟容器起不来、新镜像坏掉。没法安全地真机构造（会真的搞坏 8898）。
  单测覆盖了「起不来时如实报错」的分支，但没在真机上走过。
- **界面**：容器页那个开关没在真机界面上点过（真机 API 与单测都过了）。

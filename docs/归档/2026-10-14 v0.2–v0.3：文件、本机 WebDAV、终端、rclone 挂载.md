# 2026-10-14 · v0.2–v0.3：文件、本机 WebDAV、终端、rclone 挂载

一夜做完，**都只对假 NAS 验证过**（单测 + Electron 冒烟 + 真 rclone/WinFsp 挂载）；真机验收待做。

## 做了什么

### 共同底座：映射层的「内部通道」

`Mirror.internalEndpoint(key)`：给某个服务另起一个只在回环、端口由系统分配的监听，**复用同一套反代**（会话、链路切换、Authelia、X-Nas-Service 全都一样），流量记在同一张卡片上。

为什么不直接用卡片上那个本机端口：那个是给外部程序的，用户可以关、可以改端口。Kura 自己的功能不该因为用户关了卡片就坏掉。

上层功能全部只认这个地址（AGENTS.md 架构原则 1），不认识绿联：

| 功能 | 连的服务 | 代码 |
|-|-|-|
| 文件管理器 | `webdav`（nas-webdav / rclone serve webdav） | `core/dav-client.ts`、`main/features.ts` FileService |
| 本机 WebDAV | 同上，前面加范围裁剪 | `core/dav-server.ts`、`core/dav-scope.ts` |
| 终端 | `nas-console` | `core/console.ts`、`main/features.ts` TerminalService |
| 磁盘挂载 | 本机 WebDAV（所以挂出来的盘天然遵守范围） | `main/modules.ts` |

### v0.2 文件管理器

浏览（面包屑、筛选、多选）、新建文件夹、改名、删除（确认框）、上传（系统选择框，流式）、下载（单文件另存为、多选/文件夹选目标目录递归下载）、双击打开（下到临时目录用默认程序开）。传输列表带进度与取消，下载先写 `.part`，完成才改名。

### v0.2 本机 WebDAV + 暴露范围

- 默认 `127.0.0.1:18006`、无认证（只能本机访问），可开关、只读、改端口。
- 范围：**放行目录**（白名单）+ **排除目录**（优先于放行）。放行目录的上级自动露出、只能「路过」（只能 PROPFIND，不能 GET、不能写）。范围外的 PROPFIND 条目整块剔除，直连 404。
- 放行目录**本身**不能被外部程序删除或移走；MOVE/COPY 的目标也要在可写范围内。
- 「可见性自检」：输一个路径，告诉你可见与否、能不能写、由哪条规则决定。
- 设置存在 `%APPDATA%\Kura\webdav.json`，改了对下一个请求立即生效。

与 files-admin（服务端那套）的关系：语义一致（排除优先、白名单兜底、父目录可路过），但这里**按路径前缀**判断，不是 rclone glob，所以没有「只写目录名不生效、必须写 /**」那个坑。两层是叠加的：服务端先裁一次，本机再裁一次。

### v0.2 终端

xterm.js 多标签，主进程持有 WebSocket 与 nas-console 的 session cookie，渲染层只收发字节。登录方式二选一：nas-console 账号密码 / API Token（`nsc_`），DPAPI 加密存 `console.json`。握手 401 自动重登一次；429（并发上限）、凭据错、shell 退出都给出可读原因，断开后可就地重连。

### v0.3 模块：rclone 挂载为磁盘

- rclone：Kura 下载**固定版本 v1.75.2**，**SHA256 写死在代码里**，对不上直接丢弃；装到 `%APPDATA%\Kura\modules\rclone\`。也认 PATH 里已有的 rclone（卸载时不碰它）。
- WinFsp：内核驱动、要管理员权限，**只检测不代装**，缺了给官网链接。
- 挂载：`rclone mount :webdav,url='<本机WebDAV>',vendor=other:/ X: --vfs-cache-mode writes --network-mode …`，连接串形态不写 rclone.conf。盘符、卷名、缓存模式、只读、开机自动挂载可设；退出 Kura 时先卸盘。

## 踩过的坑

### 1. `tar.exe` 不一定是 Windows 的那个

解压 rclone 报 `tar: Cannot execute remote shell`。我以为 Win10+ 的 `tar.exe` 一定是 bsdtar；实测 PATH 里 Git 的 GNU tar 排在前面，它把 `C:\...` 当成「主机:路径」去 rsh，而且 GNU tar 本来就解不了 zip。改成写死 `%SystemRoot%\System32\tar.exe`。

### 2. 刚解压的 exe 改名 EPERM

整目录 `rename` 到安装位置报 EPERM。不是权限问题，是杀毒软件正在扫刚落地的 exe（几秒后重试就好）。改成只复制 `rclone.exe` 一个文件并重试最多 10 次。

### 3. 同进程里 `existsSync(盘符)` 会死锁

真机挂载测试卡了 10 分钟后 `ECANCELED: scandir 'R:\'`。我以为是 rclone 挂载慢；实测是**自己把自己锁死**：探测 `R:\` 要经 WinFsp → rclone → 本机 WebDAV，而本机 WebDAV 就在同一个 Node 进程里，`existsSync`/`readdirSync` 卡住事件循环，WebDAV 永远答不了。主进程里同样的代码路径（等盘符出现）改成 `fs.promises.access`。**规则：凡是会走到本机 WebDAV 的文件系统调用，在主进程里一律异步。**

### 4. Destination 只能发路径

x/net/webdav 会拿 Destination 的 host 和自己收到的 Host 比，经过网关后 Host 已变 → 502。客户端与本机 WebDAV 转发时都只发路径；假 WebDAV 也按这个行为实现，测试里断言了上游收到的是路径。

### 5. nas-console 不支持 resize

读它的源码：PTY 是 `script` 包的，resize 那条 JSON 会被当成普通输入写进 shell（它自己的网页终端每次改窗口大小都会往 shell 里打一串 JSON）。Kura **不发 resize**，接口留着；代价是全屏程序（vim、top）按 80×24 排版。

### 6. 冒烟里「关服务后端口释放」偶发失败

不是端口没放，是卡片要等下一轮 3 秒轮询才显示「已关闭」，判据先超时。开关/改端口成功后立刻拉一次快照。

## 有意的取舍

- 本机 WebDAV **不设认证**，只靠回环 + Host 校验（防 DNS 重绑定）。同机其他用户 / 恶意本地程序能访问——与「映射层只监听回环」的安全模型一致。
- 文件页走 NAS 侧完整的 WebDAV（**不受本机范围限制**），范围只管外部程序。
- 终端拿到的是 NAS 宿主 root shell（nas-console 的设计），页面上写明了。

## 遗留 / 未证实

- **全部没在真 NAS 上跑过**。尤其：绿联中继对 WebSocket 的支持（外网下终端能不能用）仍未证实。
- nas-console 不处理 resize（服务端改动，不在 Kura 范围）。
- 大文件上传经中继的速度、超时没测。上传不设超时，靠取消。
- rclone 的 SIGINT 在 Windows 上不可靠，卸载超时 3 秒后强杀（WinFsp 会在进程退出时卸盘，缓存里未上传的写入可能丢——卸载前等传完）。
- 文件页的「打开」是一次性副本：在本机改了不会写回 NAS。要改着用就走挂载盘。

## 同日补充：启动与加载体验

用户反馈「几秒才从空白到显示」「每次都卡在引导页」。

先说清两件事：
- 冒烟里每次都进引导页是**冒烟自己造成的**（每轮全新数据目录 + 假 NAS 每步故意延迟 220ms）。
- 但真实使用里**确实**有「每次都进引导页」：另一个会话查到是 safeStorage 在 `app.ready` 之前不可用、凭据读不出来，已改成惰性读取（见 `connection.ts` loadConfig 注释）。

在这之上做了五处：

| | 改前 | 改后 |
|-|-|-|
| 1 首帧 | 渲染层先空白，等一次异步 IPC 才知道画引导还是主界面 | preload 用 `sendSync(kura:bootstrap)` 同步拿到配置摘要与快照，第一帧就画对；映射先于窗口启动（只挂缓存、不等网络） |
| 2 空白期 | 「映射正在启动」一句话 | 分步进度（启动映射核心 → 登录 NAS → 拉取服务清单），对着 `MirrorSnapshot.phase` 真实状态；有缓存时直接显示卡片 + 「正在同步」提示 |
| 3 刷新 | 3 秒轮询 | `Mirror.onChange` → 主进程合并 150ms 推送 `kura:mirror:changed`；轮询只为刷流量数字 |
| 4 保存 | 测试时查一次 ID，保存时又查一次 | 5 分钟内复用同一 ID 的解析结果 |
| 5 引导 | 「测试连接」「保存并连接」两个按钮 | 一个「测试并连接」：逐条测试，全过就自动保存并进主界面 |

冒烟加了第二轮「重启」（同一数据目录、清单接口故意拖慢 2.5 秒）：不进引导页、第一帧就是概览且已有 4 个服务卡片、清单到达 1 秒内界面更新（证明是推送不是轮询），进程启动到窗口可用约 1 秒。连跑 5 次全过。

### 坑：偶发「页面卡在还没有服务」

主进程第 1 秒就挂好 4 个服务，页面 15 秒后还是空的（约 1/10）。当时没定位到根因，推测是窗口被判为遮挡后轮询停了。改成推送后这条路径不再依赖轮询，此后连续 10+ 次未复现——**根因仍未证实**，记在这里。

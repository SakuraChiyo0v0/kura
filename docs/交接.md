## 部署链路（改完代码会发生什么）

```
push 到 main（命中 server/** 或 src/core/** 等路径，见 .github/workflows/kura-server-image.yml）
  → GitHub Actions 构建镜像（server/Dockerfile，上下文是仓库根）
  → 推 ghcr.io/sakurachiyo0v0/kura-server:{latest, <version>, <sha7>}
  → NAS 上 watchtower 轮询 digest 变化，自动 pull + 重建容器
```

两条**必须记住**的：

- **触发路径要跟着 Dockerfile 的依赖走。** 镜像里 `node server/build.mjs` 会把 `server/src`
  连同 `src/core/*` 打成一个文件。日后 server 若又从 `src` 别处 import，记得把那个目录也加进
  工作流的 `paths` —— 漏了就是「改了代码但镜像不重建」，最难发现。
- **watchtower 只换镜像，不重读 compose。** 改了 `server/deploy/docker-compose.yaml`（端口、
  挂载、环境变量）watchtower 不会管，得去 NAS 上手动 `docker compose up -d`。

NAS 上的位置：部署根 `/volume1/docker/kura-server/`（`state/` 是运行时状态，
范围配置落在 `state/webdav.json`）。**改 compose 或看容器状态要去 NAS 上操作。**

## 怎么碰 NAS

本机**不在** NAS 局域网，SSH 也不通（公网只开了 443/80）。走 nas-console 的
`POST /api/exec`（宿主 root shell，经绿联中继可达）：

- 辅助脚本 `~/.config/kura/exec.sh`，token 在 `~/.config/kura/nas-console.token`（600，仓库外）
- 这条路要经过**正在运行的那个客户端**的映射端口才能通 —— 客户端在退避重试时它也会失败
- **别经这条路重建 kura-server 自己**：8890 背后就是 kura-server → kura-shell，`compose up -d` 跑到一半会把自己的执行环境停掉。
  要重建 kura-server，走旧的独立 nas-console 容器（经中继直连它的 8890 app 域，不经 kura-server），或者在 UGOS 界面上操作

## kura-server 没有认证（这是有意的）

kura-server 自己**不做认证**：能到达它的路径要么经过绿联中继（中继认证绿联账号），要么局域网直连
（由更外层的手段保护）。这是一个**明确的取舍**，不是漏做 —— 别「顺手」加回认证层：

- 客户端连它也**不再有网关凭据**。加回鉴权会牵动客户端（`session.ts`）、compose、`.env`、
  管理页一整套。
- `/api/firstfactor` 有个**兼容壳**：给旧客户端种一个固定的占位 cookie（`authelia_session=kura-no-auth`）。
  原因写在 `server/src/server.ts` 里 —— 旧客户端启动会先登录一次，且拿不到 authelia cookie 会直接
  判定失败。**别把它改成随机值**（服务端重启后旧客户端手上的旧值会对不上）。
- API Token（`nsc_`）**不是门禁**，是给审计用的「归属标签」。
- `docker.sock` 挂进来是 `:ro`，但**这挡不住经 socket 发的写请求**。边界是代码里的白名单：
  `registry.ts` 只查端口，容器管理的接口全在 `server/src/docker/engine.ts`，每个一个具名方法。
  这是宿主 root 等价物，加用途前先看那张表；别加通用的「转发任意 Docker API」口子。

## 范围和只读只有一份 —— 在 NAS 上

暴露范围（include / exclude / readOnly）**只有一份**，存在 NAS 的 `state/webdav.json`，
客户端「文件」页和 NAS 管理页读写的是同一处（走网关 `/_kura/api/scope`）。
本机 WebDAV 那层不再有自己的范围，只做端口转发，范围由上游 kura-server 裁剪。

**契约是整体替换，不是增量合并**：客户端那页是全量列表编辑器，删一条得真的删掉。改成合并的话
「删除」会静默失效（这是设计时踩过的坑）。POST 时 include/exclude 都要发全，缺一个回 400。

`state/webdav.json` 是可以**手改**的（设计如此），所以读盘时当外部输入处理：空规则会被拒
（一条空白 include 等于放行整个文件系统），整份读不回来就退回代码里的默认范围。

## 几个容易踩的坑

- **别用 `sed`/通配符批量删 NAS 上的路径**：Windows 路径不区分大小写，出过事故。
  危险删除前先打印解析后的绝对路径并确认，按已知路径逐个删。
- **冒烟和单测用的是本地假 NAS**（`scripts/smoke.mjs`）。它现在也扮演范围层（按范围裁列表、
  按范围挡直接访问），所以「改范围 → 外部程序看到什么」是在测服务端契约，不是测客户端自己算的。
- **本机 WebDAV 默认端口 18006、网关默认 8898**：跟 Go 版 nas-mirror 抢同样的端口，
  用之前先停掉 Go 版。
- **Sakura 的 `PageTransition` 按 routeKey 卸载重建子树**：终端页因此**不能**放在它里面
  （标签与 xterm 回滚缓冲会一起没），现在常驻在 `.kura-term-host`（见 `App.tsx` 的注释）。
- **打包用的是 `node_modules/electron/dist`**（`electronDist`），不让 electron-builder 另下载解压：
  解压后立刻 rename 会被杀软稳定 EPERM。
- **给 NSIS 安装包传 `/D=` 路径别经过 Git Bash**：反斜杠会被吃掉，装到不知道哪去。
- **本机 Docker 没起**，镜像从没在本机跑过（都是 CI 构建）。rclone + WinFsp 挂载在本机真跑过
  （`KURA_REAL_RCLONE=1`）。

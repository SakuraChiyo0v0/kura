# 数据库管理 设计

> 状态（2026-10-15）：**M1 已实现**（单测 + 冒烟通过）。M2（交互式命令台、自研面板）、M3（备份、
> 可装面板容器）尚未开始 —— 见文末「分阶段」。上真机需要换 kura-server 镜像（`docker compose up -d`）。

2026-10-15。目标：在 NAS 上一键装好 PostgreSQL / MySQL / MariaDB / Redis，把端口**暴露到本机回环**
让本地程序直连，并在客户端里看状态、跑命令。

**主要使用方是 AI。** 用户原话："网络上有很多现成严谨的数据库管理器，完全可以参考借鉴。客户端功能可以
不用特别专业，但是能支持命令操作，后面大多是 AI 在使用" —— 所以 MCP 工具是主线，界面是给人做手边操作的。

## 一、两个硬约束决定了整个技术方案

1. **裸 TCP 过不了现有映射层，也过不了绿联中继。** `src/core/proxy.ts` 用 `http.createServer`，
   只跑 HTTP + WebSocket 升级；AGENTS.md §四.8 明记 SSH / SMB 这类裸 TCP 过不了中继。
   而 PG / MySQL / Redis 全是裸 TCP 协议。
2. **但 WebSocket 能过中继** —— 容器 shell 已真机验通（`docs/交接.md`）。

所以「外网也能连数据库」这条需求的唯一出路是 **TCP-over-WebSocket 隧道**：本机起 `net.createServer`
听 127.0.0.1，每条本地连接开一条 WS 走 `internalEndpoint('docker')`（复用会话 / 链路 / 认证 / 中继），
NAS 侧 `net.connect(容器名, 容器端口)`，双向泵字节。**不需要新传输层。**

第二个有利条件：`server/src/docker/engine.ts` 的 `createExec` / `startExec` 已经能拿到**原始双向 socket**，
且镜像里已有 docker-cli。于是"跑数据库命令"直接 `docker exec` 进官方镜像跑官方 CLI（`psql` / `mysql` /
`redis-cli`）：零客户端驱动依赖、版本与容器里的服务端天然对齐、支持元命令（`\d`、`COPY`）。

## 二、架构

```
渲染进程 DatabasesView（列表 / 连接信息 / 命令台 / 安装）
    │ IPC  kura:db:*
主进程 DatabaseService ── DbClient ──→ Mirror.internalEndpoint('docker')
    │                                        │ 每条本地连接 = 一条 WS（二进制帧）
    └─ DbTunnelService（127.0.0.1:<本机端口>）
           ▲
           │ 本地程序直连（psql / DBeaver / 应用）
kura-server：挂在【已有的 docker 内置服务】下的 /api/db/*（server/src/db/）
    ├─ 模板安装：compose 生成 + up（复用 docker/files.ts）
    ├─ 命令执行：docker exec 进官方镜像跑官方 CLI（复用 engine.createExec/startExec）
    ├─ TCP 隧道：WS ⇄ net.connect(容器名:容器端口)
    └─ 审计：docker-db-* 动作
           │ /var/run/docker.sock
           ▼
      NAS 上的 dockerd → pg / mysql / redis 容器
```

**不新增内置服务名 `db`（重要）**：`Mirror.attach()` 会对**每个**内置服务算 `localPort = spec.port`
并在本机回环建一个 `ServiceListener` —— 新增 `db` 就会在本机凭空多一个 `127.0.0.1:5432` 的 HTTP 反代
监听，还可能撞端口显示「开着但监听失败」。改为把 `/api/db/*` 挂在已有 `docker` 内置服务下：
`server.ts` 本来就按 path 分派，`internalEndpoint('docker')` 那条通道带 `x-nas-service: docker` 头，
路径原样到达 handler。**映射层、清单、本机端口全部零改动。**

## 三、安全红线：隧道绝不能变成「任意端口转发」

三层缺一不可，**都收在 `TunnelService.targetOf()` 这一个方法里**（隧道与命令执行都必须经过它）：

1. **协议层**：隧道接口签名里**根本没有 host/port 参数**。一个"能转发任意 host:port"的接口就是开放代理，
   从形状上就不给这个可能。
2. **数据层**：目标是查出来的（登记表 + 能认出引擎的容器），不猜；查不到就 404。
3. **校验层**：查出目标后仍用 Engine API 复核（容器存在、在运行）；**只接受容器名，不做 DNS 解析到任意主机**。

另有一道闸门放在「登记」这个动作上：**登记表为空时隧道一律 403**。要有一条登记项必须在 Kura 客户端里
操作过，未用此功能的人 NAS 上零暴露面。这比在协议里加 auth 有效 —— kura-server 无法可靠区分请求来自
中继还是局域网。

**闸门必须放在真实路径上，不能放在一个"查登记表"的辅助函数里。** 这里出过一次：`resolve()`
写好了三道防线，但生产代码从头到尾没调用过它 —— 单测全绿，实际一点没挡住。现在闸门在
`targetOf()` 里，谁要开隧道都得过它。

**「登记表非空」之后，谁可以开**：登记过的**与接管的已有容器都可以**。接管的（NAS 上不是 Kura 装的）
不写盘、不进登记表，不能要求它们"被登记"，否则「M1 就支持接管」那条落空。要挡的是**完全没用过这功能的人**，
由上面那道闸门覆盖。（这一段原先在文档里自相矛盾：§三 写"只接受登记名"，「坑 3」又写"接管的要能开隧道"。
**已于 2026-10-16 统一为后者**。）

**绑回环保护的是本机、不是 NAS**，别让它冒充安全措施：它的真实价值是防本机其他程序（含浏览器里的恶意页面）。
kura-server 没有认证是有意的取舍（`docs/交接.md`），**不新增认证层**。

风险如实说清：能连到 8898 的人本来就已经等于拿到宿主 root（`POST /api/tty` 直接给 root shell），
所以隧道**没有引入新的权限层级**。但它**降低了门槛**：原来要拿数据库得会开 shell、认得 pg 协议，
现在发一条 `GET /api/db/list` 就知道有哪些库。

## 四、隧道目标为什么是「容器名」而不是宿主端口

kura-server 走**共享 docker 网络按容器名**访问应用（Docker 内置 DNS 解析）。隧道用同一套：
`net.connect(containerPort, containerName)`。三个好处：

1. **数据库不发布任何宿主端口** —— 少一层暴露面（原方案"连已发布端口"会让数据库暴露在整个 NAS 局域网上，方向相反）；
2. **不占 NAS 宿主端口** —— `host_port` 撞车与 `mirror.ts` 的 `byPort` 撞车都踩过；
3. **用容器名而不是容器 IP** —— IP 在重启后会变，内存里缓存 IP 必然踩坑，容器名由 Docker DNS 稳定解析。

前提是数据库容器要接入 kura-server 所在的那个共享网络（`sso-net`）；Kura 装的会自动接，接管的已有容器
若不在网络上，界面上提示「需要一个网络连接」。

## 五、模板的几条定死的写法

| 写法 | 为什么 |
|-|-|
| 卷用**绑定挂载 `./data`**，不用具名卷 | compose 的相对路径按执行目录解析；kura-server 在宿主原路径下执行，所以落到 `/volume1/docker/<名字>/data`，用户能在文件页看见、能备份。具名卷在 NAS 上出过「声明与运行不一致 = 静默丢数据」的事故（`docs/参考/nas-mirror/设计方案.md`） |
| **不写 `ports:`** | 隧道连容器名，不需要宿主端口；发布了反而把数据库暴露在 NAS 局域网上 |
| **固定镜像 tag** | 不用 latest，否则同一次安装在不同时间装出不同版本，没法复现 |
| Redis 必须 `--requirepass` | 官方镜像默认 protected-mode，无密码会拒绝来自容器网络的连接 |
| 口令字符集排除 shell 特殊字符 | 用户会手抄口令粘到各种客户端与命令里，排掉能省一整类「抄错连不上」的支持问题 |

## 六、背压与超时的取舍（已定）

- **背压两侧都做**：`ws.send()` 没有背压信号（只有 `bufferedAmount`），`socket.write()` 有返回值。
  TCP→WS：`bufferedAmount > 1 MiB` 就 `socket.pause()`，降下来再 `resume()`；WS→TCP：`write()` 返回
  false 就暂停 WS 上行，等 `drain` 再恢复。客户端与服务端**共用同一份 `pumpSocket`** —— 两边各写一遍必然漂移。
- **不做应用层空闲超时（容易做错）**：数据库连接池的连接会正常闲置很久（HikariCP 默认 10 分钟、有的池 30 分钟），
  任何「N 分钟无字节就断」的规则都会**周期性杀掉健康的连接池连接**，表现为「应用时不时报连接已关闭」——
  最难查的一类问题。改为 `socket.setKeepAlive(true, 60_000)`。
- **不做多路复用**：一条本地 TCP 连接 = 一条 WS。多路复用要自制帧协议 + 每流流控 + 半关闭语义，出错面远大于收益。
- **不做端口复用/共享**：一个数据库一个本机端口，和映射页的心智一致（用户能自己看、自己改）。
- **WebSocket 没有半关闭（FIN）语义** → 定「任一方向关闭 = 整条隧道关」。实际影响小（PG 发 `Terminate` 再关、
  MySQL 发 `COM_QUIT`、Redis 直接关）。
- **不开 `permessage-deflate`**：数据库协议本身可选压缩，隧道再压一层纯浪费 CPU。
- **握手前把错误用 HTTP 状态码回**（403 登记表为空 / 404 无此库 / 409 容器没跑 / 429 超限），
  101 之后只能靠 close code。

### 必须用二进制帧，不能照抄容器 shell

`server/src/docker/handler.ts` 那条 shell 流是 `ws.send(chunk.toString('utf8'))` —— PTY 只有文本，没问题；
但 PG / MySQL 的握手包里含任意字节，走 utf8 会**破坏数据**。隧道两侧都直发 Buffer，
客户端侧 `ws.binaryType = 'nodebuffer'`。

### WS 要等握手完成再返回（踩过的坑）

`ws.send()` 在 CONNECTING 状态**不发送**，只调用回调报错；而泵按 `readyState === OPEN` 过滤 ——
`tunnel()` 早返回会让本地客户端先到的那几个字节**静默消失**（psql 头几条消息很短，正好落在这个窗口）。
冒烟里表现为「隧道连上了但一个字节都过不去」。`DbClient.exec()` 本来就是等的，`tunnel()` 也必须等。
回归测试：`src/core/db-client.test.ts`。

## 七、命令执行的取舍

- **走 argv，不做字符串拼接**：`docker exec` 的 `Cmd` 是数组，参数不经任何 shell 插值 —— 注入面为零。
  CLI 名从固定枚举里选（`psql` / `mysql` / `redis-cli`），照 `shellCandidates` 的做法。
- **非 TTY 执行**：要分离 stdout / stderr（SQL 错误必须在 stderr）、要结构化输出。`createExec` 加 `{ tty }`
  参数，默认 `true`（现有容器 shell 调用不受影响）。非 TTY 时 socket 上是 Docker 多路复用帧，
  新写 `createStreamDemuxer()` 保留流身份（**不改** `createLogDemuxer`，容器日志那条路别动）。
- **MySQL / Redis 的口令只能走命令行参数**（`-p<pw>` / `-a`）→ 口令会出现在容器内的进程参数里（`ps` 可见）。
  **这是接受的风险，不是漏做；审计日志里绝不记口令**。
- 超时与输出上限照 `mcp-tools.ts` 的 `streamTimeoutMs` / `maxStreamChars` 那套。

## 八、不做什么（明确排除）

- **不**做多主机、多用户、权限角色。
- **不**做 ER 图、数据同步、Schema 迁移工具。
- **不**给 kura-server 加认证层。
- **不**透传任意 Docker API；隧道不接受任意 host:port。
- **不**直接内嵌 CloudBeaver 之类现成 Web 面板（用户要的是"基于现成的自己重写一版适配我们页面"）。
- **不**在客户端存数据库口令：唯一真相在 NAS 上项目的 `.env` 里，存两份必然不同步。

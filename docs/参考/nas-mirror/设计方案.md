# nas-mirror 设计方案 —— 外网电脑无缝访问 NAS（HTTP 统一入口）

> 状态：**待评审**（尚未开始实现）
> 日期：2026-09-11
> 相关：`docs/ugos-nas-ops.md`、`skills/nas-ops/SKILL.md`、`feishu-harness/skill/nas-remote-access/`

---

## 一、目标

在外网（含公司内网）的电脑上，让**本机任意应用**访问 NAS 服务时的体验与在家中局域网内一致，
且本机应用无需了解任何绿联相关的认证机制。

已确认的约束（用户选定）：

| 项 | 选择 |
|-|-|
| 覆盖范围 | **先只做 HTTP**，裸 TCP（SSH / SMB / PostgreSQL）暂不覆盖 |
| 外网通道 | **只用绿联中继**，不引入任何组网（Tailscale / WireGuard / ZeroTier） |
| 目标机器 | **公司电脑**，只能跑用户态程序，装不了驱动与网络组件 |
| 连接方向 | **只允许客户端 → 服务端；服务端不得能访问客户端** |

---

## 二、安全模型（本方案的核心约束）

设计红线，实现时不得违反：

1. **单向发起**：只有客户端主动发起出站 HTTPS。服务端与绿联中继侧不存在任何能主动连到客户端的通道。
2. **仅监听回环**：客户端只绑定 `127.0.0.1`，**绝不绑定 `0.0.0.0` 或局域网地址**。
   这一条直接决定了"公司内网其他机器是否能发现并连上这个客户端"。
3. **零网络改动**：不安装驱动、不新增虚拟网卡、不修改路由表、不注册任何网络组件。
4. **凭据最小化**：客户端不保存绿联账号密码（见 §5.3），凭据落在操作系统的用户级凭据存储中。

### 为什么不使用组网（Tailscale / WireGuard / ZeroTier）

| 风险 | 说明 |
|-|-|
| 双向可达 | 加入网络后，NAS 及同网任意被授权节点可**主动连入公司电脑**（Tailscale 默认允许入站） |
| 子网路由 | 一旦任一侧宣告网段（如公司 `10.x/8`），另一侧即可进入对面整个内网——即典型的"内网穿透泄漏" |
| 企业合规 | 公司电脑上出现额外网卡与到外部协调服务的长连接，EDR／网络审计极易告警，多数公司明令禁止 |
| 配置漂移 | "能配置成安全" ≠ "不会泄漏"：ACL 写错一次、版本升级改默认值一次，即成隧道，且无法持续审计 |

结论：在公司电脑上**不引入组网**。用户已明确目标机器"装不了驱动/网络组件"，组网方案直接出局。

### 残余风险（无法消除，需用户自行判断）

- 客户端需持有绿联凭据，且其出站流量在公司网络审计中**可见**（可见目标域名，不可见内容）。
- 绿联账号本身是总钥匙：任何持有该账号的人都能构造带 SSO Cookie 的请求访问已发布的端口。
  因此**必须**由服务端的统一认证（Authelia）作为真正的门禁，而不是依赖绿联 SSO。

## 三、术语与总体架构

| 层 | 组件 | 位置 |
|-|-|-|
| 服务端 | 复用现有 **sso-gateway**（nginx + Authelia，`8897 → 80`），收敛为**单入口** | NAS `<部署根>/sso-gateway` |
| 客户端 | 新增 **nas-mirror**，本机端口镜像代理 | 外网电脑（用户态程序） |

```
┌─ 公司电脑 ────────────────────────────────┐
│  浏览器 / curl / WebDAV 客户端 / 任意应用 │
│      │ http://127.0.0.1:<与服务端同端口>   │
│      ▼                                    │
│  nas-mirror（用户态，仅监听 127.0.0.1）   │
│    · 绿联 SSO 会话管理器（自动登录/续期） │
│    · 注入 Cookie，按本地端口注入路由头    │
└──────┬────────────────────────────────────┘
       │ 出站 HTTPS（唯一方向）
       ▼
  绿联中继 cn30.ugdocker.link
       │
       ▼  仅 8897 一个公网入口
┌─ NAS ─────────────────────────────────────┐
│  nginx(8897)                              │
│    · 按 X-Nas-Service 头分流到各容器      │
│    · Authelia forward-auth 统一门禁       │
│      ▼                                    │
│  openlist / nas-console / webdav / ...    │
└───────────────────────────────────────────┘
```

**体验**：本机应用访问 `http://127.0.0.1:8890/`（nas-console）、`http://127.0.0.1:5244/`（openlist）
即等同于访问 NAS 上同名端口，配置一行不用改（端口号与服务端一致，即用户所说的"对称接口"）。

## 四、服务端设计

### 4.1 现状

- `sso-gateway`：nginx（`8897→80`）+ Authelia `4.39.20`，外部网络 `sso-net`，
  用户库落在 `sakura-pg` 的 `authelia` 库；compose 注释标注为 M1 阶段，watchtower 已禁用。
- 另有 10 个宿主端口直接发布在 `0.0.0.0` 上，**每一个都自动拥有一个绿联公网域名**
  （`app-<宿主端口>-<设备名>.cn30.ugdocker.link`），暴露面远大于实际需要。

### 4.2 目标形态：单入口

1. **只保留 8897 一个公网入口**。其余服务的端口发布从 `0.0.0.0:<port>` 改为
   `127.0.0.1:<port>`（仍可在 NAS 本机访问，但不再产生绿联外网域名），
   或直接取消发布、仅加入 `sso-net` 由 nginx 按容器名访问。
2. nginx 按请求头分流：

   ```nginx
   map $http_x_nas_service $svc_upstream {
       default      "";
       openlist     "http://openlist:5244";
       nas-console  "http://nas-console:8890";
       # ...
   }
   location / {
       if ($svc_upstream = "") { return 404; }
       proxy_pass $svc_upstream;          # 变量形式：保留原始 URI
       proxy_set_header Host $host;
       proxy_http_version 1.1;
       proxy_set_header Upgrade $http_upgrade;      # WebSocket 透传
       proxy_set_header Connection $connection_upgrade;
   }
   ```

   `X-Nas-Service` 只是**路由键，不承担鉴权**：外网任何人都能伪造该头，
   真正的门禁是 Authelia。路由与授权分离，这是本设计的关键约定。

3. Authelia 作为 forward-auth 挂在所有需要保护的路由前，实现一处登录、全局放行。

### 4.3 服务清单（实测端口）

| 服务 | 宿主端口 | 覆盖 |
|-|-|-|
| sso-gateway（统一入口） | 8897 | ✅ |
| openlist | 5244 | ✅ |
| nas-console（root shell / `/api/exec`） | 8890 | ✅ 高风险，必须过 Authelia |
| account-panel | 8787 | ✅ |
| bili23-web | 8788 | ✅ |
| jmcomic-web | 8080 | ✅ |
| music-tag-web | 8022 | ✅ |
| hermes | 9119 / 8642 | ✅ |
| nas-hello（测试用） | 8899 | ✅ |

| sakura-pg | 5444 | ❌ 非 HTTP，本期不覆盖 |

## 五、客户端设计（nas-mirror）

### 5.1 技术选型

**Go 单文件静态二进制**。理由：跨平台、无运行时依赖（公司电脑不便装 Python/Node）、
标准库 `net/http/httputil.ReverseProxy` 已支持 WebSocket 升级透传与流式转发，
避免自研通用功能。

### 5.2 组成

```
config.json          服务清单：本地端口 → 服务端宿主端口 / 显示名
session manager      绿联 SSO 会话：登录、换令牌、缓存、续期、失效重建
mirror listeners     每个服务一个 127.0.0.1:<port> 的反向代理
```

### 5.3 绿联 SSO 会话管理

完整链路（沿用已验证的流程，见 `feishu-harness/skill/nas-remote-access/`）：

```
① POST /ugreen/v1/verify/check  {username}        ← 响应头 X-Rsa-Token 取 PEM
② POST /ugreen/v1/verify/login  {password: RSA_PKCS1v15(明文)} → api_token
③ GET  /ugreen/v1/gateway/proxy/dockerToken?port=8897&token=<api_token>
                                                  → {redirect_url, token}
④ GET  <redirect_url>                             ← 一次性！只能访问一次
                                                  → 正则提取 document.cookie 中的
                                                    ugreen-proxy-token=<uuid>
⑤ 业务请求携带 Cookie: ugreen-proxy-token=<uuid>
```

实现要点（全部来自既有实测踩坑记录）：

- RSA 公钥的 PEM 标签写着 `RSA PUBLIC KEY`，但内容是 `SubjectPublicKeyInfo`
  → Go 中必须用 `x509.ParsePKIXPublicKey`，不能用 `ParsePKCS1PublicKey`。
- `token` 必须放**查询参数**，放请求头会得到 `{"code":1024,"msg":"Login has expired"}`。
- 域名后缀必须是 `ugdocker.link`，写成 `ug.link` 会永远返回 errorPage。
- **会话按端口严格隔离（M0 实测，2026-09-11）**：为 4 个端口各换一次 `dockerToken`
  得到 4 个**互不相同**的 cookie；拿 A 端口的 cookie 去访问 B 端口，一律 `302`
  跳回 UGOS 登录页（`/desktop/#/login/account`）。因此**每个目标端口都要独立维护一份会话**。
  → 这反而给 M2「单入口」增加了一条理由：只保留 8897 时，客户端只需维护 **1 份**会话。
- 会话缓存默认 20 分钟，带退避重试。
- **失效检测必须看内容而不是状态码**：失败时中继返回 `302 → UGOS 登录页`，
  或返回 `HTTP 200 + 一段跳转到 ug.link/errorPage 的 HTML`。客户端两种都要检测
  （未认证看 `Location`，被拒看正文），命中即重建会话并重试一次。
  注意 Go 的 `http.Client` **默认也会跟随重定向**，必须显式关掉，否则会被伪装成 200。

**凭据存储**：**没有长期令牌可用**（M0 实测：`static_token` 与 `third_token` 都换不出
`dockerToken`，登录响应里也不含任何有效期字段）。因此结论是确定的：

- **客户端必须持有账号密码**，并在 `api_token` 过期后自动重新登录（RSA 加密提交，密码不落明文）；
- 存 `api_token` 归档是**不可行**的——它的寿命只有十几分钟（见 §8.1）。

密码存进 Windows 凭据管理器（DPAPI），不写明文配置文件。当前实现读的是
Windows 用户级环境变量 `UGREEN_PASSWORD`，M2 阶段再补凭据管理器的读写。

### 5.4 本机暴露

- 每个服务监听 `127.0.0.1:<服务端宿主端口>`，端口号与服务端一致。
- 可选增强：给回环网卡添加 `<NAS局域网IP>/32` 别名，使本机应用即使写死
  `<NAS局域网IP>:8890` 也能命中客户端，实现**真正的零改造**。
  该操作需要管理员权限，公司电脑可能不允许 → 作为可选降级项。

## 七、已知待解决的坑

### 7.1 WebDAV 的认证叠加

WebDAV 需要 NAS 账号的 HTTP Basic，而 Authelia 的 forward-auth 依赖浏览器重定向，
**命令行 WebDAV 客户端无法完成重定向登录**。可选处理：

- 该路由单独策略：Authelia 支持 Basic 认证客户端的程度需先验证（4.x 版本对此有过变更）；
- 或该路由改用 nginx `auth_basic` + htpasswd；
- 或保留 WebDAV 自身的 NAS 账号认证（与统一门禁并存，两层）。

**结论待实测**，不预设。

> **2026-09-23 实测后的结论：以上三条都不是最终答案 —— 直接把后端那层认证去掉。**
> `nas-webdav`（rclone）改为**只挂 `sso-net`、不发布任何端口、不设 `--user/--pass`**：
> 宿主上没有任何监听 ⇒ 局域网与绿联中继都摸不到（实测宿主 `curl <NAS局域网IP>:18005` → `000`），
> 认证只剩边缘那两层；网关按**容器名** `http://nas-webdav:18005` 访问，不再写死局域网 IP。
> 于是"认证叠加"这个问题本身消失了：**外部（nas-mirror 客户端、浏览器）对 WebDAV 那层认证完全无感**，
> 客户端配置里连一条服务都不用留（`services: []`），也没有任何一份主密码抄在配置里。
> **暴露范围**：最终形态是**挂整个 `/`、由过滤器决定可见范围**（2026-09-24 用户明确要求"能勾任何目录，包括系统目录"）。`nas-webdav` 只读 files-admin 生成的 `/cfg/filters.txt`（三段：排除 → 放行 → 兜底 `- /**`），页面可勾任意路径、也能对已勾选的父目录做反向排除；`/proc /sys /dev` 用 tmpfs 掩成空目录（否则 `-L` 会沿 `/proc/self/root/…` 无限递归）。⇒ 边界从"挂载"变成"过滤器 + 网关认证 + audit.log"。
> **代价（明确接受）**：无认证 + 同网络 ⇒ `sso-net` 上其它容器也能无凭据读写这两个目录；
> 想收紧就给 `nas-webdav` 单独一条网络、只让网关加入。编排见 `nas-mirror/server/nas-webdav/docker-compose.yaml`。

### 7.2 Windows 原生 WebDAV 映射

Windows 映射网络驱动器对 `http` + Basic 有注册表限制（需 `BasicAuthLevel=2`），
且有大文件（约 50MB）限制。备选：`rclone mount`。

### 7.3 nas-console 的高风险

`nas-console` 是宿主机 root shell（`privileged` + `pid: host` + nsenter 进入 PID 1），
统一入口后它仍是最危险的资产。收敛后它至少不再拥有独立的公网域名，
但仍必须由 Authelia 强制门禁，且建议评估"外网是否真的需要它"。

## 八、M0 实测结果（2026-09-11 20:00–20:03）

工具：`nas-mirror/tools/probe_external.py`，原始报告 `nas-mirror/tools/m0-report.json`。

### 8.1 已确认的事实

| # | 问题 | 结论 |
|-|-|-|
| 1 | `static_token` / `third_token` 能否当长期令牌 | **不能**。`static_token` → `code=1114 Illegal operation, unauthorized user`；`third_token` → `code=1024 Login has expired`。客户端拿不到任何长期令牌。 |
| 2 | 登录响应里有没有有效期字段 | **没有**。43 个字段中唯一带 `expire` 的是 `password_expire=False`（密码过期标志），与 token 寿命无关。寿命只能实测。 |
| 3 | 应用会话是否按端口隔离 | **严格隔离**。4 个端口 → 4 个不同 cookie；用 8899 的 cookie 访问 5244/28006/8890 全部 `302` 到 `/desktop/#/login/account`。 |
| 4 | 中继延迟 | 单次请求 **约 230–300 ms**。登录链路 270–820 ms，`dockerToken` 210–470 ms，once-token 换 cookie 280–320 ms。 |
| 5 | WebDAV 吞吐 | **上传 53 Mbps / 下载 55 Mbps**（3 MiB 往返，字节级一致，`DELETE 204`）。约 6.6 MB/s，1 GB 文件约 2.5 分钟——**可用**。 |
| 6 | 各服务可达性（用各自端口的会话） | 8899 / 5244 / 8787 / 8788 / 8022 / 8890 均 `200`；`hermes` `302` 到自身 `/login`（应用自身行为）；WebDAV 28006 `401`（需 Basic，补上后 `207`）。 |
| 7 | 会话建立成本 | 每端口约 0.5 s，8 个端口约 4.4 s。20 分钟续期一次的开销可忽略。 |
| 8 | `api_token` 有效期 | **约十几分钟**。实测 `keepalive=false` 时：600 s 仍有效、1200 s 已返回 `code=1024`，且新登录的 token 立即可用（确认为过期，不是被限流）。 |
| 9 | `keepalive` 参数的作用 | **显著延长 token 寿命**。同一时刻 `keepalive=false` 的令牌已过期，`keepalive=true` 的仍然有效。且**不改变响应里任何其他字段的语义**——用"两次 false 作对照组"测得噪声底为 4 个令牌字段 + `public_key`（每次会话临时生成的 RSA 公钥），超出噪声的差异为 **0**。客户端已改用 `true`，并有单元测试锁住这个决定。 |

### 8.2 仍未证实的

| # | 问题 | 现状 | 计划 |
|-|-|-|-|
| 1 | `keepalive=true` 的 token 到底能活多久 | **观测中**。60 秒粒度的观测器在跑，日志 `nas-mirror/tools/token-watch-keepalive-tight.jsonl`。已知它比 `false` 活得久（>1200 s），但上限未定。 | 若长达数十小时，可考虑改存令牌而非密码 |
| 2 | 中继是否支持 WebSocket 长连接 | **仍未能证实（注意：是"未证实"，不是"证伪"）**。客户端自己的 WS 透传已由集成测试证明（101 升级 + 双向字节回显 + 会话 cookie 注入）。中继那一段缺一个真实 WS 端点。已用 `probe_external.py ws` 扫过 6 个服务的 socket.io polling 握手与 4 个常见 WS 路径（`/socket.io/`、`/ws`、`/websocket`、`/api/ws`）——**没有任何服务真的提供 WS 端点**（返回的 `200` 都是 SPA 的 index.html 兜底，`404` 才是真实结果）。这条路已排除，不必重扫。 | 在 `nas-hello`（用户自己的测试应用）上加一个 WS 回显端点做可控实验——**动 NAS 前先征求同意** |
| 3 | 单入口 8897 承载全部流量的稳定性 | 未测 | M2 阶段 |

> ⚠️ **测量方法上的一个坑（已修正，务必记住）**：`urllib`（以及 Go 的 `http.Client`）
> **默认自动跟随 302**。M0 第一轮报告因此把「被踢回 UGOS 登录页」误报成「HTTP 200 成功」，
> 一度让我以为"一个 cookie 能访问所有端口"。
> 所有诊断与后续客户端实现都必须**显式关闭重定向跟随**，否则中继的任何拒绝都会被伪装成成功。

## 十、M2 实施记录

### M2.0 收敛机制的关键实验（2026-09-11，已完成）

**问题**：把服务的端口发布从 `0.0.0.0:<port>` 改成 `127.0.0.1:<port>`，
能不能撤掉它的绿联公网入口？

**做法**：拿 `nas-hello`（测试应用，影响最小）做实验，改 `ports: "8899:3000"` →
`"127.0.0.1:8899:3000"`，`docker compose up -d` 重建后做外网体检。
（注意：`sso-net` 的成员身份是手工 `network connect` 上去的，不在 compose 里，
重建容器会丢，实验后已手动补回。）

**结果**：❌ **不能**。

| 时刻 | 宿主监听 | `app-8899-*.ugdocker.link` |
|-|-|-|
| 改之前 | `0.0.0.0:8899` | HTTP 200，nas-hello JSON |
| 改之后 | 仅 `127.0.0.1:8899` | **HTTP 200**，且返回的 host id 变为新容器 → 确实走的是重建后的实例 |

**原因**：绿联的 `gateway_serv` 是**跑在 NAS 宿主机上**的进程，它连 `127.0.0.1:<port>`
一样连得上。公网入口的有无只取决于「端口有没有发布到宿主」，与绑哪个地址无关。

**结论（决定 M2 的所有做法）**：
> 想真正撤掉一个服务的公网入口，**唯一可靠的办法是删掉整个 `ports:` 映射**，
> 把容器接入共享网络（`sso-net`），由网关 nginx 按容器名反代。

副作用说明：仅回环绑定虽然撤不掉公网入口，但能**关掉局域网直连这条路**
（局域网访问绕过绿联 SSO）。`nas-hello` 目前就停在这个状态——比原来严格更少暴露，
等 M2.1 接入网关时再一并把 `ports:` 删掉。

### M2.1 网关部署（已完成，2026-09-11）

**部署动作**（`sso-gateway` 此前从未启动过）：

1. 备份 `nginx/conf.d/default.conf` 与 `authelia/configuration.yml`（`.m2bak`）
2. 把 nginx 配置从**路径前缀分流**改写为**请求头分流**（用户选定）：
   - `map $http_x_nas_service $svc_backend`；带该头 → 过 `auth_request` 后转发到对应容器；
     不带 → 用 `error_page 418 = @portal` 内部跳到 Authelia 门户（`if` 里只用 `return`，避开 "if is evil"）
   - 补了 WebSocket 透传与长超时（日志流/终端不能用默认 60s 掐断）
3. Authelia `access_control.default_policy` 由 `deny` 改为 `one_factor`，并**删掉了按路径的旧规则**：
   按头分流后应用请求的原始路径是它自己的根路径（如 `/`），匹配不到 `^/nas-hello`，
   会返回 **403 而不是跳登录**，用户根本登不进来。
   **刻意不写任何按路径 bypass 的规则**——应用自己也有 `/api/`（如 nas-console），
   一旦 bypass 就等于给鉴权开天窗。
4. `docker compose up -d` 起 Authelia + nginx

**验证**（`tools/check_gateway.py`，走真实绿联链路）：

| 步骤 | 结果 |
|-|-|
| 门户 `/` | 200，1155 字节，Authelia 门户 ✓ |
| 未登录访问应用 | 302 跳 Authelia 登录 ✓ |
| 未知服务名 | 404 拒绝 ✓ |
| Authelia 登录 | 200 `status=OK` ✓ |
| 会话 cookie | `authelia_session` ✓ |
| 带会话访问受保护应用 | 200 + nas-hello JSON ✓ |

Authelia 日志也确认了策略生效：
`no rules have been specified so the 'default_policy' of 'one_factor' is going to be applied to all requests`

### M2.2 逐个收敛（已完成）

**做法**：每个服务三件事 —— compose 去掉 `ports:`、接入 `sso-net`（**写成声明式**，
不再用手工 `docker network connect`）、在网关 nginx 的 map 里加一行；然后重建并验证。

**已收敛**：nas-console、nas-hello、openlist、account-panel、bili23-web、jmcomic-web、
music-tag-web、hermes、hermes-api、WebDAV。

**收敛后的实测结果**：

| 项 | 结果 |
|-|-|
| 宿主上还在发布的容器端口 | **只剩 8897（网关）与 5444（PG）** |
| 原有 12 个独立公网入口 | **10 个已死**（`app-*` 返回 `500 failed to forward request`） |
| 客户端 `127.0.0.1` 上的服务 | 10 个全部可用，含 WebDAV 1 MiB 字节一致往返 |
| 客户端维护的会话数 | **1 份**（全走网关；M0 的"会话按端口隔离"在单入口下不再有代价） |

**收敛过程中踩到的三个坑**（都是真缺陷，改这套配置前必读）：

1. **nginx 的 `resolver` 不读 `/etc/hosts`。**
   `proxy_pass` 用变量时（本配置为了按请求头分流必须用变量），nginx 用 `resolver`
   解析主机名，而 Docker 内置 DNS **不认识** `host.docker.internal` ——
   那只是 `extra_hosts` 写进容器 `/etc/hosts` 的东西。
   写域名会得到 `host.docker.internal could not be resolved` 并返回 502。
   **必须写 IP 字面量**：用 `172.17.0.1`（Docker 默认网桥网关 = 宿主机），
   它不随 NAS 的局域网 IP 变化。

2. **`auth_request` 会把客户端的 `Authorization` 头带进鉴权子请求。**
   WebDAV 客户端会带 `Authorization: Basic <NAS账号>`，而 nginx 默认把客户端头都转给子请求，
   于是 Authelia 拿它当**自己的** Basic 凭据去查用户库 → 库里只有 `<网关用户>`、没有 `<用户A>`
   → 整个鉴权失败，哪怕会话 cookie 完全有效。Authelia 原话：
   `failed to validate Authorization header with basic scheme: failed to retrieve user details for user <用户A>: user not found`。
   修法：在 `/internal/authelia/authz` 里加 `proxy_set_header Authorization "";`。
   这个 Basic 凭据属于后端 WebDAV，与 SSO 层无关。
   （这正是 §7.1 预判的"Authelia + Basic 叠加"问题，现在有确切答案了。）

3. **项目名与文件名不能想当然。**
   `bili23-web` 的 compose 叫 `docker-compose.nas.yml` —— compose **不会**自动发现这个名字，要 `-f`；
   `music-tag-web` 原本是 `-p music-tag-web` 起的，直接 `up` 会新建一个
   `comugreendockermusictagweb-app-1`，把旧容器晾在一边。
   重建前先看容器标签：
   `docker inspect <容器> --format '{{index .Config.Labels "com.docker.compose.project"}} ...'`

### M2.6 收敛回滚（2026-09-11，重要）

**最终形态：独立入口与网关两条路并存。** 各应用的宿主端口已全部发回，同时保留 `sso-net` 成员，
所以下面三条通路同时可用：

| 通路 | 谁在用 |
|-|-|
| `app-<宿主端口>-<设备>.cn30.ugdocker.link`（绿联 SSO 门禁） | **手机绿联 App 的"外部链接"**、局域网直连、任意浏览器 |
| `X-Nas-Service: <服务名>` → Authelia | 本客户端 |
| `https://<入口>/<服务名>/` 路径前缀 | 浏览器，且**只有部分应用可用** |

**为什么必须回滚**：

> 手机绿联 App 里的"外部链接"，指向的是 `app-<宿主端口>-<设备>.cn30.ugdocker.link` ——
> 它是**按"端口有没有发布到宿主"自动生成**的。
> 把 `ports:` 删掉，就等于把那些链接全删了；而绿联 App 不可能发 `X-Nas-Service` 头，
> 所以它永远走不通网关那条路。

这是收敛的**硬性代价**，不是可以绕过的实现细节。

**我的评估漏项**（要记住的教训）：

提 M2 方案时，我只考虑了"浏览器直连"这一条通路会受影响，并且把它写成了一个可以靠路径前缀
补回来的小代价。**我漏掉了手机上每天都在用的那个入口** —— 它不是浏览器，是绿联 App 自己
生成的链接。所以"收敛的必要性"从一开始就被我高估了：代价比我说的更大，收益（在用户信任局域网
的前提下）比我说的更小。

**顺带一个验证方法上的教训**：

> 写"前缀方案能不能用"的检查脚本时，我第一版只看状态码，得到"7/9 可用"的结论 —— **是假阳性**。
> 因为 SPA 对任何未知路径都会兜底返回 index.html（看着像 200 成功），
> 而我把门户页返回的 200 也算成了"资源可访问"。
> 改成"取回来的是不是门户页"之后，真实结果是 **3/9**。
>
> **判据必须能区分"真成功"和"看起来像成功"。**

**路径前缀的实测结果**：

| 可用 | 白屏 |
|-|-|
| nas-hello、music-tag-web、webdav | nas-console、openlist、account-panel、bili23-web、jmcomic-web、hermes |

白屏根因是结构性的：SPA 的 HTML 里写死 `/assets/...`，在子路径下浏览器会去入口根取，
而那条路被"门户请求"接走、返回登录页。`sub_filter` 改写 HTML 也救不了 ——
JS 包里的 `fetch('/api/...')` 改不到，会变成"页面能开、功能全坏"，比白屏更难排查。

**网关本身保留**：它仍然是一个可用的"单点登录入口"，`sso-gateway` 容器继续运行，
配置就在 NAS 的 `<部署根>/sso-gateway/`。要彻底拆掉的话，停掉那两个容器即可。

**遗留**：`hermes` 的 8642 端口显示 `500 failed to forward request`，因为容器内部根本没在
8642 上监听（宿主 `curl 127.0.0.1:8642` 返回 `000`）。端口发布正常，是应用自身的问题，
**与本次改动无关**（重建前后 command 与环境变量完全一致）。

| | 实际在用 | compose 声称要用 |
|-|-|-|

**顺带又踩了同一个坑，值得单独记下来**：

> 重建 PG 之后，Authelia 立刻报
> `lookup sakura-pg on 127.0.0.11:53: no such host`。

> 不在 compose 里 —— 容器一重建，成员身份就没了。

### M2.3 客户端适配（已完成）

网关引入了**第二层认证**（Authelia），所以客户端必须把这一层也代持了，
否则本机应用会被拦在 Authelia 登录页外。

> 曾经想走"让用户在本机浏览器里经客户端登录"这条路，推演后否定：
> Authelia 门户的 HTML/JS 里写死了公网域名（`authelia_url`），表单会直接提交到公网域名，
> 会话 cookie 落在公网域上，`127.0.0.1` 这一侧的请求永远带不上它。
> **所以"把认证提前做好"只能由客户端完成**——这恰好就是需求原文的语义。

客户端改动：

- 新增 `gateway_port` / `gateway_user` 配置；密码取 `NAS_SSO_PASSWORD`（绝不写进配置文件）
- 走网关的服务：上游统一是 `app-<网关端口>`，每个请求注入 `X-Nas-Service: <service>`
- **会话端口也要跟着改**：走网关的多个服务共用**网关端口那一份**会话。
  这点如果搞错就会拿到被中继踢回登录页的假会话（M0 的会话按端口隔离结论的直接后果）
- 建会话时在网关端口上追加一次 Authelia 登录，把两层 cookie 一起注入本机请求
- `mergeCookie` 改为**按 cookie 名**剔除客户端自己管理的那几个（值会随续期变化，按值匹配会漏）

### M2.4 链路模式（局域网 / 外网 / 自动）与状态页（已完成）

**动机**：即使人在家里、和 NAS 同处一个局域网，客户端原本也一律走绿联中继 ——
流量路径是 NAS → 公网 → 中继 → NAS（M0 实测 230–300ms），而局域网内只要个位数毫秒。

**实现**：

| 项 | 说明 |
|-|-|
| `mode: lan` | 直连 `nas_lan_host:<端口>`，**完全跳过绿联**（不需要绿联账号、不需要 SSO 会话） |
| `mode: wan` | 经绿联中继（原行为） |
| `mode: auto` | 默认。每 `lan_probe_seconds`（默认 10s）TCP 探一次局域网可达性并自动切换 |
| 热切换 | `--mode lan\|wan\|auto`，或状态页上点按钮；**不用重启**，切换时作废会话缓存 |
| 状态页 | `http://127.0.0.1:8898/`（仅回环）：每行给出本机地址（蓝）与该服务自己的绿联外链（灰）、最近 30 分钟趋势柱状图（每分钟一柱、失败叠红段、悬停给数字）、上下行流量、最近一次错误，以及每个服务独立的开关与端口输入框；`/status.json` 为机器可读版 |

**实测（同一服务，热切换瞬间）**：外网中继 **348–550 ms** → 局域网直连 **15–21 ms**，约 20 倍。

**一个关键的坑（改这段代码前必读）**：

> 局域网模式下**拨号地址是局域网 IP，但 Host 头仍然是公网域名**。
>
> 原因：Authelia 会校验请求 URL 的域名必须匹配它配置的 `session.cookies[].domain`，
> 而那里只登记了公网域名。用局域网 IP 当 Host 会直接 401，Authelia 日志原话：
> `unable to retrieve session cookie domain provider: no configured session cookie domain matches the url 'https://<NAS局域网IP>:8897/api/firstfactor'`。
>
> 这个坑很隐蔽：代理转发那一条路径改了 Host，但**Authelia 登录请求是另外发的**，
> 第一次修只改了前者，仍然 401。两处都要改。
>
> 让后端看到的 Host 与外网模式完全一致，也顺带避免容器应用因 Host 变化而行为不同。

**依赖注入上的一个教训**：`newModeRouter` 必须自己调用 `sessions.SetLAN(...)`，
不能指望调用方记得同步 —— 会漏。已改成构造函数内部完成。

## 十一、分层原则：传输层不认识应用

这一节记录一条**方向性**的决定，它比任何一段代码都重要，因为后面的取舍都要回头看它。

### 原则

> **nas-mirror 只负责"连接"（认证 + 链路 + 转发），永远不负责"应用"。**
>
> 它不知道对面跑的是 WebDAV、漫画站还是 API —— 正因为不知道，才能同时服务 10 个服务，
> 而且加第 11 个只要在配置里加一行。

### 反面例子：我自己先犯了一次

为了让 WebDAV 客户端不用配账号密码，我加了一个配置项 `inject_basic_auth`。
功能上没问题，但**表达上把应用概念写进了传输层**：

- 字段名、注释、文档都在说"**代持 WebDAV 的 Basic 凭据**"
- 凭据来源写死成 `UGREEN_*`，等于假设了"这个应用用 NAS 账号"
- 想再接一个需要 Basic 的服务，就得再加一个开关

**是用户指出来的**："它作为一个客户端和服务端，只是起到了端口转发的功能，
我们突然给它加上 WebDAV 和命令行功能，反而让它的功能不统一了，有点耦合了。"

### 正解：把"加个头"做成通用的

```jsonc
// 现在（通用：传输层只懂"加个头 + 展开变量"）
{ "port": 28006, "service": "webdav",
  "headers": { "Authorization": "Basic ${BASIC_AUTH}" } }
// 2026-09-23 起 WebDAV 已不需要这一条（服务端去掉后端认证，见 §7.1 的实测结论）；
// 能力保留，供将来"要求固定头的后端"使用。
```

`${VAR}` 支持派生变量、进程环境变量、Windows 用户级环境变量；查不到的变量原样保留。
`BASIC_AUTH = base64(用户名:密码)` 是唯一一个派生变量 ——
而 `Basic` 是 RFC 7617 定义的 **HTTP 层**方案，不是应用概念，所以放在传输层是干净的。

**客户端代码里没有任何一行知道 "WebDAV" 这个词。**

### 顺势做的清理

同一原则下，`webdav-proxy`（一个 netcat 桥接容器）被删掉了：
它存在的唯一理由是给 WebDAV 一个独立的绿联公网入口（给手机 App 点），
而客户端这条路走的是网关 → 宿主 nginx18005 → UGOS 内置 WebDAV，**从来不经过它**。

删掉后宿主上还剩 11 个 docker 发布端口（8 个应用 + 网关 + PG + …），
`app-28005/28006` 两个入口随即变成 `500 入口已死`。手机 App 不再有 WebDAV 链接 ——
用户确认不需要（手机上用绿联 App 自己就能操作文件）。

### 判据：一个新功能该不该进客户端？

| 问 | 该进 | 不该进 |
|-|-|-|
| 它懂不懂"某个应用"的语义？ | 不懂（认证、链路、转发、头、日志） | 懂（"这是 WebDAV"、"这是 exec 接口"） |
| 加第 11 个服务要不要改代码？ | 不要（改配置即可） | 要 |
| 换个应用还用得上吗？ | 用得上 | 用不上 |

按这个判据，"把 WebDAV 和命令行内置到客户端"这个想法被否掉了 ——
不是做不到，而是**做进去之后它就不再是传输层了**。想要更方便的用法，
应该做成**另一个独立的工具**去调 `127.0.0.1:<端口>`，而不是把语义塞进传输层。

### 这一节为什么值得单独写

同一个病，这段对话里犯了两次：

1. **M2 统一网关与收敛**（§M2.6）：把"服务端也该统一"当成了用户的需求，做出来才发现要回滚。
2. **`inject_basic_auth`**：把应用概念写进传输层，改动小但方向错。

第一次是**做完了才回滚**，第二次是**用户在动手前拦住的**。差别不在技术，在于是否先问。

## 十二、清理记录（2026-09-11 晚）

### watchtower 轮询：30 秒 → 5 分钟

原来 `WATCHTOWER_POLL_INTERVAL=30`，一天 2880 次请求；而且它**会自动重建带标签的容器**
（含 `nas-console` 那个 root shell），重建会打断正在进行的会话。已改为 300。

**顺带查清了一件重要的事：它到底覆盖哪些服务。**

| 自动更新 | 服务 | 为什么 |
|-|-|-|
| ✅ 开 | nas-console、bili23-web、account-panel、browser-proxy（＋当时的 nas-hello） | **正好是"我们自己有 CI 工作流、会往 ghcr 推镜像"的那几个** |
| ❌ 无标签 | openlist、hermes、sakura-pg | 上游官方镜像，不是我们构建的 |
| ❌ 无标签 | jmcomic-web、music-tag-web | 本地 `build:` 构建 / UGOS 应用市场安装 |
| ❌ `enable=false` | sso-gateway ×2 | 当初为避免配置漂移刻意关的 |

所以整条链路（push → GitHub Actions 构建 → ghcr → watchtower 自动部署）**是完整的**：
覆盖的正好是"自己构建的镜像"，没覆盖的都是不该自动更新的（自动更新上游镜像反而危险）。

> ⚠️ **watchtower 只换镜像，不读 compose 文件** —— 它按容器当前配置重建。
> 所以改了 compose（端口、网络、环境变量）之后，仍然要自己 `docker compose up -d`。
> 这条不写下来很容易误以为"push 了就什么都会生效"。

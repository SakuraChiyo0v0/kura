# 2026-09-23 WebDAV 去掉自己的认证（改成"只有网关进得来"）

## 起因（用户的判断，是对的）

> "webdav 的服务没包装好？按理来说这种 rclone 都封装到服务内部就好了，不需要外部再单独输入密码。"
> "我不觉得给网关是对的 —— 我觉得他本身不需要这个认证，直接在容器内解决，外部对这个认证无感是对的。"

背景：nas-mirror 客户端配置里始终留着一条 `webdav`，作用是**代填 `Authorization: Basic ...`**。
它存在的原因是 WebDAV 后端（rclone）自己带认证 —— 即设计文档 §7.1 记的「WebDAV 的认证叠加」：
网关 Authelia 认人 + 后端再认一次服务。我当时提的方案是"把凭据交给网关代填"（凭据仍在，只是换地方），
用户否掉了：**应该让后端根本不需要这层认证**。

## 做了什么

`<部署根>/nas-webdav/docker-compose.yaml`（仓库副本 `server/nas-webdav/docker-compose.yaml`）：

| 项 | 旧 | 新 |
|-|-|-|
| 网络 | `network_mode: host` | 只挂 `sso-net`，**不发布任何端口** |
| 监听 | `--addr <NAS局域网IP>:18005` | `--addr :18005`（只在容器内） |
| 认证 | `--user/--pass`（= NAS 主账号） | **去掉**，由网关注解 |
| 凭据文件 | 同目录 `.env`（600，含主密码） | **删掉**（改名 `.env.unused-*`） |

网关（`server/nginx/conf.d/default.conf`）两处上游：`http://<NAS局域网IP>:18005` → **`http://nas-webdav:18005`**
（容器名，Docker 内置 DNS 解析），并把那段"为什么绑局域网 IP"的注释改写成新形态的说明。

客户端：`config.json` 的 `services` 变成 **空数组** —— 11 个服务全部由服务端清单下发，
WebDAV 落到本机 **18005**（不再需要 28006，也不再代填凭据）。

## 为什么这样比"交给网关代填"更好

1. **密码不存在了**：客户端不用存、网关配置里也不用存；`ps` 里也再看不到明文
   （旧形态的 rclone 命令行上就印着主密码，同机任何用户都能 `ps aux` 读到）；
2. **最弱的一条路被彻底关掉**：旧形态靠"绑局域网 IP"躲绿联中继，代价是写死 IP、换 IP 静默 502；
   现在宿主上**根本没有监听**（实测 `curl <NAS局域网IP>:18005` → `000`），局域网与中继都摸不到；
3. **顺手治了两个老毛病**：不再写死局域网 IP（网关改按容器名）；
   后端终于有了自己的编排文件（此前是 compose 管的手搓容器，头部那堆实测教训也一并留档）。

## 代价（用户明确拍板接受）

无认证 + 挂在 `sso-net` ⇒ **同一条 docker 网络上的任何容器**都能无凭据读写整个宿主文件系统
（当前该网络上有 openlist / bili23-web / jmcomic-web / hermes / nas-console 等 12 个容器）。
想收紧的最省事做法：给 `nas-webdav` 单独建一条网络、只让网关也加入它 —— 客户端与网关都不用改。
这条已写进 compose 头部、设计方案 §7.1 与 sso-gateway skill，免得以后忘了这是"选择"而不是"疏忽"。

## 换的过程里撞出来的一个真问题：`services: []` 起不来

改完客户端配置重启，客户端**直接退出**：
`错误：配置里没有任何服务（services 为空）`。这是 `validate()` 里的老校验 ——
在"服务列表全靠服务端下发"的新形态下已经站不住了。顺着又发现第二处：
`main` 里 `if okCount == 0 { return errors.New("所有端口的会话都建立失败") }`，
空服务时 `ports` 为空、`okCount` 也为 0，会被误判成"会话全失败"而拒绝启动。

两处都改了，并**把旧测试也改了**（`TestValidateRejectsEmptyServices` 断言的是被推翻的旧行为，
改成"空 services + 关掉发现才算错"）。

> 教训：把"必须至少有一条配置"改成"可以全靠下发"时，**校验层与启动层的所有"至少一个"假设都要过一遍** ——
> 光改渲染逻辑不够。

## 验证（判据都是实机）

| 检查 | 结果 |
|-|-|
| 容器新形态 | `NetworkMode=sso-net`、`Ports={}`、`Cmd=[serve webdav /data -L --addr :18005]`（无 `--user/--pass`） |
| 网关能按容器名取 | 网关容器内 `wget http://nas-webdav:18005/` → 目录列表 ✓（**不带任何凭据**） |
| 旧暴露面已关闭 | 宿主 `curl <NAS局域网IP>:18005` → `000`（没人监听）✓ |
| 客户端零配置 | `config.services = 0`，服务数 11、全部在监听、0 失败（来源全是 `discovery`） |
| WebDAV 真能用 | `PROPFIND http://127.0.0.1:18005/volume1/` → **207**、14226 字节、返回是真实 `multistatus` **且客户端没有任何 headers 配置** |
| 其它服务 | nas-console 200 / openlist 200 / navidrome 302 ✓ |
| 网关语法 | `nginx -t` 通过后才 reload；改动前核对线上 sha、并留了 `default.conf.pre-webdav.bak` |

## 遗留风险

- 上面那条"同网络容器无凭据可读写全盘"是**已知且接受**的代价。
- 本机 WebDAV 端口从 28006 变成 18005（谁要是抄了旧地址就得改）。
- rclone 仍是 `--user/--pass` 之外的形态：**如果哪天有人把认证加回去，记得客户端那条配置也要跟着回来**。
- 主密码仍在别处使用（NAS 登录等），"与登录同串"这件事本身还没处理（用户此前选择先不管）。

# 2026-09-14 nas-mirror 仓库泄密事件与处置

## 是什么

用户建 `nas-mirror` 仓库、要求把服务端也放进去时，我先把**从会话记录重建出来的 `server/`**
（12 个服务的 compose 副本 + sso-gateway 的 nginx 配置 + nas-webdav 的脚本）提交并推上去了。
用户指出：**不只是密码，compose 本身就是敏感内容**（端口、容器名、内部路径、服务清单），
要求从 git 历史里删除。

取证结果：初始提交里 `server/postgres/docker-compose.yaml` 含**明文 Postgres 密码**
（`[已脱敏，Kura 副本删去部分字符]` —— 与 NAS 登录/sudo 密码**同一个字符串**），已推送到 GitHub **私有**仓库，
存在约 1 小时。工作区其余位置核查：`bili23-web`（**公开**仓库）工作区与全部历史**都没有** ✓；
归档的 `sso-gateway` 仓库历史也没有 ✓。

## 处置

1. 本地重建历史：`git checkout --orphan` → 用**当前干净树**建一条提交 → `git branch -M`；
2. `git reflog expire --expire=now --all` + `git gc --prune=now --aggressive`；
3. **删掉仓库并用同名重建**（`gh repo delete` 缺 `delete_repo` 权限 → 用户在网页上删），
   再 `push` 那唯一一条提交；
4. 验证：新仓库 1 提交 / 43 文件 / 密码 0 命中；**用完整 SHA 尝试 fetch 旧提交 → "远端已无此对象"**，
   并用 `fetch main` 成功作为对照（证明不是网络问题）。

## 关键认识：force-push 不等于删除

force-push 只让旧提交**不可达**，对象仍留在仓库里、**仍可按完整 SHA fetch 到**
（实测：push -f 之后四个旧提交全部仍可访问 ✗）。GitHub 的 gc 时间不可控，
**要彻底清除只能删仓库**（或找 GitHub Support）。

## 踩过的坑（判断方法本身错了三次）

1. **用短 SHA 查"是否还存在"** → API 返回 404，我判成"已删除" ✓✓ **假阴性**；
   换成完整 SHA 才发现对象都还在。
2. **空仓库查询返回 409**，我的判断分支只匹配 404/Not Found → 输出"仍可访问" ✗ **假阳性**；
3. **本机 git 配了失效代理**（127.0.0.1:7897），`fetch` 报 `Failed to connect to github.com
   over proxy` —— 我把**网络失败**当成了"对象不存在" ✗ **假阳性**。
   → 教训：**删除/清理类操作的验证，必须 ①用完整标识符 ②打印原始响应 ③带一个"应该成功"的对照组**
   （本次 `fetch main` 成功就是对照）。否则"没有报错"和"操作真的生效了"根本分不开 ——
   这与本项目硬约定 #4（判据要能区分"真成功"和"看起来像成功"）是同一件事。

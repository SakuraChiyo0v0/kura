## 一、起因

需求原话：**"外网电脑上的应用去访问客户端，就跟访问服务端一模一样，无需考虑任何绿联的东西。"**

约束（用户确认）：只做 HTTP、不引入组网（公司电脑装不了驱动，且担心内网穿透）、
只允许客户端 → 服务端单向发起。

## 二、做了什么

### 阶段 1：M0 实测（先把事实搞清，再动手）

把整条绿联外网链路变成**可观测的数字**，工具留在 `nas-mirror/tools/probe_external.py`。

**关键结论**：

| 问题 | 结论 |
|---|---|
| 应用会话能否跨端口复用 | **不能，严格按端口隔离**。4 个端口 → 4 个不同 cookie |
| 有没有可长期保存的令牌 | **没有**。`static_token` → `code=1114`，`third_token` → `code=1024` |
| `api_token` 寿命 | `keepalive=false`：600s 有效、**1200s 已过期**；`keepalive=true`：**>1.3 小时**仍有效 |
| `keepalive` 有无其他副作用 | **无**（用"两次 false 作对照组"测噪声底，超出噪声的差异为 0） |
| 延迟 | 直连中继 230–300ms；复用连接 38–72ms；局域网直连 **15–21ms** |
| WebDAV 吞吐 | 上传 53 / 下载 55 Mbps，1 MiB 往返字节一致 |
| 中继是否支持 HTTP | **只转 HTTP**。SSH/SMB/PG 这些裸 TCP 过不去 |

### 阶段 2：M1 客户端

`nas-mirror/client/`，Go 单二进制，**78 个测试**。核心能力：

- 把 NAS 服务镜像到 `127.0.0.1:<同端口>`，应用零改造
- 绿联 SSO 全自动（RSA 登录 → 换令牌 → once-token → cookie → 续期 → 失效重建）
- **三条安全红线写在代码里**：只监听回环、只出站、不跟随重定向
- 链路模式热切换：局域网直连 / 外网中继 / 自动探测
- 状态页（可点击、分组、深浅色）+ 日志落盘 + 开机自启脚本

### 阶段 3：M2 统一网关（**做出来又回滚了**）

`sso-gateway`（nginx + Authelia）从"从未部署"到上线，支持请求头与路径前缀两种分流。
把 10 个服务的独立公网入口收敛成 1 个，**随后因为一个漏项整体回滚**（见"踩过的坑"第 1 条）。

最终形态：**独立入口与网关两条路并存**。网关保留，作为可选的单点登录入口。

### 阶段 4：skill 与文档沉淀

- 新增 4 个 skill：`nas-mirror`、`sso-gateway`、`nas-external-link`、`nas-new-service`
- 4 份同步到飞书（`Harness/skill/`），本地镜像存在 `feishu-harness/skill/`
- 修正 `docs/sso-spec.md` 里一条**早已被推翻却没同步**的结论
- 审计记录追加"问题 6–12"：`feishu-harness/经验总结/文档审计与错误纠正记录.md`

### 阶段 5：清理

| 项 | 结果 |
|---|---|
| watchtower 轮询 | 30 秒 → **5 分钟**（30 秒 = 一天 2880 次，且每次发现新镜像就重建容器） |
| 孤儿镜像 | **清零**（12 个镜像全部被引用） |
| 空网络 | 8 个 → **清零** |
| Build cache | 回收 **308.4MB** |
| 容器 | 13 → 12（移除 `nas-hello` 测试应用与 `webdav-proxy`） |
| docker 卷 | **一个没动**（4 个未用的加起来才约 2MB，零收益纯风险） |

## 三、踩过的坑（本归档最重要的部分）

### 1. 把"我自己的架构偏好"当成了用户的需求 🔴

**做了什么**：用户只说要做"端口转发客户端"，我顺手把"服务端也该统一"也做了——
统一网关 + 把 12 个独立公网入口收敛成 1 个，还把它推销成"顺便解决安全问题"。

**漏掉了什么**：**手机绿联 App 里的"外部链接"是按"端口有没有发布到宿主"自动生成的。**
删掉 `ports:` 就等于删掉那些链接，而绿联 App 不可能发 `X-Nas-Service` 头，走不通网关。
这是收敛的**硬性代价**，不是可以绕过的实现细节。

**结果**：整套回滚。用户原话："它作为一个客户端和服务端，只是起到了端口转发的功能，
我们突然给它加上……反而让它的功能不统一了，有点耦合了。"

**教训**：提方案时要问自己"这是他要的，还是我觉得该有的"。代价要主动说，别等对方发现。

### 2. 验证脚本的判据必须能区分"真成功"和"看起来像成功" 🔴

写"路径前缀能不能用"的检查脚本，第一版**只看 HTTP 状态码**，得出"7/9 可用"。

**是假阳性**，两个原因：
- SPA 对任何未知路径都兜底返回 index.html（200），"200"不代表那个资源真的在
- 门户页返回的 200 也被算成了"资源可访问"

改成"**取回来的是不是门户页**"之后，真实结果是 **3/9**。

### 3. 不跟随重定向，不轻信 200 🔴

`urllib`（以及 Go 的 `http.Client`）**默认自动跟随重定向**。
中继把"你未认证"实现成 `302 → UGOS 登录页`，跟随之后就变成一个 **HTTP 200**——
**"被拒绝"被伪装成了"成功"**。

第一轮实测因此得出了完全错误的结论（"一个 cookie 能访问所有端口"）。

### 4. 改数据落盘方式之前，先看运行中的容器到底挂的是什么

`sakura-pg` 的 compose 写着绑目录 `<部署根>/postgres/data`，注释还声称"已迁移"，
但 `docker inspect` 显示它**实际挂的是具名卷** —— 那份 compose 从未被应用过。
两边都是合法的 PG18 数据目录。谁跑一次 `docker compose up -d`，数据库就会切走，
而 **Authelia 的用户库就在这个库里**。

**教训**：别信 compose 注释，看 `docker inspect`。

### 5. 手工 `docker network connect` 加的网络成员身份，容器一重建就没了

踩了**两次**：`nas-hello`、`sakura-pg`。
第二次的症状是 Authelia 报 `lookup sakura-pg on 127.0.0.11:53: no such host`。

**规矩**：凡是网关要访问的容器，网络必须在**它自己的 compose 里声明**。

### 6. nginx 的 `resolver` 不读 `/etc/hosts`

变量形式的 `proxy_pass` 会用 `resolver`（Docker 内置 DNS）解析，而内置 DNS
**不认识** `host.docker.internal`（那只是 `extra_hosts` 写进 `/etc/hosts` 的）。
写域名会得到 `could not be resolved` 并返回 502。**必须写 IP 字面量**。

### 7. `auth_request` 会把客户端的 `Authorization` 头带进鉴权子请求

WebDAV 客户端带 `Authorization: Basic <NAS账号>`，Authelia 拿它当**自己的** Basic 凭据去查用户库，
库里只有 `<网关用户>`、没有 `<用户A>` → **整个鉴权失败，哪怕会话 cookie 完全有效**。
修法：在鉴权 location 里 `proxy_set_header Authorization "";`

### 8. 删除要连着引用一起删

删 `nas-hello` 时，它出现在 **网关 map、客户端配置、三个工具、五份文档** 里。
只删容器的话，网关会开始返 502、工具会开始报失败、文档会继续骗人。

### 9. 用某个工具之前，先读关于它的那份 skill

同步 skill 到飞书时，我只验证了标题和内容就以为完事。
后来读了那份 feishu-mcp 文档才发现：`doc_create` 的 `folder_token` **会被忽略**——
4 篇新文档全散在"我的空间"根目录，而**文档里白纸黑字写着这个坑**。

## 六、一句话

**需求本身（外网无感访问）做到了，而且比预期好**（多代理了 8 个服务、局域网快约 20 倍）。

那一轮的教训（先问、报价、别把自己的偏好当需求）比代码值钱。

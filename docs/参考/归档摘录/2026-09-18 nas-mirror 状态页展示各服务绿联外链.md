# 2026-09-18 nas-mirror 状态页改为展示各服务自己的绿联外链

## 起因

用户看着状态页问："（本机地址 8890 下面）那个链接怎么都是 8897？我想要这个服务**真实的 uglink 链接**，
点开能到这个服务，而不是发往网关的。"

原页面上那行"上游"写的是客户端**把请求发到哪**：M2 之后 9 个服务全部经统一网关，所以都是 `app-8897-…`。
这没错，但读起来像"这台服务在 NAS 上的地址"，确实容易误解 —— 尤其用户要的是**手机绿联 App 里
"外部链接"那条**（`app-<宿主端口>-<设备>.ugdocker.link`），那是直连该服务、不经我们网关的路。

## 做了什么

- 状态页每行在"本机地址"下面改为展示该服务自己的绿联外链（可点），并标注"绿联登录后可达"；
  网关地址不再作为链接出现在这里（"经由"列照旧写着 `网关:openlist`，路由信息没丢）。
- `/status.json` 增加 `external` 字段（`upstream` 保留，供程序读）。
- `--status` 表格里"实际上游"列换成"绿联外链"。
- 外链用现成的 `appBase(base, port)` 推导，抽成 `externalURL()`：推不出来（base 不是 `.ug.link`）就**返回空串**，
  模板退回显示上游 —— **宁可不显示，也不硬造一个域名**。

## 关键发现：那个 302 证明不了任何事

第一版验证是"直接请求 9 个 `app-<端口>` 看返回码"：9 个全是 **302 → 绿联登录页**。
差点就此写"9 个外链都活着"。**按本项目硬约定 #4 加了对照组**：

| 端口 | 状态 |
|-|-|
| 8890/9119/8642/28006/5244/8022/8080/8788/8787（正常服务） | 302 → 登录页 |
| **18005**（2026-09-12 故意关掉、公网不可达） | 302 → 登录页 |
| **19999**（随机、根本没发布） | 302 → 登录页 |
| 5005（宿主内置 WebDAV） | 302 → 登录页 |

**结论**：绿联中继在检查端口是否存在**之前**就先要求登录，所以**任何端口都返回同一个 302**。
"302 = 入口存在"是彻底的假阳性；要判断入口是否真的可用，必须带绿联会话（`tools/probe_external.py` 那套登录流程）。
页面上因此写的是"绿联登录后可达"，不是"已验证可达"。

> 这与项目里既有的两条教训是同一族：SPA 对未知路径兜底返回 index.html、中继把"未认证"伪装成 HTTP 200 ——
> **判据必须能区分"真成功"和"看起来像成功"**。

## 同日第三轮：把「请求 / 失败」两列换成趋势柱状图

用户看完说："请求/失败，感觉可以用时间线的柱状图来表示，更好展示趋势。"

- **数据**：`serviceStats` 里加一圈定长分钟桶（`trendBuckets = 30` 格 × `trendBucketSeconds = 60` 秒）。
  关键约定：**柱子按墙钟时间对齐**，不是"来一次请求就往前挪一格" —— 空闲时没人调用它，
  下次来请求按时间差一次性补零；否则空闲会被压缩，画出来的趋势是假的（"看起来一直在忙"）。
  读的时候也会把窗口推到当前时刻，所以"最近 30 分钟"是真的最近 30 分钟。
- **渲染**：服务端把几何算完（`chartBars`），模板只拼 `<svg>` + `<rect>`，
  每根柱子带 `<title>` 做悬停提示（`10:08 · 3 请求 / 0 失败`）。**不引任何前端库**，与本页一贯做法一致。
  高度按窗口内峰值归一（只回答"什么时候忙"）；失败画成叠在柱顶的红色段。
  空闲格画 1px 淡基线，时间轴才看得见。
- **命令行**：`--status` 加一列迷你趋势图 `▁▃▅█`（终端里画不了 SVG）。
- **删掉的**：`请求` / `失败` 两个数字列（改成柱子 + 柱下一行"累计 请求 · 失败"）；
  顺带删掉随之不再使用的 `.num` / `.ok` / `.bad` 三条 CSS（不留死代码）。

### 测试逼出来的一个真缺口

写测试时两条失败：一条是我期望写错（`noteError` 不会重复计一次请求），
**另一条是真问题**：某一格"只有失败、没有请求"时（会话建立失败那条路径会这样），
`chartBars` 原来走"空闲格"分支直接 `continue`，**把这根失败柱整根丢掉了** —— 图上完全看不见。
已改成：这种格子画一根最小的全红柱，悬停提示如实写 `0请求 / 2失败`。这正是本项目最忌讳的
"看不见的失败"。

## 同日第五轮：加上行/下行流量统计

用户要"流量上行下行的统计数字，方便看流量"。

- **在反代两侧各包一层计数**（`mirror.go`）：`countReader` 统计从调用方读走的请求体 = **上行**；
  `countWriter` 统计写回的响应体 = **下行**。都**不含 HTTP 头**。
- **`countWriter` 必须把 `Flush` / `Hijack` 透传给底层 ResponseWriter** —— 少了 `Hijack`，
  WebSocket 升级会因为"ResponseWriter 没实现 Hijacker"直接失败。
  这一点不用另写测试：既有的 `TestMirrorTunnelsWebSocketUpgrade` 就是那道闸（实测仍通过）。
- **代价（如实记）**：升级之后的字节由被接管的连接直接搬运，**不经过计数器** —— WebSocket 流量不计。
- 展示：每行 `↑ 上行 · ↓ 下行`（`humanBytes` 转 1024 进制，悬停给原始字节数），页面顶部一行合计；
  `/status.json` 增加每服务 `bytes_up` / `bytes_down`；`--status` 表格加两列并在首行给合计。

### 验证（判据是"与 curl 报的字节数吻合"，不是"计数器动了"）

| 操作 | curl 报的 | 客户端增量 |
|-|-|-|
| `GET openlist 首页` | `download=4302` | ↓ **+4302**、↑ +0 ✓ |
| `POST 2048 字节` 到 nas-console 一个不存在的路径（返回 404，**不写 NAS 任何东西**） | `upload=2048` | ↑ **+2048**、↓ +0 ✓ |

单测另加三条：双向字节精确相等（2000 字节往返）、无 body 的 GET 上行必须为 0、`humanBytes` 换算。

## 遗留风险

- 外链是否真的通，仍然需要用户点开（或在 NAS 上确认该端口已发布）才能知道 —— 客户端验证不了。
- `webdav` 那条的宿主端口在配置里是 `28006`（早期 netcat 桥接容器的端口），而 M2 之后 WebDAV 后端已换成
  `nas-webdav` 容器的宿主 `18005`。**所以 `app-28006` 很可能已经没有对应入口**。
  这条没动：它不是本次需求，改动它要连带核对客户端配置里 `port` 的语义（现在同时当本机端口用）。
